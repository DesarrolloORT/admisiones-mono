Cómo se integra un endpoint de backend

El camino completo de un dato, desde el swagger del backend hasta la pantalla. Hay una sola puerta de entrada al front — el adapter — y todo lo demás depende de tipos nuestros. Este diagrama es el mapa; abajo está el porqué.

Por qué no llamamos al endpoint directo

Antes esto era una línea: importabas el endpoint generado en el .ts , y el DTO que volvía era el modelo de la pantalla. Funcionaba hasta que algo del otro lado cambiaba. Estas tres capas existen para que ese cambio se pague una vez y en un solo archivo.

El adapter · la única puerta

En el swagger todos los campos son opcionales . Si el DTO llega crudo a la pantalla, ese ? se te propaga a cada template, a cada computed y a cada test: cien ?? '' repartidos por la feature.

El adapter colapsa la nullability una sola vez y devuelve tipos donde los campos existen. Y el default no se improvisa: requiresPriorEnrollment cae en true porque es el caso restrictivo — un backend caído nunca debe habilitar una postulación.

  • Es el único que importa generated/** y ApiHttpClient .
  • Si mañana el backend renombra un campo, se toca este archivo y nada más.
  • Sus tests son los que fijan el mapeo, los defaults y el body exacto del POST.

La fachada · dónde vive el estado

Un GET de lectura no necesita fachada: la page inyecta el adapter y listo. La fachada aparece cuando hay orquestación real .

En el proceso de becas los steps se destruyen al navegar. Si los FormGroup fueran del step, volver atrás perdería lo cargado — por eso viven en ScholarshipProcessFacade , que tiene scope de página.

  • Un POST se dispara de una fachada, nunca del template.
  • Siempre con finalize() para apagar el spinner y takeUntilDestroyed() para cortar si el paso se desmonta.
  • Las fachadas de sección validan lo suyo y recién entonces llaman a process.continue() .

Lo que no existe

No hay capa store/ y casi no hay services/ . Si un método sólo iba a hacer return this.api.mismoMetodo() , no se escribe : el consumidor inyecta el adapter.

Un service existe sólo si aporta comportamiento propio — combina llamadas, guarda estado, prepara archivos.

  • Los FormGroup salen de factories en models/ .
  • Las cards son presentacionales puras: sólo input() , sin inject() .
  • Las fechas quedan string | null ; el Date se arma en la UI.

El atajo y el camino

Los dos hacen lo mismo hoy. El de la izquierda no compila: eslint.config.js y npm run check-api-contracts lo rechazan.

Antes · hoy bloqueado

// pages/scholarships/scholarships.ts
import { getScholarshipsAvailableEndpoint }
  from 'shared/api/generated/endpoints/…';

data = toSignal(
  this.http.get(endpoint)
);

// el DTO ES el modelo de pantalla:
// scholarship.name?  scholarship.description?
// …y un ?? '' en cada template

La pantalla queda acoplada al swagger. Un campo que cambia de nombre rompe templates, tests y computed a la vez, y no hay un solo lugar donde arreglarlo.

Ahora · el camino

// api/scholarships.api.ts — el adapter
getAvailableScholarships(): Observable<AvailableScholarships> {
  return this.api.data(endpoint).pipe(
    map(r => ({
      requiresPriorEnrollment: r?.… ?? true,
      scholarships: (r?.scholarships ?? []).map(…),
    }))
  );
}

// pages/… — la page inyecta el adapter
available = toSignal(
  this.scholarshipsApi.getAvailableScholarships()
    .pipe(catchError(() => of(EMPTY_CATALOG))),
  { initialValue: EMPTY_CATALOG }
);

La page no sabe que existe un swagger. Habla con un tipo de la feature donde los campos existen, y el fallback ante error es explícito.

Regla práctica: si en un archivo que no está en api/ escribís la palabra generated , algo está mal ubicado. Y si no encontrás el endpoint en generated/endpoints/ , el paso es npm run api-spec:refresh && npm run update-api — nunca escribir la URL a mano.

Qué hay hecho y qué falta

Los cuatro endpoints de becas existen en el swagger. Estos son los que ya bajaron al front y hasta dónde llegaron.

Endpoint Estado Hasta dónde llega
GET /scholarships/available Completo Adapter → pages/scholarships . Es el recorrido de referencia: copialo.
GET /scholarships/enrollments Sin consumidor Mapeado en el adapter con api.list . Hoy nadie lo usa: /available ya responde la habilitación.
POST /scholarships/applications Sin consumidor Mapeado en el adapter. Falta dispararlo desde facades/scholarship-proposal.ts al confirmar el paso 1.
GET /scholarships/application-options El próximo Opciones del paso 1: inscripciones, modalidades y fechas de prueba. Todavía no está en el adapter.

Tu primer endpoint, paso por paso

Tomando application-options como ejemplo. Son dos archivos nuevos y tres ediciones.

  1. Leé el contrato de negocio primero. .api-spec/contracts/becas.contract.json es la autoridad de estas pantallas. El frontHint de este endpoint dice exactamente cómo se filtran las pruebas y de dónde sale el testId — el front no lo calcula , lo elige de tests[] . El OpenAPI no te cuenta eso.
  2. Bajá el contrato. npm run api-spec:refresh y después npm run update-api . Si el endpoint no aparece en generated/endpoints/ , falta del lado del backend — no inventes la URL.
  3. Escribí el tipo de la feature en models/…interface.ts . Sin opcionales, fechas como string | null . El sufijo .interface.ts importa: exime del spec obligatorio en test-generator.config.json .
  4. Agregá el método al adapter. Objeto → api.data ; array → api.list (normaliza null , objeto suelto o array; no escribas ese chequeo a mano); POST/PUT → api.request con body . Elegí el default ante ausencia de dato pensando en cuál es el caso restrictivo.
  5. Cubrilo con un spec. Mapeo, defaults de nullability, lista vacía y body exacto. Se stubea sólo request sobre el prototipo real de ApiHttpClient , así list() y data() corren de verdad.
  6. Consumilo. Lectura simple → la page inyecta el adapter. Orquestación o estado entre pasos → una fachada.
  7. Sumá el mock e2e en e2e/support/api-mocks.ts . Playwright no pega al backend, y cada endpoint nuevo necesita su handler.
  8. Actualizá docs/flujos/becas.md en el mismo PR, o declará docs-none: <motivo> .

Dos pendientes abiertos que te vas a cruzar: faltan los ID_TIPO_BECA de reválidas, concursables y capacitación laboral (hay un fallback por palabra clave del nombre, marcado para borrar en cuanto backend los pase), y el POST de postulación todavía no tiene quién lo dispare.
