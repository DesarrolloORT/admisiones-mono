## Aplicabilidad y alcance

La búsqueda en src/, package.json y package-lock.json del frontend no encontró WYSIWYG, contenteditable, Quill, CKEditor, TinyMCE, TipTap, Froala, Summernote ni rich text; tampoco innerHTML, outerHTML, insertAdjacentHTML, DomSanitizer, bypassSecurityTrustHtml, DOMPurify, srcdoc, DOMParser, document.write o createContextualFragment. Esto sustenta ausencia de esas implementaciones en las rutas buscadas, sin demostrar ausencia global de HTML no confiable.

Hay textareas de texto libre en becas y consulta de resultado. El reglamento es HTML fijo versionado; el formulario de pagos crea nodos y asigna input.value. Estos mecanismos leídos no son editores HTML enriquecidos. La API acepta JSON y aplica un filtro global de sanitización a argumentos MVC. Se incluyen filtro, exclusiones, tests existentes y un flujo real de listas de texto libre hasta entidades y response. Core se incluye como constructor/transporte de correo HTML; el consumidor leído construye plantillas institucionales y codifica nombre/link.

Quedan fuera de inspección interna las librerías @desarrolloort/components, fdp-components, ngx-utils y sus artefactos instalados; servicios de correo/pagos; otras aplicaciones que leen la misma DB y otros consumidores de Core. No se afirma NOT_APPLICABLE global por falta de ese inventario ni se evalúan requisitos de SVG, SMTP o templates como puntos adicionales.

## Resultado por componente y conclusión

- Frontend: NEEDS_REVIEW. No se localizaron entradas enriquecidas ni sinks HTML explícitos en código propio; falta inventario interno de librerías y evidencia desplegada para excluir mecanismos similares.
- API: NEEDS_REVIEW. Existe biblioteca de sanitización y registro global estático. La cobertura genérica presenta un límite concreto de colecciones; falta validación ejecutada y justificar el tratamiento de cada flujo que realmente acepte HTML.
- Core: NEEDS_REVIEW. El flujo institucional leído utiliza HTML propio con valores codificados; el helper compartido no sanitiza por sí mismo y falta inventario de consumidores.
- Conclusión: análisis documental completo del ID; no hay evidencia suficiente para PASS/FAIL ni NOT_APPLICABLE global. La brecha de listas no demuestra XSS: no se identificó que sus valores se interpreten como HTML ni provengan de un editor enriquecido. Se aplica [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md).

## Hallazgos y propuesta documental

### H1 — Cobertura de colecciones del filtro no demostrada

Condición: SanitizeObject refleja propiedades y omite indexadores problemáticos; no enumera elementos ni reemplaza strings de colecciones. SaveInitialSurveyRequest incluye listas de texto que los pasos leídos solo normalizan. Si un consumidor futuro o externo las trata como HTML, confiar en el filtro global podría dejar contenido activo sin tratar. Evidencia E5/E9/E10. No se confirma vulnerabilidad ni severidad.

Responsable candidato: API, coordinando con frontend y consumidores de la DB. Propuesta futura: acordar cuáles campos son texto y cuáles admiten HTML. Mantener texto como texto con codificación en el receptor; si se requiere sanitizar HTML en colecciones, extender mínimamente el filtro existente para sus formas reales y preservar strings transformados. Respetar reglas/contratos de contenido; no agregar un sanitizador paralelo por suposición. Validar listas de strings/DTOs, arrays y diccionarios efectivamente usados, anidados, propiedades omitidas y representación posterior, incluyendo etiquetas permitidas y contenido activo.

### H2 — Tests de registro no acreditan el filtro global

Condición: los tests E8 verifican colección DI no vacía, sin comprobar el descriptor del filtro. Esto permite que una pérdida de registro no sea detectada por esos asserts. Responsable candidato: API. Propuesta futura: comprobar MvcOptions.Filters y un request real que atraviese binding/filtro/action con inputs sintéticos. No es evidencia de que el registro actual falte: E4 lo muestra en código.
