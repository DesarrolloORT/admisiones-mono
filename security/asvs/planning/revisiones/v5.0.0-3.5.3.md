# v5.0.0-3.5.3

## Identificación

- ID: v5.0.0-3.5.3. Nivel mínimo: L1.
- Texto oficial: "Verify that HTTP requests to sensitive functionality use appropriate HTTP methods such as POST, PUT, PATCH, or DELETE, and not methods defined by the HTTP specification as \"safe\" such as HEAD, OPTIONS, or GET. Alternatively, strict validation of the Sec-Fetch-* request header fields can be used to ensure that the request did not originate from an inappropriate cross-origin call, a navigation request, or a resource load (such as an image source) where this is not expected."
- Interpretación local: las fichas v5.0.0-3.5.1/3.5.2 establecieron que la defensa CSRF declarada del sistema es la dependencia del preflight CORS (método no-simple + `Content-Type` no-safelisted), y dejaron pendiente explícito (E8 en ambas) revisar el **cuerpo completo** de las acciones `[HttpGet]` para descartar que alguna funcionalidad sensible/mutante esté expuesta bajo un método "seguro" (GET), que nunca dispara preflight y sería alcanzable sin las protecciones de 3.5.1/3.5.2. Ese pendiente es exactamente el objeto de 3.5.3, evaluado aquí por primera vez de forma dedicada.
- Pregunta concreta: ¿alguna acción HTTP de `api-admisiones` marcada con un método "seguro" (`GET`/`HEAD`/`OPTIONS`) ejecuta, en su implementación real (no sólo en su firma o nombre), un efecto mutante/sensible equivalente al de una acción de escritura? Alternativamente, ¿existe validación de `Sec-Fetch-*` en algún punto del pipeline?
- Avance documental: DOCUMENTADO.
- Resultado de seguridad: NEEDS_REVIEW.
- Fecha de revisión: 2026-09-17.

## Aplicabilidad y alcance

- Componente incluido: `api-admisiones` — único componente que declara rutas/métodos HTTP de negocio (confirmado en 3.5.1/3.5.2: sin Minimal APIs de negocio, Core no expone HTTP).
- Componente excluido con justificación: `admisiones` (SPA) no decide qué método HTTP acepta el servidor para una funcionalidad; sólo consume las rutas ya definidas por la API. Este requisito es una propiedad del servidor, no del cliente.
- Componente excluido con justificación: `Core` no expone controladores HTTP propios (ya confirmado, no reinspeccionado esta iteración).
- No inspeccionado: comportamiento real de Kestrel/IIS ante `HEAD`/`OPTIONS` implícitos sobre rutas `GET` (ASP.NET Core no mapea `HEAD` automáticamente a menos que middleware lo habilite; no se encontró tal middleware, pero no se ejecutó una prueba real), configuración de proxy/hosting no versionada, y la API interna de pagos (`EnrollmentsAndPaymentsApiClient`), externa al alcance de este monorepo salvo su llamada GET saliente (ver E3).
- Alcance de esta ficha: inventariar **todas** las acciones `[HttpGet]` de `api-admisiones` (cerrando el pendiente E8 heredado de 3.5.1/3.5.2) y leer el cuerpo completo de cada una —siguiendo la cadena hasta el caso de uso/servicio inyectado— para confirmar si alguna ejecuta una escritura (persistencia, caché, integración externa mutante) en lugar de una lectura pura.

## Resultado por componente y conclusión

- **API (`api-admisiones`)**: cierra el pendiente heredado de las fichas 3.5.1/3.5.2 (E8): de las 15 acciones `[HttpGet]` existentes (inventario corregido respecto del recuento previo de 14), las 15 fueron trazadas hasta su implementación real y las 15 son lecturas puras sin persistencia, sin escritura de caché de negocio y sin integración externa mutante. Las 24 acciones mutantes inventariadas en 3.5.2 (E1) ya estaban confirmadas usando exclusivamente `POST`/`PUT`. No se localizó ningún método "seguro" (`GET`/`HEAD`/`OPTIONS`) ejecutando una funcionalidad sensible/mutante, que es la condición central que 3.5.3 exige evitar. No se implementa la vía alternativa de validación de `Sec-Fetch-*` (E4), pero el requisito la ofrece como alternativa, no como obligación adicional cuando la primera condición (elección de método) ya se sostiene.
- **Core**: no aplica (sin controladores HTTP propios).
- **Frontend**: fuera de alcance de este punto (no decide el método del servidor).
- **Conclusión de esta ficha**: NEEDS_REVIEW, no PASS. La evidencia es un inventario completo (no muestreado) de la superficie HTTP propia del repo, con lectura de cada cuerpo de implementación, lo que da alta confianza dentro de ese alcance. Pero, según ADR-002, una revisión estática de IA sin evidencia determinística reproducible (prueba de tráfico real, ejecución de tests) no puede cerrar en PASS; además persisten límites de alcance explícitos (API de pagos externa no inspeccionada, comportamiento real de `HEAD` en el servidor no verificado en runtime, configuración de hosting/proxy no versionada).

## Hallazgos y propuesta documental

- Sin hallazgo de defecto en esta ficha: no se encontró ninguna funcionalidad sensible expuesta bajo un método HTTP "seguro". No se abre propuesta de remediación porque no hay código defectuoso identificado.
- Observación de corrección documental (no defecto de producto): la ficha v5.0.0-3.5.1 (E8) contó 14 acciones `[HttpGet]`; el recuento exhaustivo de esta iteración es 15 (la acción que faltaba en el conteo anterior no se identificó de forma aislada — la discrepancia es de conteo, no de omisión de un endpoint distinto, dado que la lista de rutas de esta ficha coincide con los cuatro controladores ya citados en 3.5.1/3.5.2). Se registra para que una lectura futura de 3.5.1/3.5.2 use el número corregido.
- Observación de deuda (no defecto): el sistema no implementa la vía alternativa de validación de `Sec-Fetch-*` (E4). No es necesaria mientras la separación de métodos se sostenga, pero es una capa de defensa en profundidad ausente, consistente con el hallazgo de deuda ya registrado en 3.5.1 (dependencia de una única capa CORS+credentials) y con el hallazgo 1 de 3.5.2 (falta de header no-safelisted independiente en `logout`/`refresh-token`).
