# v5.0.0-3.5.3

## Identificación

- ID: v5.0.0-3.5.3. Nivel mínimo: L1.
- Texto oficial: "Verify that HTTP requests to sensitive functionality use appropriate HTTP methods such as POST, PUT, PATCH, or DELETE, and not methods defined by the HTTP specification as \"safe\" such as HEAD, OPTIONS, or GET. Alternatively, strict validation of the Sec-Fetch-* request header fields can be used to ensure that the request did not originate from an inappropriate cross-origin call, a navigation request, or a resource load (such as an image source) where this is not expected."
- Interpretación local: ninguna funcionalidad sensible o mutante debe estar expuesta bajo un método «seguro» (`GET`/`HEAD`/`OPTIONS`). Hay un motivo adicional: el nuevo `UseOriginCheck` (ver 3.5.1/3.5.2) deja pasar los métodos seguros sin validar el origen. Por eso esta separación de métodos es la que sostiene que un `GET` cross-site no tenga efecto.
- Pregunta concreta: ¿alguna acción de `api-admisiones` marcada con un método seguro ejecuta, en su implementación real, un efecto mutante o sensible equivalente al de una escritura? Como alternativa, ¿existe validación estricta de `Sec-Fetch-*`?
- Avance documental: DOCUMENTADO.
- Resultado de seguridad: NEEDS_REVIEW.
- Fecha de revisión: 2026-09-17; actualización: 2026-10-23.

## Resultado por componente y conclusión

- **API (`api-admisiones`)**: las 25 acciones `GET` y los 2 `MapGet`/`MapMetrics` se trazaron hasta su implementación. Ninguna persiste datos de negocio ni dispara una integración externa mutante (E2-E4). Las únicas escrituras adyacentes son de infraestructura (caché y contadores, E4-E5). Las acciones mutantes, incluidas las nuevas de becas, usan `POST`/`PUT`/`DELETE` (E6). No se implementa la validación de `Sec-Fetch-*` para `GET` (E7), pero el requisito la ofrece como alternativa.
- **Core / Frontend**: no aplican.
- **Conclusión**: NEEDS_REVIEW, no PASS. El inventario es completo y cada cuerpo se leyó, pero es una revisión estática sin evidencia reproducible (ADR-002). Quedan límites explícitos: `HEAD`/`OPTIONS` en runtime y los sistemas externos.

## Hallazgos y propuesta documental

- Sin hallazgo de defecto: no se encontró funcionalidad sensible bajo un método seguro.
- **Observación de corrección documental (anterior): resuelta.** El recuento de 3.5.1 (14) frente a 15 en esta ficha ya no aplica. El inventario vigente es 25 y 3.5.1 se actualizó para remitir aquí.
- **Observación de deuda (vigente, matizada):** no hay validación de `Sec-Fetch-*` para métodos seguros (E7). Ahora hay una capa independiente para métodos no seguros (`UseOriginCheck`), así que la deuda de «una única capa» señalada antes en 3.5.1/3.5.2 quedó resuelta para las mutaciones. Para los `GET`, la protección sigue dependiendo de que no tengan efectos.
- **Observación nueva (no defecto, no CSRF): `GET /scholarships/study-material` dispara trabajo saliente costoso.** Cuando no hay caché, descarga archivos de un origen externo («College Board tarda 30-60 s», comentario en `StudyMaterialService.cs:36-37`). Un `GET` cross-site o un `<img src>` desde otro sitio con la cookie de la víctima (si `SameSite` lo permite) puede forzar esa descarga, aunque la caché de 1 h y la tarea compartida lo acotan. No cambia estado de negocio. Corresponde a consumo de recursos (V2.4/V13), no a este requisito.
