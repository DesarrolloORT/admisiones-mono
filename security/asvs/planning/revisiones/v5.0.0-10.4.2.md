# v5.0.0-10.4.2 — Uso único del authorization code

## Identificación

- **ID y nivel mínimo:** v5.0.0-10.4.2 (L1).
- **Texto oficial:** "Verify that, if the authorization server returns the authorization code in the authorization response, it can be used only once for a token request. For the second valid request with an authorization code that has already been used to issue an access token, the authorization server must reject a token request and revoke any issued tokens related to the authorization code."
- **Interpretación local:** si un componente evaluado opera un authorization server OAuth que entrega authorization codes, debe consumir cada código de forma única al emitir tokens y, ante un segundo canje válido, rechazarlo y revocar los tokens asociados.

- **Avance documental:** DOCUMENTADO.
- **Resultado de seguridad:** NOT_APPLICABLE para los componentes del monorepo inspeccionados.

## Aplicabilidad y alcance

El requisito es condicional: exige el canje único sólo cuando existe un authorization server OAuth que retorna authorization codes. La API expone autenticación propia por LDAP, 2FA, cookies HttpOnly, refresh token y JWT; el frontend consume esas rutas con credenciales de cookie. No se encontró endpoint de autorización ni token endpoint OAuth, registro de clientes, `response_type=code`, `client_id`, `redirect_uri`, `grant_type=authorization_code` ni dependencias de servidor OAuth/OIDC en API, frontend o el Core fijado.

Los códigos de segundo factor y de activación/recupero de contraseña no son authorization codes OAuth: autentican o habilitan flujos propietarios y no se canjean ante un token endpoint por un cliente OAuth. La única coincidencia OAuth es documentación de un JWT saliente para una API externa, descrito como client-credentials “simplificado”; el servicio sólo genera el JWT de servicio y no procesa respuestas de autorización ni códigos.

No se evaluaron la API externa de Inscripciones y Pagos, infraestructura de gateway, LDAP ni proveedores de identidad fuera del monorepo. Si alguno opera un authorization server para la aplicación, este resultado no lo cubre.

## Resultado por componente y conclusión

- **API:** NOT_APPLICABLE. Actúa como autenticador y emisor/validador de JWT propios, no como authorization server OAuth que entregue y canjee authorization codes.
- **Frontend:** NOT_APPLICABLE. Consume la API propia y no maneja callback ni canje de un authorization code OAuth.
- **Core:** NOT_APPLICABLE dentro del alcance del inventario; no se localizó un componente OAuth/OIDC en la versión fijada.
- **Integración externa:** fuera del alcance de evidencia disponible. No se transfiere el resultado a Inscripciones y Pagos ni a un IdP no incluido en el monorepo.

La conclusión DOCUMENTADO / NOT_APPLICABLE se limita al monorepo: no hay un authorization server OAuth bajo inspección que genere authorization codes, por lo que no existe un segundo canje local que evaluar ni tokens asociados que revocar. No se ejecutaron tests, builds, runtime, escaneos ni cambios de código/configuración.

## Hallazgos y propuesta documental

No se identificó un hallazgo aplicable en estos componentes. La mención documental de “OAuth 2.0 Client Credentials Flow (simplificado)” para un JWT de servicio puede inducir a atribuirle controles de authorization server que no implementa. Responsable candidato: `api-admisiones`. Propuesta documental futura: describirlo como autenticación JWT de servicio propietaria, o documentar su perfil OAuth completo si existe en la API externa; validar contra el contrato y despliegue de esa API. No se aplicó ningún cambio.
