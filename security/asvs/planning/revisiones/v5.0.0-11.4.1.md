# v5.0.0-11.4.1 — Funciones hash aprobadas

## Identificación

- **ID y nivel mínimo:** v5.0.0-11.4.1, L1.
- **Texto oficial:** “Verify that only approved hash functions are used for general cryptographic use cases, including digital signatures, HMAC, KDF, and random bit generation. Disallowed hash functions, such as MD5, must not be used for any cryptographic purpose.”
- **Interpretación local:** comprobar los algoritmos de hash/HMAC usados efectivamente por Core, API y frontend en usos criptográficos; una función SHA-256 sola no acredita, por sí misma, que su protocolo de firma, KDF o autenticación sea correcto.
- **Pregunta:** ¿los usos criptográficos de funciones hash localizados emplean algoritmos aprobados y no hay MD5/SHA-1 para esos fines?
- **Avance documental / resultado:** DOCUMENTADO / NEEDS_REVIEW.
- **Fecha de revisión:** 2026-09-23.

## Aplicabilidad y alcance

Aplica a Core y API: ambos implementan SHA-256 y la API firma/valida JWT con HMAC-SHA-256. Aplica al frontend para descartar hashing Web Crypto; el único uso de `crypto` localizado genera identificadores/aleatoriedad, no digests.

El alcance cubre archivos fuente `cs`, `ts`, `js`, `json` y configuración bajo los tres componentes, excluyendo `bin`, `obj` y código Devart generado. No cubre dependencias transitivas, configuraciones desplegadas, binarios, servicios externos ni el validador de Inscripciones/Pagos que recibe el JWT de servicio.

## Resultado por componente y conclusión

- **Core — NEEDS_REVIEW:** los usos localizados son SHA-256. `Util.VerificarFirma` no demuestra una construcción MAC o firma con clave y `GetSHA2` puede tener consumidores externos no presentes en el árbol.
- **API — NEEDS_REVIEW:** los usos localizados de hash y HMAC son SHA-256/HMAC-SHA-256 y no se localizaron MD5/SHA-1 dentro del alcance. La evidencia es estática, sobre archivos con cambios ajenos, y no alcanza para validar despliegue, dependencias ni el receptor del token de servicio.
- **Frontend — NEEDS_REVIEW:** no se localizaron funciones de hash ni `subtle.digest`; sólo aleatoriedad Web Crypto. El worktree tiene cambios ajenos y no se evaluó el artefacto construido ni dependencias.

La conclusión global es **NEEDS_REVIEW**, conforme ADR-002: la revisión estática no aporta evidencia determinística suficiente para PASS, aunque el inventario localizado no contiene una función hash prohibida.

## Hallazgos y propuesta documental

No se confirma una función hash prohibida dentro del alcance inspeccionado. Se registra una observación para fase posterior: `Util.Firmar`/`VerificarFirma` presentan un SHA-256 simple como “firma”; el responsable candidato es Core. Debe inventariarse su consumidor y, si protege autenticidad contra un actor no confiable, sustituir el protocolo por un MAC o firma aprobados y validar manipulación. No se aplicó ningún cambio.

## Pendientes y dependencias

1. El equipo de plataforma debe aportar configuración efectiva y un inventario SBOM/dependencias para descartar algoritmos prohibidos fuera de fuentes propias.
2. El responsable de Inscripciones/Pagos debe aportar el validador y política criptográfica del JWT de servicio emitido por `TokenServiceInternalApi`; ese sistema no está en este monorepo.
3. El responsable de Core debe identificar consumidores internos/externos de `GetSHA2` y `Util.Firmar`/`VerificarFirma`, y confirmar si el último protege autenticidad. Si corresponde, validar su protocolo en una iteración de remediación.
4. Las pruebas existentes de hashing y 2FA no se ejecutaron por el límite de esta fase. Una fase posterior debe ejecutar casos de firma/validación, hashes de tokens y configuraciones desplegadas sin regenerar Devart.
5. La suficiencia de SHA-256 para códigos 2FA de seis dígitos y su almacenamiento pertenece a `v5.0.0-11.4.2` y requisitos MFA relacionados; no se decide en este punto.
