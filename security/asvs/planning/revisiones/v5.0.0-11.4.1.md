# v5.0.0-11.4.1 — Funciones hash aprobadas

## Identificación

- **ID y nivel mínimo:** v5.0.0-11.4.1, L1.
- **Texto oficial:** “Verify that only approved hash functions are used for general cryptographic use cases, including digital signatures, HMAC, KDF, and random bit generation. Disallowed hash functions, such as MD5, must not be used for any cryptographic purpose.”
- **Interpretación local:** comprobar los algoritmos de hash/HMAC usados efectivamente por Core, API y frontend en usos criptográficos; una función SHA-256 sola no acredita que su protocolo de firma, KDF o autenticación sea correcto.
- **Pregunta:** ¿los usos criptográficos de funciones hash localizados emplean algoritmos aprobados y no hay MD5/SHA-1 para esos fines?
- **Avance documental / resultado:** DOCUMENTADO / NEEDS_REVIEW.
- **Fecha de revisión:** 2026-09-23; actualización: 2026-10-23.

## Resultado por componente y conclusión

- **API — NEEDS_REVIEW:** todos los usos localizados de hash, HMAC y aleatoriedad emplean SHA-256, HMAC-SHA-256 y el CSPRNG del sistema; no hay MD5/SHA-1. Queda la observación de la derivación de clave AES por SHA-256 simple (E7) y la falta de evidencia ejecutada y de despliegue.
- **Core — NEEDS_REVIEW (residual):** `GetSHA2` y `Util.Firmar`/`VerificarFirma` siguen igual, ya sin consumidores en la API.
- **Frontend — NEEDS_REVIEW** según la evidencia de `86979de2`, no re-verificada.

Conclusión global **NEEDS_REVIEW**, conforme ADR-002: el inventario no contiene funciones prohibidas, pero la revisión estática no aporta evidencia determinística suficiente para PASS.

## Hallazgos y propuesta documental

No se confirma una función hash prohibida dentro del alcance.

- **Observación O1 (vigente, residual):** `Util.Firmar`/`VerificarFirma` en Core presentan un SHA-256 sin clave como «firma». Ya no hay consumidor en la API; responsable candidato: Core. Propuesta: confirmar si otro consumidor lo usa para autenticidad; si es así, reemplazar por HMAC o firma aprobada; si no, retirarlo.
- **Observación O2 (nueva):** la clave AES-256-GCM de la caché de imágenes se deriva como `SHA256(secreto)` (E7). SHA-256 es aprobado, pero no hay KDF estándar, sal ni etiqueta de contexto; la seguridad depende de que `DocumentImages:EncryptionKey` sea aleatorio de alta entropía (sólo se exige ≥ 32 bytes UTF-8). Responsable candidato: API/Identity. Propuesta: exigir un secreto aleatorio de 32 bytes en Base64 o usar HKDF-SHA-256 con etiqueta de contexto, y documentar rotación. No se aplicó ningún cambio.

## Pendientes y dependencias

1. Plataforma: configuración efectiva y SBOM/dependencias (incluidos paquetes `ORT.*`) para descartar algoritmos prohibidos fuera de las fuentes propias.
2. Inscripciones/Pagos y backoffice: política criptográfica de quien valida el JWT de servicio y de quien firma enlaces con `PasswordActivation:SecretKey`.
3. Core: consumidores de `GetSHA2` y `Util.Firmar`/`VerificarFirma` fuera de la API.
4. Infraestructura: confirmar, sin revelar valores, que `DocumentImages:EncryptionKey` es aleatorio de alta entropía (O2).
5. Ejecutar en fase autorizada `TokenHashingTests`, `TwoFactorAuthServiceTests` y `RedisIdentityDocumentImageCacheTests`, sin regenerar Devart.
6. La suficiencia de SHA-256 para códigos 2FA pertenece a v5.0.0-11.4.2 y MFA.
7. Frontend: re-verificar al actualizar el checkout de `admisiones`.
