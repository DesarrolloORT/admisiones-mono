## Aplicabilidad y alcance

El flujo principal usa access JWT autocontenidos enviados por cookie HttpOnly o por `Authorization: Bearer` y refresh tokens de referencia cuyo hash se guarda en Oracle. Logout se inicia en el frontend, llama a la API y termina con limpieza local y de cookies. La frontera decisiva es la aceptación posterior de una copia de cualquiera de esos tokens por la API. Se incluyeron emisión, validación, renovación, persistencia y tests existentes. Core no aparece en esos pasos. No se inventariaron consumidores externos de bearer, gateways, topología ni configuraciones efectivas. Las sesiones temporales de 2FA/activación requieren comprobación separada de sus disparadores de terminación; no se les atribuye el hallazgo principal.

La ficha [7.2.4](./v5.0.0-7.2.4.md) ya documentó que un access JWT anterior sigue verificándose tras una nueva autenticación; aquí se evalúa el disparador específico de logout y expiración.

## Resultado por componente y conclusión

- **API: FAIL.** El logout no invalida el hash de refresh en Oracle y el validador del access JWT no consulta estado de terminación. Borrar cookies no basta para impedir el uso posterior de una copia de ambos tokens. La configuración sí valida la expiración del access JWT, con 30 segundos de tolerancia, y la consulta de refresh compara `ExpiresAt`; el rechazo efectivo en despliegue no fue probado.
- **Frontend:** invoca logout y limpia el estado local incluso ante error. No tiene autoridad para revocar tokens en el servidor.
- **Core:** no se identificó participación directa en la ruta examinada.

El resultado global es **DOCUMENTADO / FAIL** por una contradicción directa entre la terminación exigida y las rutas de logout/validación/renovación del código evaluado. No se afirma explotación observada ni se extrapola a controles externos no inventariados.

## Hallazgos y propuesta documental

1. **Refresh reutilizable tras logout.** Condición: `Logout` sólo elimina cookies; la fila activa de refresh queda en Oracle. Impacto: quien conserve el valor antes de logout podría canjearlo por nuevas credenciales. Evidencia E1, E2 y E4. Responsable candidato: API. Propuesta futura: identificar de forma segura el refresh presentado y revocarlo en backend al cerrar sesión, con semántica definida para múltiples clientes y fallas de Oracle. Validar con dos clientes: tras logout, reutilizar el refresh antiguo debe devolver 401 y no emitir cookies nuevas.
2. **Access JWT reutilizable tras logout.** Condición: no hay lista de terminados, fecha mínima por persona, versión de sesión ni consulta equivalente en `OnTokenValidated`. Impacto: un token conservado puede acceder hasta vencer aun después de logout. Evidencia E1–E3, E5. Responsable candidato: API. Propuesta futura: acordar el modelo de sesión y comprobar su revocación en cada validación JWT; considerar el costo y la disponibilidad del almacenamiento. Validar el rechazo 401 con bearer y con cookie conservados inmediatamente después de logout y durante el resto de su vigencia.

Las propuestas se conservan aquí. No se distribuyeron a otro worktree: no se verificó uno vigente en los clones originales y no se crean checkouts en esta fase.
