# v5.0.0-7.4.1 — terminación efectiva de sesiones

## Identificación

- ID: v5.0.0-7.4.1; nivel mínimo L1; sección V7.4, Session Termination.
- Texto oficial íntegro: “Verify that when session termination is triggered (such as logout or expiration), the application disallows any further use of the session. For reference tokens or stateful sessions, this means invalidating the session data at the application backend. Applications using self-contained tokens will need a solution such as maintaining a list of terminated tokens, disallowing tokens produced before a per-user date and time or rotating a per-user signing key.”

## Aplicabilidad y alcance

El flujo usa access JWT autocontenidos (cookie HttpOnly o `Authorization: Bearer`) y refresh tokens de referencia con hash en Oracle. El logout lo inicia el front y lo ejecuta la API. Se incluyeron emisión, validación, revocación, renovación, logout, sesiones temporales de contraseña y tests. Core no participa. No se inventariaron consumidores externos de bearer ni la disponibilidad efectiva de Redis por ambiente.

Relacionados: [7.2.4](./v5.0.0-7.2.4.md) (sesión nueva al reautenticar) y [7.4.2](./v5.0.0-7.4.2.md).

## Resultado por componente y conclusión

- **API: NEEDS_REVIEW (antes FAIL).** Ahora existe el mecanismo que pide el requisito para tokens autocontenidos: lista de `jti` terminados y corte por persona, consultados en cada validación. El refresh se invalida en Oracle. Los tests de punta a punta con el pipeline real pasan. No llega a PASS por dos motivos:
  - el control falla abierto: con Redis caído, un access conservado sigue sirviendo hasta su `exp` (15 min + 30 s). Es un riesgo aceptado en [ADR-033](../../../../kb/00-adr/ADR-033-redis-fail-open.md), pero **no hay una excepción formal** en `asvs/exceptions/`, así que no puede figurar como ACCEPTED_RISK;
  - no hay evidencia contra un Redis y un Oracle reales en un ambiente desplegado.
- **Frontend:** llama al logout y limpia el estado local.
- **Core:** sin participación.

## Hallazgos y propuesta documental

1. **Refresh reutilizable tras logout:** resuelto (`833d8f73`). Riesgo residual: la revocación en Oracle es best-effort.
2. **Access JWT reutilizable tras logout:** **resuelto** por SEG-L4-01 (`jti` revocado en logout, E2–E5) y PT-L1 (access anterior revocado al rotar, E6). Lo verifica E7, ejecutado.
3. **Fail-open con Redis caído (nuevo, riesgo aceptado sin excepción).** Condición: `IsRevokedAsync` devuelve `false` ante cualquier error de Redis. Impacto: mientras Redis esté caído, logout no corta el access. Propuesta: formalizar la excepción (aprobador, vencimiento, ticket) o cambiar a fail-closed para la revocación. Validación: test existente `IsRevoked_RedisCaido_AceptaElToken` fija el comportamiento actual.
