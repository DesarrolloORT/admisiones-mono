## Aplicabilidad y alcance

Aplicable: se reciben identidad, nombres, email, teléfono, credenciales, identificadores de catálogos, encuestas, declaración jurada de becas e imágenes/PDF por `multipart/form-data`. Cliente documenta UX; API es responsable de los contratos y validación confiable. Desde el desacople de `Core/Utilities` (`12248719`, `d12599c4`), los formatos compartidos (teléfono, archivos, cédula, contraseña) viven en la API (`AppLogic.Contracts`, `AppLogic.Identity`) o en el paquete `ORT.Utilities.Phone`, no en Core. La revisión se concentra en documentación de estructuras (2.1.1), sin evaluar cumplimiento de validación efectiva (2.2) ni consistencia combinada/límites de negocio (2.1.2/2.1.3, L2 reservado).

Se re-verificaron los contratos locales (`telefono`, `registro` y el nuevo `becas`), DTO de registro, reglas de identidad y teléfono, y tests de contrato. No se hizo inventario exhaustivo campo por campo ni se inspeccionó cada documento histórico, esquema registrado, DTO, controller, dependencia privada o consumidor Core. Pagos se delega a una integración interna: no se excluyen formatos de tarjetas por simple ausencia de un campo observado. Contrato del proveedor, documentación del paquete `ORT.Utilities.Phone` y cobertura de entradas externas quedan pendientes.

## Hallazgos y propuesta documental

1. **Trazabilidad desactualizada de registro.** Sigue abierto. Condición: el frontend referencia `DtoRegistroRequests`, `DocumentUtils.ValidarDocumentoBase`, `RegistroValidationHelper` (E2, no re-verificado); los comentarios del DTO enumeran «CI, PS o DE» y el contrato `CI/DE/PS/CC` (E4/E5); y ahora el README de Registration remite a `Core/AzureService` para el reconocimiento (E12). Impacto candidato: un integrador puede inferir un conjunto de entradas o un componente responsable distinto del vigente. Responsables candidatos: frontend knowledge hub y API Identity/Registration. Propuesta futura: actualizar enlaces a refs fijadas, acordar allowlist pública única con ejemplos y formato CI explícito (`NNNNNNN-D`), y corregir el README. Validación: comparación de documentación, DTO, regla y OpenAPI sobre el mismo commit. No es fix implementado.
2. **Cobertura de formatos pendiente.** Sigue abierto, con avance parcial. Condición: DE/PS/CC siguen sin validación por formato (E4/E6); el email se refiere por nombre de validador; la regla del teléfono depende de un paquete cuya documentación no está en el repo (E7); falta inventario exhaustivo (E10). Avance: el contrato de becas documenta la declaración jurada y sus adjuntos (E11) y los ejemplos de teléfono se volvieron ejecutables (E8). API/dominio deben aprobar estructura y restricciones o explicar deliberadamente la ausencia de restricciones adicionales; no inventar reglas de pasaportes. Propuesta: matriz reutilizando docs canónicas, con campo/flujo, required/null, tipo, largo, caracteres, normalización previa, método/versionado, ejemplos y evidencia.
3. **Obligatoriedad condicional ISO2.** Sigue abierto, sin cambios: E3 declara `requiredOnSave=true` y la excepción con `+`. Propuesta documental: expresar la condición directamente y validarla contra ejemplos y DTO. No se infiere error runtime.
