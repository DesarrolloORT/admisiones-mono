## Aplicabilidad y alcance

Aplicable: se reciben identidad, nombres, email, teléfono, credenciales, identificadores de catálogos, encuestas e imágenes. Cliente documenta UX; API es responsable de los contratos y validación confiable; Core aporta formatos y parsers compartidos. La revisión se concentra en documentación de estructuras (2.1.1), sin evaluar cumplimiento de validación efectiva (2.2) ni consistencia combinada/límites de negocio (2.1.2/2.1.3, L2 reservado).

Se inventariaron cuatro flujos canónicos frontend, documentación API y cinco contratos locales (`telefono`, `registro`, `encuesta-inicial`, `inscripcion-detalle`, `carreras`). Se leyeron muestras acotadas de reglas de identidad/teléfono y DTO de registro. No se hizo inventario exhaustivo campo por campo ni se inspeccionó cada documento histórico, esquema registrado, DTO, controller, dependencia privada o consumidor Core. Pagos se delega a una integración interna: no se excluyen formatos de tarjetas por simple ausencia de un campo observado. Contrato del proveedor y cobertura de entradas externas quedan pendientes.

## Resultado por componente y conclusión

- Frontend: NEEDS_REVIEW. Documenta varias estructuras y validaciones UX, pero las referencias históricas del bloque de registro (164–170, enlaces definidos en 321–322 al commit `6161d5deb2e5ef9d4a84930013481196a6fd5e1d`) apuntan a símbolos/rutas anteriores. **Drift detectado** respecto del árbol evaluado: DTO actual `RegistrationRequests.cs` y regla actual `IdentityDocumentRules`. No se atribuye fallo al commit histórico no inspeccionado.
- API: NEEDS_REVIEW. Teléfono tiene especificación concreta y ejemplos; registro documenta allowlist y diferencia CI/otros tipos. Falta matriz completa de estructuras y evidencia de contrato publicado para esta ref; la referencia genérica a “email válido” requiere fijar autoridad y versión del validador o casos aceptados/rechazados.
- Core: NEEDS_REVIEW. Docs XML describen teléfono y código expone validación CI; no hay catálogo completo de formatos compartidos evaluado ni equivalencia reproducible con docs públicas.
- Global: DOCUMENTADO / NEEDS_REVIEW, conforme ADR-002. Hay evidencia positiva de documentación parcial, sin suficiente cobertura ni validación determinística para PASS o FAIL global. No se confirma vulnerabilidad de inyección ni se aplica remediación.

## Hallazgos y propuesta documental

1. **Trazabilidad desactualizada de registro.** Condición: referencias a `DtoRegistroRequests`, `DocumentUtils.ValidarDocumentoBase`, `RegistroValidationHelper` y listas documentadas de tipos divergentes (E2/E4/E5/E6). Impacto candidato: un integrador puede inferir un conjunto de entradas distinto del vigente. Responsables candidatos: frontend knowledge hub y API Identity/Registration. Propuesta futura: actualizar enlaces a refs fijadas y acordar allowlist pública única, con ejemplos y formato CI explícito. Validación: comparación de documentación, DTO, regla y OpenAPI sobre el mismo commit. No es fix implementado.
2. **Cobertura de formatos pendiente.** Condición: formatos DE/PS/CC explícitamente sin validación por formato y email referido por nombre de validador; falta inventario exhaustivo (E2/E4/E10). Impacto candidato: reglas ambiguas para consumidores y ausencia de criterio verificable para entradas no cubiertas. API/dominio deben aprobar estructura y restricciones o explicar deliberadamente la ausencia de restricciones adicionales; no inventar reglas de pasaportes. Propuesta: matriz reutilizando docs canónicas, con campo/flujo, required/null, tipo, largo, caracteres, normalización previa, método/versionado, ejemplos y evidencia. Coordinar Core para reglas compartidas.
3. **Obligatoriedad condicional ISO2.** E3 declara requerido y excepción con `+`. Propuesta documental: expresar condición directamente y validarla contra ejemplos y DTO. No se infiere error runtime.
