## Aplicabilidad y alcance

El requisito aplica a toda función expuesta por el host, no sólo a las acciones de negocio: controllers, endpoints mínimos y superficies operativas. Se evaluó si cada función queda autorizada explícitamente para un consumidor anónimo o autenticado y si existe una regla global que impida publicar accidentalmente una función sin metadata.

Se inventariaron los seis controllers concretos y sus 56 acciones HTTP, la configuración JWT/autorización, filtros MVC, orden del pipeline (incluido el nuevo chequeo de origen), endpoints de contratos, Swagger y Prometheus, y las pruebas de atributos localizadas. El frontend se incluyó sólo para el gating de navegación (no re-verificado). Core es una dependencia interna sin frontera HTTP propia.

No se inspeccionó configuración efectiva de reverse proxy, firewall, service mesh, Prometheus ni plataforma porque no está versionada en el repositorio. Tampoco se ejecutó la API ni pruebas de integración; esos límites no revierten el hecho verificable de que el host no asigna autorización a `/metrics`.

## Resultado por componente y conclusión

- **API/controllers: cobertura positiva parcial.** Las 56 acciones de negocio están clasificadas: 41 requieren un JWT autenticado y 15 permiten anónimo explícitamente; la clasificación de Auth y Registration tiene ahora tests por reflexión. Para el modelo visible de una única clase de persona autenticada, no se observó una acción de negocio accidentalmente pública.
- **API/host: FAIL.** `/metrics` sigue expuesto en todos los ambientes sin permiso explícito. `AddAuthorization()` no define fallback y `MapMetrics()` no exige autorización. Swagger/contratos carecen de una decisión por consumidor, limitados a ambientes no productivos. El chequeo de origen no es un control de permiso.
- **Frontend:** el guard de rutas no es un boundary de autorización.
- **Core:** no expone funciones HTTP propias en el alcance evaluado.

El resultado global es **DOCUMENTADO / FAIL**. Basta la función operativa `/metrics` sin restricción de consumidor para incumplir el requisito. Una ACL externa podría reducir la exposición productiva, pero no fue aportada.

## Hallazgos y propuesta documental

1. **Prometheus sin autorización funcional en la aplicación (vigente en `912fc665`).** Condición: `MapMetrics()` (`MiddlewarePipelineExtensions.cs:149`) se registra siempre y no encadena `RequireAuthorization`; tampoco existe fallback. Impacto: cualquier consumidor con alcance de red puede solicitar métricas, que incluyen etiquetas de cliente (`client_route`, `client_device`, `test_run_id`), sin una concesión explícita. Evidencia E2, E4 y E10. Responsable candidato: API/plataforma. Propuesta futura: definir el consumidor de monitoreo y proteger la superficie mediante policy, `RequireHost`/puerto interno o control de gateway verificable; agregar una prueba que demuestre denegación para anónimo y acceso para el scraper autorizado.
2. **Cobertura funcional dependiente de anotaciones manuales (vigente, mitigada en parte).** Condición: los seis controllers tienen `[Authorize]` de clase y hay tests por reflexión para Auth y Registration, pero no hay fallback deny-by-default ni test de inventario completo que incluya endpoints mínimos. Impacto: un endpoint mínimo nuevo (como `/contracts` o `/metrics`) o un controller nuevo sin `[Authorize]` se publica abierto. Evidencia E1, E2, E7 y E8. Responsable candidato: API. Propuesta futura: configurar `FallbackPolicy` autenticada y exigir excepción pública explícita; verificar automáticamente todas las acciones y endpoints no-controller. Relacionado con 8.3.1.
3. **Superficies de desarrollo sin permiso de consumidor (vigente).** Condición: Swagger y contratos se restringen por ambiente, no por identidad. Impacto: en LocalHost/Development/Testing cualquier consumidor con acceso de red puede enumerar contratos. Evidencia E5. Responsable candidato: API/plataforma. Propuesta futura: documentar si esos ambientes son redes confiables y, si no, aplicar una policy o restricción de gateway comprobable.

No se aplicó ninguna propuesta ni se modificó código, configuración, contratos o tests.

## Pendientes y dependencias

1. Plataforma/operaciones: aportar configuración efectiva de ingress, proxy, firewall o service mesh para `/metrics`, Swagger y contratos, junto con el consumidor autorizado.
2. API/QA: ejecutar en una fase permitida una prueba de integración que confirme 401/403 para un consumidor no autorizado y acceso para el consumidor permitido de métricas.
3. API/QA: crear y ejecutar un control exhaustivo que clasifique cada acción y endpoint mínimo como protegido o público explícito; los tests actuales cubren Auth, Registration y excepciones puntuales.
4. Producto/seguridad: confirmar que toda persona autenticada tiene permiso para las 41 funciones privadas (p. ej. `study-material`, aceptación de beca, declaración jurada) o definir roles/scopes/policies si existen clases de consumidores distintas.
5. Relacionados: 8.1.1 documenta el modelo incompleto; 8.2.2 revisa acceso por objeto; 8.3.1 trata la capa de enforcement.
