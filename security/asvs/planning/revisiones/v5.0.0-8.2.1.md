## Aplicabilidad y alcance

El requisito aplica a toda función expuesta por el host, no sólo a las acciones de negocio: controllers, endpoints mínimos y superficies operativas. Se evaluó si cada función queda autorizada explícitamente para un consumidor anónimo o autenticado y si existe una regla global que impida publicar accidentalmente una función sin metadata.

Se inventariaron los seis controllers concretos y sus 38 acciones HTTP, la configuración JWT/autorización, filtros MVC, orden del pipeline, endpoints de contratos, Swagger y Prometheus, y las pruebas de atributos localizadas. El frontend se incluyó sólo para confirmar el gating de navegación; no se lo trató como control de seguridad del servidor. Core es una dependencia interna sin frontera HTTP propia en este host.

No se inspeccionó configuración efectiva de reverse proxy, firewall, service mesh, Prometheus ni plataforma porque no está versionada en el repositorio. Tampoco se ejecutó la API ni pruebas de integración; esos límites no revierten el hecho verificable de que el host no asigna autorización a `/metrics`.

## Resultado por componente y conclusión

- **API/controllers: cobertura positiva parcial.** Las 38 acciones de negocio actuales están clasificadas: 23 requieren un JWT autenticado y 15 permiten anónimo explícitamente. Para el modelo visible de una única clase de persona autenticada, no se observó una acción de negocio accidentalmente pública.
- **API/host: FAIL.** `/metrics` es una función expuesta en todos los ambientes y queda disponible sin permiso explícito. `AddAuthorization()` no define fallback y `MapMetrics()` no exige autorización. Las superficies Swagger/contratos también carecen de una decisión por consumidor, aunque están limitadas a ambientes no productivos.
- **Frontend:** el guard de rutas no es un boundary de autorización y no compensa una función del host accesible directamente.
- **Core:** no expone funciones HTTP propias en el alcance evaluado; su uso hereda la decisión del API.

El resultado global es **DOCUMENTADO / FAIL**. La clasificación de los endpoints de negocio evita una conclusión más amplia, pero basta la función operativa `/metrics` sin restricción de consumidor para incumplir el requisito. Una ACL externa podría reducir la exposición productiva, pero no fue aportada y no cambia que la aplicación evaluada no impone el permiso.

## Hallazgos y propuesta documental

1. **Prometheus sin autorización funcional en la aplicación.** Condición: `MapMetrics()` se registra siempre y no encadena `RequireAuthorization`; tampoco existe fallback. Impacto: cualquier consumidor con alcance de red puede solicitar métricas y obtener información operativa sin una concesión explícita. Evidencia E2, E4 y E9. Responsable candidato: API/plataforma. Propuesta futura: definir el consumidor de monitoreo y proteger la superficie mediante policy/autenticación del host, listener interno o control de gateway verificable; agregar una prueba que demuestre denegación para anónimo y acceso para el scraper autorizado.
2. **Cobertura funcional dependiente de anotaciones manuales.** Condición: los controllers actuales están clasificados, pero no hay fallback deny-by-default ni test de inventario completo. Impacto: una nueva acción o endpoint mínimo puede publicarse por omisión. Evidencia E1, E2, E6 y E7. Responsable candidato: API. Propuesta futura: decidir una política global segura y exigir excepción pública explícita; verificar automáticamente todas las acciones y endpoints no-controller. La decisión de deny-by-default se relaciona con 8.3.1 y debe tratarse allí sin abrirlo en esta iteración.
3. **Superficies de desarrollo sin permiso de consumidor.** Condición: Swagger y contratos se restringen por ambiente, pero no por identidad. Impacto: en Development/Testing cualquier consumidor con acceso de red puede enumerar contratos. Evidencia E5. Responsable candidato: API/plataforma. Propuesta futura: documentar si esos ambientes son redes confiables y, si no, aplicar una policy o restricción de gateway comprobable.

No se aplicó ninguna propuesta ni se modificó código, configuración, contratos o tests.

## Pendientes y dependencias

1. Plataforma/operaciones: aportar configuración efectiva de ingress, proxy, firewall o service mesh para `/metrics`, Swagger y contratos, junto con el consumidor autorizado.
2. API/QA: ejecutar en una fase permitida una prueba de integración que confirme 401/403 para un consumidor no autorizado y acceso para el consumidor permitido de métricas.
3. API/QA: crear y ejecutar un control exhaustivo que clasifique cada acción y endpoint mínimo como protegido o público explícito; los tests actuales sólo comprueban excepciones puntuales.
4. Producto/seguridad: confirmar que toda persona autenticada tiene permiso para las 23 funciones privadas o definir roles/scopes/policies si existen clases de consumidores distintas.
5. Relacionados: 8.1.1 documenta el modelo incompleto; 8.2.2 revisará acceso por objeto; 8.3.1 tratará deny-by-default. No se abrió otro requisito.
