## Aplicabilidad y alcance

El requisito aplica a todas las funciones HTTP y recursos de la aplicación, incluidos consumidores anónimos, personas autenticadas y eventuales servicios integrados. La documentación puede estar distribuida si en conjunto permite responder quién puede ejecutar cada función y sobre qué instancia de datos, según identidad, pertenencia y estado del recurso.

Se incluyeron el mapa de autoridades y páginas de flujo del knowledge hub (frontend, sin re-verificar), reglas del repositorio API, README del host y READMEs de Authentication, Registration, People, Enrollments, Catalogs y Scholarships, y los ADR nuevos que fijan reglas de acceso (ADR-030). Se contrastaron contra atributos de los seis controllers, uso de identidad derivada del token, políticas registradas y controles de pertenencia localizados. Core se trató como dependencia interna sin frontera HTTP propia. No se inventariaron permisos de la API interna de inscripciones/pagos, LDAP, backoffice, Tivenos, gateways, jobs ni operaciones manuales.

El alcance distingue consumidor anónimo y persona autenticada; no se localizaron roles, claims de permiso ni políticas de autorización funcionales en el código API.

## Resultado por componente y conclusión

- **API: NEEDS_REVIEW.** Mejoró la documentación por módulo: Scholarships documenta reglas de pertenencia y estado de sus endpoints nuevos y ADR-030 fija una regla de dato concreta. Sin embargo, no hay un inventario versionado que conecte las 56 funciones actuales con consumidor, permiso, recurso, atributos de pertenencia/estado y efecto de denegación; el conteo del README del host está desactualizado (39 frente a 56) y la declaración jurada documenta la convención sin enumerar sus rutas.
- **Frontend/docs: NEEDS_REVIEW.** El knowledge hub explica flujos y varias restricciones; no se re-verificó en esta actualización. Los guards y el gating de UI no sustituyen autorización del servidor.
- **Core:** sin frontera HTTP propia evaluada. Contratos y permisos de servicios remotos (inscripciones/pagos, backoffice, LDAP) quedan fuera del inventario disponible.

El resultado global es **DOCUMENTADO / NEEDS_REVIEW**. Existe documentación parcial valiosa y más completa que en la revisión anterior, pero la cobertura no alcanza para verificar de forma reproducible que estén definidas todas las reglas de acceso funcional y por dato.

## Hallazgos y propuesta documental

1. **Inventario de autorización incompleto y distribuido (vigente en `912fc665`).** Condición: OpenAPI clasifica público/privado y los módulos describen reglas puntuales, pero no hay una vista que relacione cada función con consumidor, identidad, recurso, atributos, decisión y respuesta de denegación. El crecimiento de 38 a 56 acciones amplía la brecha. Impacto: cambios de endpoint o reglas por estado/ownership pueden quedar sin especificación revisable y sin pruebas asociadas. Evidencia E1–E8, E10. Responsable candidato: API con coordinación de producto/seguridad. Propuesta futura: mantener una matriz versionada generada o verificada contra OpenAPI/controllers, con columnas mínimas de ruta/operación, consumidor, autenticación/política, fuente de identidad, recurso, condición de pertenencia/estado, allow/deny y test/evidencia.
2. **Drift en inventario y becas — parcialmente resuelto.** La contradicción de la revisión anterior (la página de becas describía `/scholarships/available`, `/application-options` y `/applications`, inexistentes en el controller) quedó resuelta del lado API: esas rutas existen y el README del módulo las documenta (E6). Sigue vigente el conteo del README del host (39 declarados, 56 reales) y queda pendiente re-verificar `becas.md` contra el contrato actual. Evidencia E3, E6 y E8. Responsable candidato: API y frontend/docs. Propuesta futura: automatizar la lista de rutas y su clasificación pública/privada y alinear la página de becas.

Las propuestas se conservan en esta ficha. No se modificaron páginas, código ni contratos.

## Pendientes y dependencias

1. API/seguridad: confirmar que los únicos consumidores funcionales son anónimo y persona autenticada, o aportar roles, claims, gateways, service tokens y operaciones administrativas externas (incluido el backoffice que firma links de alta).
2. API/producto: completar y aprobar una matriz de las 56 acciones actuales; para cada identificador aportado por cliente (inscripción, prueba, declaración jurada, ingreso, `applicationId`), registrar ownership/estado requerido y código de denegación.
3. API: generar OpenAPI en una fase permitida y verificar que las 56 operaciones queden correctamente marcadas públicas/privadas; esta fase no regeneró contratos.
4. Frontend/API: re-verificar `becas.md` y el resto del knowledge hub contra `912fc665` y corregir el conteo del README del host.
5. QA: ampliar evidencia de objeto con pruebas de dos identidades para inscripción, encuesta, pago, documentos personales, postulación/aceptación de beca y declaración jurada.
6. Infraestructura/owners externos: documentar autorización en API de inscripciones/pagos, LDAP, backoffice, Tivenos, jobs y operaciones manuales, o justificar su exclusión por boundary.
