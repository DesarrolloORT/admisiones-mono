## Aplicabilidad y alcance

El requisito aplica a todas las funciones HTTP y recursos de la aplicación, incluidos consumidores anónimos, personas autenticadas y eventuales servicios integrados. La documentación puede estar distribuida si en conjunto permite responder quién puede ejecutar cada función y sobre qué instancia de datos, según identidad, pertenencia y estado del recurso.

Se incluyeron el mapa de autoridades del knowledge hub, páginas de login/registro/inscripciones/becas, reglas del repositorio API, README del host y READMEs de Authentication, Registration, People, Enrollments, Catalogs y Scholarships. Se contrastaron contra atributos de los seis controllers, uso de identidad derivada del token, políticas registradas y controles de pertenencia localizados. Core se trató como dependencia interna sin frontera HTTP propia en este monorepo. No se inventariaron permisos de la API interna de inscripciones/pagos, LDAP, Tivenos, gateways, jobs ni operaciones manuales.

El alcance actual distingue principalmente consumidor anónimo y persona autenticada; no se localizaron roles, claims de permiso o políticas de autorización funcionales adicionales en el código API. Esa ausencia observada no demuestra que no haya controles en servicios externos o infraestructura.

## Resultado por componente y conclusión

- **API: NEEDS_REVIEW.** Hay una convención general y documentación concreta por módulos. El filtro de Swagger puede clasificar funciones públicas/privadas y los controllers derivan la identidad desde el token. Sin embargo, no hay un inventario versionado y consistente que conecte las 38 funciones actuales con consumidor, permisos, recurso, atributos de pertenencia/estado y efecto de denegación. El conteo del README está desactualizado y parte de la documentación de becas contradice el controller actual.
- **Frontend/docs: NEEDS_REVIEW.** El knowledge hub explica flujos y varias restricciones, pero sus páginas actuales están modificadas sin commit y la de becas mezcla funciones pendientes con endpoints presentados como backend vigente. Los guards y el gating de UI no sustituyen autorización del servidor.
- **Core:** sin frontera HTTP propia evaluada; las reglas de autorización de los flujos que lo consumen corresponden a API. Contratos y permisos de servicios remotos quedan fuera del inventario disponible.

El resultado global es **DOCUMENTADO / NEEDS_REVIEW**. Existe documentación parcial valiosa, pero la cobertura y coherencia no alcanzan para verificar de forma reproducible que estén definidas todas las reglas de acceso funcional y por dato. No se marca FAIL definitivo porque las reglas están distribuidas y faltan inventario/autoridad de consumidores externos; tampoco se marca PASS por los gaps y contradicciones directas.

## Hallazgos y propuesta documental

1. **Inventario de autorización incompleto y distribuido.** Condición: OpenAPI clasifica público/privado y los módulos describen reglas puntuales, pero no hay una vista que relacione cada función con consumidor, identidad, recurso, atributos, decisión y respuesta de denegación. Impacto: cambios de endpoint o reglas por estado/ownership pueden quedar sin especificación revisable y sin pruebas asociadas. Evidencia E1–E5, E7–E9. Responsable candidato: API con coordinación de producto/seguridad. Propuesta futura: mantener una matriz versionada generada o verificada contra OpenAPI/controllers, con columnas mínimas de ruta/operación, consumidor, autenticación/política, fuente de identidad, recurso, condición de pertenencia/estado, allow/deny y test/evidencia.
2. **Drift en inventario y becas.** Condición: el host declara 39 endpoints frente a 38 actuales; la página de becas documenta rutas que no existen en `ScholarshipsController` y combina comportamiento vigente con alta pendiente. Impacto: una revisión puede atribuir protección o restricciones a funciones no desplegadas y omitir el único endpoint real. Evidencia E3 y E6. Responsable candidato: frontend/docs y API. Propuesta futura: alinear la página con el contrato/implementación efectiva, separar claramente “vigente” de “propuesto” y automatizar al menos la lista de rutas y su clasificación pública/privada.

Las propuestas se conservan en esta ficha. No se modificaron páginas, código ni contratos; tampoco se distribuyó documentación a otros worktrees porque los componentes están en ramas de desarrollo con cambios ajenos y sin worktree `fix/owasp` listado.

2. API/producto: completar y aprobar una matriz de las 38 acciones actuales; para cada identificador aportado por cliente, registrar ownership/estado requerido y código de denegación.
3. API: generar OpenAPI en una fase permitida y verificar que las 38 operaciones queden correctamente marcadas públicas/privadas; esta fase no regeneró contratos.
4. Frontend/API: resolver el drift de becas y el conteo 39/38 sin mezclar cambios locales en curso; fijar refs comunes para que el portal no apunte a comportamientos incompatibles.
5. QA: ampliar evidencia de objeto con pruebas de dos identidades para inscripción, encuesta, pago, documentos personales y becas; la prueba histórica de un archivo no cubre todos los recursos y no se reejecutó.
6. Infraestructura/owners externos: documentar autorización en API de inscripciones/pagos, LDAP, Tivenos, jobs y operaciones manuales, o justificar su exclusión por boundary.
