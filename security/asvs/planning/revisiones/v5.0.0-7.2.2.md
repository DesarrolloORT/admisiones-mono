## Aplicabilidad y alcance

Se inspeccionaron tokens de acceso y refresh de sesiones autenticadas (login, 2FA, refresh, contraseña inicial y, desde `73794742`, renovación tras `person/change-password`), sesión previa al 2FA y sesiones temporales para establecer contraseña, incluida la del link del backoffice (ADR-030). Fronteras: navegador → API; API → Oracle para hash del refresh y API → Redis para identificador 2FA. El frontend transporta cookies con `withCredentials` y el identificador 2FA; no crea una credencial de sesión autenticada. Los JWT de servicio a servicio se distinguen de las sesiones de usuario y se mencionan para evitar confundir la clave de firma con un token estático de sesión.

Quedan fuera de la conclusión exhaustiva el despliegue, otros consumidores de Core, servicios externos, configuración efectiva (Key Vault) y cualquier mecanismo de sesión fuera de los flujos localizados.

## Resultado por componente y conclusión

- API: los flujos leídos generan JWT autocontenidos o referencias nuevas. Las claves de firma configuradas no aparecen como credencial de sesión. El access token sigue sin variación aleatoria explícita: dos emisiones para la misma persona con marcas de tiempo que se serialicen igual podrían coincidir. Esa posibilidad requiere prueba controlada; no se declara vulnerabilidad confirmada.
- Frontend: consume las credenciales emitidas por la API y mantiene estado de UI; no se re-verificó en esta actualización.
- Core fijado: sin emisión de sesiones identificada en la búsqueda acotada; no se extrapola a todos sus consumidores.

Resultado global: DOCUMENTADO / NEEDS_REVIEW. La evidencia estática respalda el diseño dinámico de los flujos localizados, pero no un PASS de toda la aplicación ni la unicidad efectiva del access token en emisiones próximas.

## Hallazgos y propuesta documental

- **Posible repetición del JWT de acceso (vigente en `912fc665`).** Condición: `GenerateAccessToken` sólo incorpora identidad y expiración calculada, sin `jti` o nonce; si la serialización reduce los tiempos a la misma unidad, dos emisiones próximas para la misma persona podrían devolver el mismo JWT. El camino nuevo de `change-password` → `IssueTokensForPerson` agrega una emisión más que puede ocurrir segundos después del login. Impacto posible: una reemisión podría no distinguir una sesión nueva para revocación o seguimiento. Evidencia: E1, E6 y E8. Responsable candidato: API. Propuesta futura: reproducir dos emisiones para la misma persona dentro de la misma unidad de tiempo; si se confirma repetición, incorporar un identificador generado por emisión y validar login, refresh, `change-password` y reautenticación. Relacionado con 7.2.4; no se aplica fix ahora.

No se distribuyó propuesta Markdown a otros repos: queda central hasta validar el comportamiento y comprobar disponibilidad del worktree `fix/owasp` correspondiente.
