## Aplicabilidad y alcance

Se inspeccionaron tokens de acceso y refresh de sesiones autenticadas, sesión previa al 2FA y sesión temporal para establecer contraseña. Fronteras: navegador → API; API → Oracle para hash del refresh y API → Redis para identificador 2FA. El frontend transporta cookies con `withCredentials` y el identificador 2FA; no crea una credencial de sesión autenticada. Los JWT de servicio a servicio se distinguen de las sesiones de usuario y se mencionan para evitar confundir la clave de firma con un token estático de sesión.

Quedan fuera de la conclusión exhaustiva el despliegue, otros consumidores de Core, servicios externos, configuración efectiva y cualquier mecanismo de sesión fuera de los flujos localizados. La búsqueda de Core fue acotada; no constituye inventario completo.

## Resultado por componente y conclusión

- API: los flujos leídos generan JWT autocontenidos o referencias nuevas. La clave de firma configurada no aparece como credencial de sesión. El access token carece de variación aleatoria explícita: dos emisiones para la misma persona con marcas de tiempo que se serialicen igual podrían coincidir. Esa posibilidad requiere prueba controlada y revisión de la implementación de serialización; no se declara vulnerabilidad confirmada.
- Frontend: consume las credenciales emitidas por la API y mantiene estado de UI; no se encontró un generador propio de sesiones autenticadas en los archivos revisados. Falta inventario de otros clientes.
- Core fijado: sin emisión de sesiones identificada en la búsqueda acotada; no se extrapola a todos sus consumidores.

Resultado global: DOCUMENTADO / NEEDS_REVIEW. La evidencia estática respalda el diseño dinámico de los flujos localizados, pero no un PASS de toda la aplicación ni la unicidad efectiva del access token en emisiones próximas.

## Hallazgos y propuesta documental

- **Posible repetición del JWT de acceso.** Condición: `GenerateAccessToken` solo incorpora identidad y expiración calculada, sin `jti` o nonce; si la serialización reduce los tiempos a la misma unidad, dos emisiones próximas para la misma persona podrían devolver el mismo JWT. Impacto posible: una reemisión podría no distinguir una sesión nueva para revocación o seguimiento. Evidencia: E1 y E8. Responsable candidato: API. Propuesta futura: reproducir dos emisiones para la misma persona dentro de la misma unidad de tiempo y revisar el contrato de generación; si se confirma repetición y la política requiere token nuevo en cada emisión, incorporar un identificador generado por emisión y validar login, refresh y reautenticación. Relacionado con 7.2.4; no se aplica fix ahora.

No se distribuyó propuesta Markdown a otros repos: queda central hasta validar el comportamiento y comprobar disponibilidad del worktree `fix/owasp` correspondiente.
