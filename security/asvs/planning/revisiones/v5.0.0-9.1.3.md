# v5.0.0-9.1.3 — fuente confiable de claves de tokens autocontenidos

## Identificación

- ID: v5.0.0-9.1.3; nivel mínimo L1.
- Texto oficial íntegro: “Verify that key material that is used to validate self-contained tokens is from trusted pre-configured sources for the token issuer, preventing attackers from specifying untrusted sources and keys. For JWTs and other JWS structures, headers such as 'jku', 'x5u', and 'jwk' must be validated against an allowlist of trusted sources.”
- Interpretación local: los validadores JWT deben elegir claves exclusivamente desde fuentes preconfiguradas y no aceptar fuentes o claves indicadas por el token.
- Pregunta: ¿los JWT aceptados por la API resuelven sus claves desde fuentes preconfiguradas, sin consultar `jku`, `x5u`, `jwk` ni otro dato controlado por quien presenta el token?
- Avance: DOCUMENTADO. Resultado: NEEDS_REVIEW. Fecha: 2026-09-22.

Refresh tokens opacos, gateways, proxy, valores efectivos de secretos y permisos sobre su almacén no se evaluaron.

## Resultado por componente y conclusión

- API: la revisión estática muestra que ambos validadores entrantes obtienen claves de variables de entorno nombradas y de mapeos locales preconfigurados; no se observó consumo de fuentes de clave declaradas por headers JWT/JWS. El `issuer` leído antes de validar sólo selecciona una entrada fija y el issuer se valida después por el handler.
- Core: sin participación directa identificada.
- API destino de Inscripciones/Pagos: no evaluada, pues sólo se ve el emisor local.

Resultado global: DOCUMENTADO / NEEDS_REVIEW. El código disponible es favorable, pero no hay evidencia determinística del rechazo de headers que intenten redirigir la fuente de claves ni de que el aprovisionamiento efectivo de variables sea una fuente confiable. Según [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md), esta revisión estática no permite PASS.

## Hallazgos y propuesta documental

No se confirma incumplimiento de código. Gap de evidencia: las pruebas actuales no demuestran el comportamiento del bearer ante `kid`, `jku`, `x5u` o `jwk` suministrados por el cliente, y no existe evidencia disponible del control de acceso al secreto desplegado. Responsable candidato: API/QA e Infraestructura. Propuesta para fase posterior: pruebas de integración que presenten JWT con esos headers y verifiquen 401 sin tráfico de resolución remota; documentar el almacén/identidad que provee las variables y su control de cambios. No se aplicó fix ni se distribuyó propuesta a ramas `fix/owasp`.
