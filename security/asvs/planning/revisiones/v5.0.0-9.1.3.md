# v5.0.0-9.1.3 — fuente confiable de claves de tokens autocontenidos

## Identificación

- ID: v5.0.0-9.1.3; nivel mínimo L1.
- Texto oficial íntegro: “Verify that key material that is used to validate self-contained tokens is from trusted pre-configured sources for the token issuer, preventing attackers from specifying untrusted sources and keys. For JWTs and other JWS structures, headers such as 'jku', 'x5u', and 'jwk' must be validated against an allowlist of trusted sources.”
- Interpretación local: los validadores JWT deben elegir claves exclusivamente desde fuentes preconfiguradas para cada emisor y no aceptar fuentes o claves indicadas por el token.
- Pregunta: ¿los JWT aceptados por la API resuelven sus claves desde fuentes preconfiguradas, sin consultar `jku`, `x5u`, `jwk` ni otro dato controlado por quien presenta el token?
- Avance: DOCUMENTADO. Resultado: NEEDS_REVIEW. Fecha de revisión: 2026-09-22; actualización: 2026-10-23.

## Resultado por componente y conclusión

- API: ambos validadores obtienen claves de entradas fijas de `IConfiguration` (Key Vault o variable de entorno), sin consumo de fuentes declaradas por headers JWT/JWS. El `issuer` leído antes de validar sólo selecciona una entrada fija y se valida después.
- API, contexto de activación: la clave sirve a dos emisores (API y backoffice) con el mismo `iss`. Esto no permite al atacante elegir la clave, pero sí debilita el vínculo «clave por emisor» del requisito: el backoffice, o quien obtenga ese secreto, puede firmar cualquier `purpose` (recupero de una persona existente, sesión temporal), no sólo enlaces `idSolicitudAlta`.
- Core: sin participación.
- API destino de Inscripciones/Pagos: no evaluada.

Resultado global: DOCUMENTADO / NEEDS_REVIEW. El código es favorable respecto de fuentes de clave controladas por el atacante, pero no hay evidencia determinística del rechazo de headers adversarios, ni del aprovisionamiento efectivo en Key Vault, y aparece la observación O1. Según [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md), esta revisión estática no permite PASS.

## Hallazgos y propuesta documental

No se confirma incumplimiento de código respecto de `jku`/`x5u`/`jwk`. Gap de evidencia: las pruebas no demuestran el comportamiento ante `kid`, `jku`, `x5u` o `jwk` suministrados por el cliente, ni existe evidencia del control de acceso a los secretos del vault. Responsable candidato: API/QA e Infraestructura. Propuesta para fase posterior: pruebas de integración con esos headers que verifiquen 401 sin resolución remota; documentar vault, credencial de acceso (sin Managed Identity) y control de cambios.

**Observación O1 (nueva) — clave simétrica compartida con el backoffice.** Condición: `PasswordActivation:SecretKey` valida tanto tokens propios como los del backoffice, con igual `iss`/`aud` (E6). Impacto potencial: no hay separación de clave por emisor; un compromiso o uso indebido en el backoffice permitiría acuñar tokens de cualquier propósito del flujo de contraseña. Responsable candidato: API/Authentication y equipo backoffice. Propuesta: clave e issuer propios para el backoffice (o firma asimétrica con clave pública preconfigurada), validados en un contexto separado que sólo admita el claim `idSolicitudAlta`. Validación futura: un token del backoffice con `purpose` de recupero debe rechazarse. No se aplicó fix ni se distribuyó propuesta a ramas `fix/owasp`.
