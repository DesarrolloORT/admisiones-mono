# v5.0.0-3.2.2 — Renderizado seguro de contenido como texto

## Identificación

- ID: v5.0.0-3.2.2. Nivel mínimo: L1. Fecha de revisión: 2026-09-17; actualización: 2026-10-23.
- Texto oficial (JSON fuente, `V3.2.2`): "Verify that content intended to be displayed as text, rather than rendered as HTML, is handled using safe rendering functions (such as createTextNode or textContent) to prevent unintended execution of content such as HTML or JavaScript."
- Interpretación local: cuando el sistema muestra datos que deberían leerse como texto plano (nombre de persona, mensajes, comentarios, códigos), el mecanismo de salida no debe interpretarlos como marcado HTML/JS ejecutable. Aplica a la SPA (DOM) y a cualquier generación de HTML del lado servidor que termine renderizada como HTML en un cliente (navegador o lector de correo), por ejemplo los cuerpos de correo.
- Pregunta concreta: ¿existe algún punto del frontend o del backend donde texto que debería tratarse como plano se concatene o inyecte en un contexto HTML sin una función de renderizado segura (equivalente a `textContent`/`createTextNode`) o sin codificación HTML previa?
- Avance documental: DOCUMENTADO.
- Resultado de seguridad: NEEDS_REVIEW. La evidencia estática es favorable en la SPA (no re-verificada) y la API ya no genera HTML. Falta runtime y falta revisar los templates del worker de correo, que están fuera de este repo.

## Aplicabilidad y alcance

- **Frontend (Angular, SPA)**: aplica directamente. El framework decide si un dato se renderiza como texto (interpolación `{{ }}`) o como HTML (`[innerHTML]`, `bypassSecurityTrustHtml`). Se conserva la inspección de `admisiones/src` de la revisión original, sin re-verificar.
- **API (.NET)**: aplica en cualquier punto que genere HTML a partir de datos que deberían tratarse como texto. En `912fc665` la API **ya no arma HTML de correo**. Los correos (activación, recupero, código 2FA) se publican como mensajes estructurados en Service Bus (`ORT.Messaging`). Un worker externo los renderiza con templates Razor de TemplatesORT. No hay vistas Razor, `.cshtml` ni motores de templating en la API.
- **Core**: el antiguo generador (`MailORT.EnvioMail`) ya no se compila con la API, así que queda fuera del alcance efectivo.
- **Fuera de alcance**: el worker y los templates de TemplatesORT (otro repositorio), el cliente de correo y el runtime del navegador. 3.2.1 cubre un riesgo distinto (tipo MIME al servir bytes).

## Resultado por componente y conclusión

- **Frontend**: en la ref `86979de2` no había sinks de interpretación HTML, y la interpolación de Angular equivale a `textContent`. No se re-verificó en esta actualización.
- **API**: ya no genera HTML. Los correos salen como datos estructurados (E3-E5). La protección de salida que pide el requisito para correo depende ahora del worker y de los templates Razor externos. Razor codifica por defecto con `@`, pero no se verificó que ningún template use `@Html.Raw` o equivalente sobre `FirstName` o las URLs.
- **Core**: ya no participa (`MailORT` fuera del grafo).
- **Conclusión global**: no se encontró una violación concreta en el código de este monorepo, pero no hay evidencia determinística suficiente para PASS (ADR-002). Se mantiene NEEDS_REVIEW por cuatro motivos: los tests no se ejecutaron, falta runtime, el frontend no se re-verificó contra una ref vigente y los templates del worker no se inspeccionaron.

## Hallazgos y propuesta documental

No hay condición concreta de incumplimiento en el código inspeccionado.

- **Observación anterior (deuda de diseño en `MailORT.EnvioMail`): ya no aplica en 912fc665.** Los helpers `CuerpoConTitulo`, `CuerpoParrafos`, etc. de `Core/MailORT/EnvioMail.cs` no codificaban HTML. La API ya no los usa: no hay `ProjectReference` a `MailORT` y `PasswordMailTemplate` se eliminó. El correo pasó a ORT.Messaging/Service Bus (E3-E6). La observación se conserva como rastro. Si otro consumidor de Core sigue usando `EnvioMail`, sigue vigente para ese consumidor.
- **Observación nueva (dependencia externa, no defecto)**: la codificación HTML del correo depende de los templates Razor del worker (TemplatesORT), fuera de este repo.
  - Impacto potencial: un template que use `@Html.Raw(Model.FirstName)` o similar permitiría inyectar HTML en el correo (phishing, enlaces falsos) con un nombre de persona controlado por el usuario.
  - Evidencia: E3, E4.
  - Responsable candidato: dueño del worker de mensajería / TemplatesORT.
  - Propuesta (documental, no aplicada): verificar en ese repo que los templates `PasswordActivation`, `PasswordReset` y `TwoFactorCode` usan solo `@Model.X` codificado, y documentar ese contrato en ORT.Messaging.Contracts.
  - Validación futura: lectura de los templates y envío de prueba con un nombre que contenga `<b>`/`<script>`.
