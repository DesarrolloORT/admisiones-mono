# v5.0.0-3.2.2 — Renderizado seguro de contenido como texto

## Identificación

- ID: v5.0.0-3.2.2. Nivel mínimo: L1. Fecha: 2026-09-17.
- Texto oficial (JSON fuente, `V3.2.2`): "Verify that content intended to be displayed as text, rather than rendered as HTML, is handled using safe rendering functions (such as createTextNode or textContent) to prevent unintended execution of content such as HTML or JavaScript."
- Interpretación local: cuando el sistema muestra datos que deberían leerse como texto plano (nombre de persona, mensajes, comentarios, códigos), el mecanismo de salida no debe interpretarlos como marcado HTML/JS ejecutable. Esto aplica tanto a la SPA (DOM) como a cualquier generación de HTML del lado servidor (por ejemplo, cuerpos de correo) donde el contenido final se renderiza como HTML en un cliente (navegador o lector de correo).
- Pregunta concreta: ¿existe algún punto del frontend o del backend donde texto que debería tratarse como plano se concatene o inyecte en un contexto HTML sin usar una función de renderizado segura (equivalente a `textContent`/`createTextNode`) o sin codificación HTML previa?
- Avance documental: DOCUMENTADO.
- Resultado de seguridad: NEEDS_REVIEW (evidencia estática favorable en los flujos localizados; sin runtime ni cobertura de otros posibles receptores de correo/plantillas).

## Aplicabilidad y alcance

- **Frontend (Angular 22, SPA)**: aplica directamente. El framework decide por defecto si un dato se renderiza como texto (interpolación `{{ }}`) o como HTML (`[innerHTML]`, `bypassSecurityTrustHtml`). Se inspeccionó todo `admisiones/src` en busca de sinks de interpretación HTML.
- **API/Core (.NET)**: aplica en cualquier punto que genere HTML consumido por un cliente (navegador o lector de correo) a partir de datos que deberían tratarse como texto. Se identificó el único generador de HTML relevante: las plantillas de correo en `MailORT.EnvioMail` y sus consumidores de Autenticación (activación de cuenta, recuperación de contraseña, 2FA). No se hallaron vistas Razor, motores de plantillas HTML adicionales (Handlebars, etc.) ni otro código que arme HTML a partir de datos de usuario.
- **Fuera de alcance de esta ficha**: el requisito 3.2.1 (Content-Type/`nosniff` en servir bytes) ya fue documentado por separado y cubre un riesgo distinto (interpretación de tipo MIME, no de HTML embebido); no se reutiliza como evidencia aquí. Tampoco se evaluó runtime del cliente de correo (Outlook/Office365) ni el pipeline SOAP de envío en sí.
- No se excluyó ninguna tecnología del inventario disponible (SPA Angular, API .NET, Core .NET) sin justificación: se buscó exhaustivamente sobre los tres.

## Resultado por componente y conclusión

- **Frontend**: sin sinks de interpretación HTML localizados; el mecanismo de renderizado por defecto de Angular (interpolación) es funcionalmente equivalente a `textContent`. Evidencia estática favorable, pero no es una prueba en runtime ni cubre dependencias de terceros compiladas en el bundle.
- **API/Core (correo)**: el único flujo real con dato de usuario (nombre de persona y enlace de activación/recupero) usa `HtmlEncoder.Default.Encode` antes de insertarse en HTML. El resto de interpolaciones en plantillas de correo son literales del sistema o un código OTP generado por el servidor. Evidencia estática favorable en los flujos localizados.
- **Conclusión global**: no se encontró una violación concreta del requisito en el código inspeccionado, pero la ausencia de sinks detectados mediante patrones de búsqueda no constituye, según ADR-002, evidencia determinística suficiente para PASS. Se mantiene NEEDS_REVIEW por falta de: (a) ejecución de los tests existentes, (b) verificación en runtime del renderizado real en un cliente de correo y en el navegador, y (c) cobertura de código de terceros/bundle compilado que escapa a una búsqueda por patrones de texto.

Un resultado favorable en un componente no implica cumplimiento del requisito compartido completo; ver pendientes.

## Hallazgos y propuesta documental

No se identificó una condición concreta de incumplimiento (no hay sink sin codificar alimentado por datos de usuario). Se documenta como observación de bajo riesgo, no como hallazgo de defecto:

- **Observación (deuda de diseño, no defecto confirmado)**: los métodos de plantilla de `MailORT.EnvioMail` (`CuerpoConTitulo`, `CuerpoParrafos`, `LineaNegrita`, `LineaNormal`, `PieReferencia`) no codifican HTML internamente; la seguridad depende enteramente de que cada llamador futuro codifique antes de invocarlos. Hoy el único llamador con dato de usuario (`PasswordMailTemplate`) lo hace correctamente, pero un nuevo consumidor podría omitirlo sin que el compilador o un test lo señale.
  - Impacto potencial: si un futuro flujo (por ejemplo, notificaciones de becas o inscripción con texto libre de usuario) reutiliza estos helpers sin codificar, se introduciría HTML injection en el correo (phishing, enlaces falsificados, ruptura de layout).
  - Evidencia: E3, E4.
  - Responsable candidato: equipo API (Core `MailORT` y `AppLogic.Authentication`/consumidores futuros).
  - Propuesta de cambio (documental, no aplicada): considerar que `CuerpoConTitulo`/`CuerpoParrafos`/etc. acepten explícitamente un flag o codifiquen por defecto usando `HtmlEncoder.Default.Encode` salvo que el llamador pase contenido ya marcado como HTML seguro (por ejemplo mediante un tipo dedicado `HtmlSafeString`), de modo que la codificación no dependa de la disciplina de cada llamador nuevo.
  - Validación futura: revisar cada nuevo consumidor de `EnvioMail` en próximas iteraciones y, si se materializa un flujo con texto libre de usuario, verificar codificación antes de dar por cerrado el punto.

No se distribuye propuesta a un worktree separado porque no hay un fix concreto que aplicar sobre código actual defectuoso; la propuesta es preventiva sobre una superficie de reutilización futura.
