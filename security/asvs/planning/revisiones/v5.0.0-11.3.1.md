## Aplicabilidad y alcance

El control aplica a código propio que cifra datos y a las integraciones cuyo algoritmo se configure o se pueda verificar desde este monorepo. API y Core son aplicables: Core contiene una utilidad denominada `Encriptador`, y la API referencia el proyecto `Utilities`. El frontend no implementa criptografía WebCrypto/CryptoJS; transporta un parámetro que la API declara como cifrado para un flujo de pago externo.

No se evaluaron el servicio interno de Inscripciones/Pagos, pasarelas Banred/Sistarbanc/Geopay, almacenamiento de parámetros LDAP, gateway, configuraciones de plataforma ni tráfico real. Esos límites impiden concluir sobre el algoritmo del blob de pagos o sobre datos persistidos previamente fuera del código fuente.

## Resultado por componente y conclusión

- **Core:** NEEDS_REVIEW. No se encontró ECB, PKCS#1 v1.5 ni otro modo/padding de bloque, pero la única utilidad reversible propia no constituye evidencia de cifrado seguro. Debe revisarse como deficiencia de criptografía general y su formato/almacenamiento real antes de declarar este punto conforme.
- **API:** NEEDS_REVIEW. No se hallaron primitivas con los modos/paddings prohibidos en código propio. El flujo de pagos delega el blob criptográfico a un sistema externo no evaluado.
- **Frontend:** NEEDS_REVIEW. No cifra ni descifra localmente; transporta el blob de pago. Esto no cubre el algoritmo que emplea el receptor externo.
- **Integraciones externas:** fuera del alcance disponible. No se les atribuye cumplimiento ni incumplimiento.

La evidencia estática no revela el uso de ECB o PKCS#1 v1.5 en el monorepo, pero no es suficiente para PASS según el modelo de evidencia: falta una confirmación determinística de los algoritmos y configuraciones efectivas de los datos cifrados, sobre todo los producidos por Pagos. No se ejecutaron tests, builds, runtime, escaneos ni cambios de código o configuración.

## Hallazgos y propuesta documental

**Observación O1 — helper reversible propio para secreto LDAP.** `Encriptador` transforma caracteres, Base64 y URL encoding; no aplica cifrado estándar autenticado ni gestión de claves. Su uso para `PasswordLdap` queda evidenciado en `Ldap`. Impacto potencial: quien lea el valor persistido y el código puede revertirlo; esta observación excede el modo/padding concreto pero limita la conclusión criptográfica. Responsable candidato: Core/API.

Propuesta documental futura: inventariar el origen, almacenamiento, rotación y consumidores de `Parametro.PasswordLdap`; reemplazar el esquema por un mecanismo de secretos de plataforma o cifrado autenticado con claves administradas, tras diseñar migración y pruebas de compatibilidad. No se aplicó ningún cambio.

**Observación O2 — blob de pagos opaco.** API y frontend propagan `parametrosEncriptados` sin conocer su algoritmo. Responsable candidato: integración Inscripciones/Pagos. Propuesta documental futura: solicitar contrato técnico que identifique algoritmo, modo, padding, versionado y protección de integridad, y revisar el servicio emisor/receptor. No se aplicó ningún cambio.

## Pendientes y dependencias

1. **Inventario criptográfico efectivo:** Core/API deben identificar todas las rutas que crean y persisten `PasswordLdap`, su formato histórico y el almacenamiento. Método: revisión de repositorio productor, esquema/configuración no secreta y prueba controlada de descifrado; sin exponer credenciales.
2. **Contrato de pagos:** el responsable de Inscripciones/Pagos debe aportar contrato/deployment sin secretos que indique el algoritmo, modo y padding de `parametrosEncriptados`, más una prueba de integración representativa. Si el proveedor usa ECB o PKCS#1 v1.5, abrir la remediación en su repositorio responsable.
3. **Validación negativa:** ejecutar en una fase autorizada pruebas o revisión de configuración que demuestren el rechazo/ausencia de ECB y PKCS#1 v1.5 en los servicios que realmente cifran datos. La búsqueda estática actual no sustituye esa validación.
4. **Dependencias relacionadas:** `v5.0.0-11.2.1` y `v5.0.0-11.3.2` deberán reutilizar solamente esta evidencia con sus límites; O1 es especialmente pertinente para la implementación criptográfica general.

No hay propuesta distribuida: no se confirmó un worktree ni repositorio responsable del servicio externo de pagos.
