# v5.0.0-11.3.1 — Modos de bloque y padding inseguros

## Identificación

- **ID y nivel mínimo:** v5.0.0-11.3.1 (L1).
- **Texto oficial:** "Verify that insecure block modes (e.g., ECB) and weak padding schemes (e.g., PKCS#1 v1.5) are not used."
- **Interpretación local:** los componentes que cifren datos no deben usar ECB, PKCS#1 v1.5 ni otro modo de bloque o padding inseguro. Una codificación, una ofuscación o un blob criptográfico de un tercero no prueban cifrado seguro.
- **Pregunta:** ¿el monorepo evita ECB, PKCS#1 v1.5 y otros modos/paddings inseguros en sus implementaciones de cifrado?
- **Avance documental:** DOCUMENTADO.
- **Resultado de seguridad:** NEEDS_REVIEW.
- **Fecha de revisión:** 2026-09-23; actualización: 2026-10-23.

## Aplicabilidad y alcance

Aplica a código propio que cifra datos y a integraciones cuyo algoritmo se pueda verificar desde el monorepo. En 912fc665 la API tiene una implementación de cifrado real: la caché Redis de imágenes de documento de identidad usa AES-256-GCM (`62effb5d`). El secreto LDAP sigue protegido por una ofuscación reversible, ahora reimplementada en la API (`LdapServiceKeyProvider`, `cebff419`/`12248719`) en lugar de `Core/Utilities/Encriptador`. El frontend sólo transporta el blob de pagos.

No se evaluaron el servicio de Inscripciones/Pagos, pasarelas, los paquetes `ORT.*` (Ldap, Messaging, DocumentIntelligence, Vision) como binarios, Redis/Key Vault efectivos, gateway ni tráfico real. No hay `.codegraph/` utilizable; se usó `rg`.

## Resultado por componente y conclusión

- **API:** NEEDS_REVIEW. La única primitiva de cifrado propia (AES-256-GCM, E1) no usa modos ni paddings inseguros. El secreto LDAP depende de una ofuscación sin cifrado (E2), que limita la conclusión criptográfica general, y el blob de pagos es opaco.
- **Core:** NEEDS_REVIEW, sin impacto en el camino activo de la API: `Encriptador` sigue sin modo/padding y ya no se consume desde la API.
- **Frontend:** NEEDS_REVIEW según la evidencia de `86979de2`, no re-verificada; sólo transporta el blob.
- **Integraciones externas:** fuera del alcance.

No se halló ECB ni PKCS#1 v1.5 en el monorepo. Falta confirmación determinística de las configuraciones efectivas y del algoritmo de Pagos, por lo que no hay PASS según ADR-002. No se ejecutaron tests, builds, runtime ni scans.

## Hallazgos y propuesta documental

**Observación O1 — ofuscación reversible del secreto LDAP (vigente, reubicada).** Antes en `Core/Utilities/Encriptador` + `Core/LdapService/Ldap`; desde `cebff419`/`12248719` en `WebApiAdmisiones/Security/Ldap/LdapServiceKeyProvider.Deobfuscate` (E2). Quien lea el valor persistido y el código puede revertirlo. Responsable candidato: API (y dueño de la tabla de parámetros). Propuesta: mover `PASSWORD_LDAP` a Key Vault como los demás secretos (`60c05999`) o cifrarlo con AEAD y clave administrada; diseñar migración. No se aplicó ningún cambio.

**Observación O2 — blob de pagos opaco (vigente).** API y frontend propagan `parametrosEncriptados` sin conocer su algoritmo. Responsable candidato: integración Inscripciones/Pagos. Propuesta: contrato técnico con algoritmo, modo, padding, versionado e integridad.

## Pendientes y dependencias

1. **Secreto LDAP:** identificar quién escribe `PASSWORD_LDAP`, su formato y almacenamiento; evaluar migración a Key Vault. Sin exponer credenciales.
2. **Contrato de pagos:** algoritmo, modo y padding de `parametrosEncriptados` y prueba de integración; si se usa ECB o PKCS#1 v1.5, remediar en el repositorio responsable.
3. **Paquetes `ORT.*`:** inventario criptográfico de los paquetes que cifran o firman (si alguno lo hace). No disponible.
4. **Validación negativa:** en fase autorizada, ejecutar E7 y revisar configuración efectiva.
5. **Frontend:** re-verificar E6 al actualizar el checkout de `admisiones`.
6. **Dependencias relacionadas:** v5.0.0-11.2.1, v5.0.0-11.3.2 (FAIL por O1/H1) y v5.0.0-11.4.1.

No hay propuesta distribuida.
