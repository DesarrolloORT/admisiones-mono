# v5.0.0-5.2.2

## Identificación

- ID: v5.0.0-5.2.2. Nivel mínimo: L1. Sección V5.2, File Upload and Content.
- Texto oficial: "Verify that when the application accepts a file, either on its own or within an archive such as a zip file, it checks if the file extension matches an expected file extension and validates that the contents correspond to the type represented by the extension. This includes, but is not limited to, checking the initial 'magic bytes', performing image re-writing, and using specialized libraries for file content validation. For L1, this can focus just on files which are used to make specific business or security decisions. For L2 and up, this must apply to all files being accepted."
- Interpretación local: para L1 se priorizan los documentos que alimentan reconocimiento de identidad, las imágenes de identidad/foto persistidas y, desde que están expuestos, los adjuntos de la declaración jurada que respaldan la evaluación de becas. Debe verificarse tanto la extensión declarada como la correspondencia entre esa extensión y el contenido.
- Pregunta verificable: ¿rechaza el servidor un archivo cuyo nombre tiene una extensión inesperada o cuya extensión no representa el contenido, antes de usarlo para reconocimiento o guardarlo?
- Avance documental: DOCUMENTADO. Resultado de seguridad: NEEDS_REVIEW.
- Fecha: 2026-09-17; actualización: 2026-10-23.

## Aplicabilidad y alcance

La SPA envía los archivos por `multipart/form-data` (ADR-019). El flujo de registro acepta un documento (imagen o PDF) para Azure Document Intelligence y usa los campos extraídos para decisiones de registro; el frente reconocido y el recorte de cara se guardan en Redis y luego en Oracle. La API también acepta foto de persona, frente/dorso de identidad y, ahora expuestos por HTTP (`347f8080`), el documento de la declaración jurada y los comprobantes de ingreso, que respaldan la evaluación de la beca. La validación común está en `AppLogic.Contracts/Files/FileValidator` (`d12599c4`); Core ya no participa. No se observó aceptación de ZIP en estos flujos; el ZIP del material de estudio es una salida generada por el servidor, no una carga. Formatos comprimidos de todos los archivos corresponden a 5.2.3 (L2).

No se inspeccionaron clientes externos, la implementación interna de los paquetes `ORT.Vision`/`ORT.DocumentIntelligence` (NuGet), la API de pagos ni la configuración de producción. La presencia de magic bytes no demuestra que el contenido entero sea un archivo decodificable.

## Resultado por componente y conclusión

Frontend: restricciones de UX, sin valor como barrera frente a clientes directos (no re-verificado). API: todos los flujos relevantes llaman al validador nuevo, que comprueba el prefijo contra una allowlist pero omite las dos condiciones del requisito sobre la extensión: que sea una extensión esperada (salvo en adjuntos de la declaración jurada) y que corresponda al contenido detectado (en ningún flujo). En el reconocimiento la extensión nominal, no verificada, decide además el MIME que se envía a Azure y si se valida la imagen con una librería especializada. El test E3 documenta la omisión. La revisión estática sustenta un defecto concreto de diseño para los flujos L1; el resultado permanece NEEDS_REVIEW conforme a ADR-002 hasta una prueba reproducible del boundary. No se atribuye ejecución de archivos, compromiso de identidad ni severidad definitiva. Core no participa.

## Hallazgos y propuesta documental

1. **Extensión no cotejada con contenido en archivos L1 (vigente en 912fc665).** Condición: `FileValidator.ValidateFile` acepta el primer magic byte de la allowlist y sólo exige que el nombre no esté vacío (E1-E3, E6); en adjuntos de la declaración jurada la extensión sí debe estar en allowlist, pero no se coteja con los bytes (E8). Impacto posible: el nombre/tipo almacenado o entregado a otro consumidor contradice los bytes (se materializa en el `Content-Type` de descargas, 4.1.1). Responsables candidatos: API (`AppLogic.Contracts/Files`). Propuesta para fase de fixes: en `ValidateFile`, exigir extensión nominal en la allowlist y que pertenezca al grupo del tipo detectado (`.jpg/.jpeg` ↔ JPEG, `.png` ↔ PNG, `.pdf` ↔ PDF); definir regla para nombre ausente (generar el nombre desde el tipo detectado); pruebas negativas por endpoint. Actualizar el test E3, que hoy codifica el comportamiento contrario.
2. **Nombre persistido incompatible con la imagen aceptada (vigente).** Condición: frente/dorso admiten PNG pero se nombran `.jpg`; la foto deriva la extensión del nombre no cotejado, sin allowlist (E7). Impacto posible: consumidores que interpretan por extensión reciben otro tipo o un nombre inesperado. Propuesta: derivar y guardar extensión/tipo desde el contenido validado, o normalizar a JPEG; revisar consumidores y datos existentes antes de migrar.
3. **Validación de contenido limitada al prefijo (parcialmente mitigada).** Condición: `FileValidator` sólo revisa magic bytes (E2). Nuevo: el reconocimiento decodifica imágenes para medir calidad (E5), pero esa validación se saltea si la extensión nominal no es de imagen, y foto, identidad y adjuntos no decodifican. Propuesta: decodificar (o re-escribir) imágenes con librería especializada en todos los flujos L1 y validar estructura de PDF; probar archivos truncados y polyglot de manera controlada. No equivale a una evaluación del L2 completo.
4. **Nuevo — MIME enviado a Azure derivado de la extensión no verificada.** Condición: `TextNormalizer.ResolverTipoMime` prioriza la extensión del nombre sobre el MIME del cliente y sobre el tipo detectado por bytes (E4). Impacto posible: discordancia entre el tipo declarado a Azure y el contenido, y omisión del chequeo de calidad/cara; no se evaluó cómo responde Azure. Responsable candidato: API (`AppLogic.Identity`). Propuesta: usar el tipo detectado por `FileValidator` como fuente del MIME y corregir el comentario de `ValidateRequest`.

No se distribuyó propuesta a ramas fix/owasp: la propuesta central queda aquí para distribución futura.
