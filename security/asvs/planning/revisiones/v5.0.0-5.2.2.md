- Texto oficial: "Verify that when the application accepts a file, either on its own or within an archive such as a zip file, it checks if the file extension matches an expected file extension and validates that the contents correspond to the type represented by the extension. This includes, but is not limited to, checking the initial 'magic bytes', performing image re-writing, and using specialized libraries for file content validation. For L1, this can focus just on files which are used to make specific business or security decisions. For L2 and up, this must apply to all files being accepted."

## Aplicabilidad y alcance

La SPA envía archivos como base64 dentro de JSON a la API. El flujo de registro acepta un documento para Azure Document Intelligence y usa los campos extraídos para decisiones de registro; el controlador puede guardar temporalmente el archivo reconocido. La API también acepta foto de persona y frente/dorso de identidad, que persiste como BLOB. Core aporta la validación común. Los adjuntos de becas se analizaron como posible superficie adicional, pero no se localizó una acción HTTP que llame sus métodos de subida en esta ref; su exposición queda pendiente. No se observó aceptación de ZIP en los flujos L1 leídos; inspeccionar formatos comprimidos de todos los archivos corresponde también a 5.2.3 (L2).

El frontend tiene .codegraph/ sin índice (sólo .gitignore), así que se usaron rg y lectura directa. API y Core no tienen .codegraph/. No se inspeccionaron clientes externos, todas las integraciones de archivos fuera de estas rutas, la API de pagos ni la configuración de producción. La presencia de magic bytes no demuestra que el contenido entero sea un archivo decodificable o que el nombre sea coherente.

## Resultado por componente y conclusión

Frontend: restricciones de UX, sin valor como barrera de seguridad frente a clientes directos. API: los flujos relevantes llaman al validador de Core, pero aceptan el nombre entregado por el cliente y en algunos casos persisten metadatos que pueden no representar los bytes. Core: comprueba que el prefijo pertenezca a un formato permitido, pero omite las dos condiciones de cotejar la extensión nominal contra la allowlist y contra el formato detectado. El test E3 documenta expresamente esa omisión. La revisión estática sustenta un defecto concreto de diseño para los flujos L1; el resultado permanece NEEDS_REVIEW conforme a ADR-002 hasta una prueba reproducible del boundary y del comportamiento completo. No se atribuye ejecución de archivos, compromiso de identidad ni severidad definitiva.

## Hallazgos y propuesta documental

1. **Extensión no cotejada con contenido en archivos L1.** Condición: ValidateFile acepta el primer magic byte de la allowlist y sólo exige que FileName no esté vacío (E1-E5); un PNG con nombre .jpg, .exe o sin extensión es un caso explícito de test (E3). Impacto posible: el nombre/tipo almacenado o entregado a otro consumidor puede contradecir los bytes; el control exigido por 5.2.2 no está implementado en el boundary. Responsables candidatos: Core y API. Propuesta para fase de fixes: validar extensión nominal permitida y correspondencia exacta con el tipo detectado antes de Azure o persistencia; definir una regla explícita para nombres ausentes y MIME, y pruebas negativas para extensiones inesperadas/mismatched en cada endpoint.
2. **Nombre persistido incompatible con imagen aceptada.** Condición: frente/dorso admiten PNG pero se nombran .jpg; foto deriva extensión del nombre no cotejado (E6). Impacto posible: consumidores que interpretan el archivo por extensión pueden recibir un tipo distinto, o un nombre no esperado. Responsables candidatos: API/Core según contrato de persistencia. Propuesta: decidir si normalizar bytes a JPEG o derivar y guardar nombre/tipo desde el contenido validado; validar clientes de lectura y datos ya guardados antes de migrar.
3. **Validación de contenido limitada al prefijo.** Condición: E2 revisa sólo magic bytes; no hay decodificación completa en FileValidator. Azure puede rechazar muchos archivos malformados en reconocimiento, pero foto/identidad no pasan necesariamente por ese parser. Riesgo de contenido malformado aceptado; no se confirmó explotación. Propuesta: en fase posterior evaluar decodificación con librería de imagen/PDF apropiada y, si procede, reescritura; probar archivos truncados y polyglot de manera controlada. No equivale a una evaluación del L2 completo.

No se distribuyó propuesta a ramas fix/owasp de Core/API: se verificaron los clones originales y estaban en gabriele/feat/getScolarship (API) y develop (Core), sin worktree fix/owasp disponible; no se creó ni cambió checkout. La propuesta central queda aquí para distribución futura.
