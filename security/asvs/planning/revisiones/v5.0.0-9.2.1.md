# v5.0.0-9.2.1 — vigencia de tokens autocontenidos

## Identificación

- ID: v5.0.0-9.2.1; nivel mínimo L1.
- Texto oficial íntegro: “Verify that, if a validity time span is present in the token data, the token and its content are accepted only if the verification time is within this validity time span. For example, for JWTs, the claims 'nbf' and 'exp' must be verified.”
- Interpretación local: la API debe rechazar un JWT que contenga `nbf` o `exp` fuera de su intervalo temporal antes de usar sus claims.
- Pregunta: ¿los JWT entrantes de acceso y de activación/sesión temporal validan `nbf`/`exp` antes de consumir identidad o propósito?
- Avance: DOCUMENTADO. Resultado: NEEDS_REVIEW. Fecha: 2026-09-22.

## Aplicabilidad y alcance

Se incluyeron los JWT de acceso recibidos desde cookie HttpOnly o `Authorization`, y los JWT de enlace de activación y sesión temporal de contraseña. Estos últimos se validan antes de leer `purpose` y `sub`; el bearer se registra antes de autorización y controladores.

El refresh token es opaco y persistido, por lo que no es JWT autocontenido. El JWT HS256 de `TokenServiceInternalApi` es un boundary saliente cuyo receptor no está en este monorepo. No se evaluaron gateway/proxy, configuración efectiva, reloj del host ni comportamiento HTTP desplegado.

## Resultado por componente y conclusión

- API: la lectura estática muestra `ValidateLifetime = true` en ambos validadores JWT entrantes y que los emisores propios incluyen expiración. Los flujos de activación/sesión no usan claims antes de esa validación.
- Core: sin intervención directa localizada.
- Receptor externo del JWT de servicio: no evaluado; no hereda este resultado.

Resultado global: DOCUMENTADO / NEEDS_REVIEW. Según [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md), lectura estática y tests no ejecutados no habilitan `PASS`. No se identificó contradicción estática ni se confirma incumplimiento.

## Hallazgos y propuesta documental

No se confirma un hallazgo ni se propone un fix. Gap de evidencia: faltan pruebas reproducibles de tokens con `exp` pasado, `nbf` futuro y fronteras dentro/fuera del `ClockSkew`, en bearer, enlace y sesión temporal. Responsable candidato: API/QA. Para una fase posterior, agregar pruebas de unidad/integración que demuestren rechazo 401 y ausencia de principal o continuación del flujo. No se distribuyó propuesta a ramas `fix/owasp`.
