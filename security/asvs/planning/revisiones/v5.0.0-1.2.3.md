## Aplicabilidad y alcance

Incluye JSON de solicitudes/respuestas HTTP, errores, estado en Redis (sesión 2FA, flujo de registro, persona pendiente, caché de catálogos, imágenes cifradas), sessionStorage del frontend, formulario de pago, mensajes a Service Bus (ORT.Messaging) y logs. Boundaries: datos API → navegador → proveedor de pagos; DTO → formatter HTTP; objeto → Redis; contrato → Service Bus → worker; objeto → texto de log.

Búsqueda en la API vigente (AppLogic y WebApiAdmisiones): JsonSerializer.Serialize, WriteAsJsonAsync, PostAsJsonAsync, ReadFromJsonAsync, UnsafeRelaxed/Encoder, WriteRawValue, Utf8JsonWriter, application/javascript y literales JSON armados a mano. Solo se encontró un literal JSON fijo de ejemplo de esquema (JsonSchemaValidationFilter 257), sin datos variables. Core/Utilities (SerializeJsonLog, Firmar) y Core/LdapService ya no están en el grafo de la API. La serialización de los contratos ORT.Messaging la hace el paquete ORT.Messaging.ServiceBus, no inspeccionado. Frontend: inventario original (sin eval, new Function, bypassSecurityTrustScript, JSONP ni scripts inline con los patrones consultados), no re-verificado.

## Resultado por componente y conclusión

Frontend (sin re-verificar), API y Core: NEEDS_REVIEW. En la API todos los JSON localizados (HTTP, errores, Redis, salientes) se producen con serializadores y ya no queda la transformación posterior de Core/Util en el flujo. Faltan la serialización de los paquetes ORT, el receptor de pagos, el visor de logs y la evidencia ejecutada. Conforme a [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md), esta revisión estática no produce PASS/FAIL.

## Hallazgos y propuesta documental

- H1, Core: SerializeJsonLog transforma la salida del serializador (E9). **Resuelto en 912fc665 para la API**: Core/Utilities ya no se referencia desde ningún proyecto de la API. Sigue abierto para otros consumidores de Core, a cargo de sus mantenedores; validar la compatibilidad de firmas antes de cualquier cambio.
- H2, API: el formato textual de LoggingHelper usa un encoder relajado y retornos sin serialización (E8). Vigente, sin cambios. Responsable candidato: API/observabilidad. Propuesta condicionada: codificar en la frontera del visor/exportador y no reutilizar LogMessage como documento JSON/script.
- Pago externo: el comentario de parsing manual del receptor sigue siendo una dependencia a verificar, no evidencia de vulnerabilidad.
- Nuevo, a verificar: serialización de contratos ORT.Messaging (E7). Se espera System.Text.Json en el paquete; confirmarlo con su dueño. Sin hallazgo atribuido.

No se aplicaron cambios de código, tests, configuración ni dependencias. Las copias documentales distribuidas en la revisión original (worktrees temporales admisiones-owasp-20260916 de API y Core, refs 2df055e7… y 43e63b3a…) no se volvieron a verificar y pueden no existir. La de Core corresponde a H1, que ya no afecta a la API.

## Pendientes y dependencias

1. Frontend/API: en una fase de validación autorizada, comprobar bytes y round trip de strings con comillas, backslash, saltos, controles, `</script>`, U+2028/U+2029 y secuencias Unicode literales en éxito y errores MVC/middleware, HTTP saliente y Redis.
2. Dueño del proveedor de pagos: aportar la ref y el parser real del campo data y de encryptedParameters.
3. Dueños de ORT.Messaging.ServiceBus: aportar versión y opciones de serialización de los contratos.
4. Observabilidad/infraestructura: aportar la configuración y el renderizado del visor (Loki/OTel) para establecer si LogMessage cruza una frontera HTML/JavaScript/JSON.
5. Hosting/frontend: re-verificar E1–E3 contra 86979de2 o posterior e inspeccionar el artefacto servido.
6. IDs relacionados: v5.0.0-1.1.2, v5.0.0-1.2.1 y v5.0.0-16.2.1 (logs).
