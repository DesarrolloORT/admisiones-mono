## Resultado por componente y conclusión

- Frontend: NEEDS_REVIEW. Se observan interpolación, builder de path y APIs estructuradas de formulario; quedan intérprete real, librería UI y transporte de pagos por demostrar.
- API: NEEDS_REVIEW. Respuestas serializables, escritura JSON explícita y codificación HTML/URL en correo conservada hasta el envío en los tramos leídos. Falta cobertura y evidencia del extremo receptor.
- Core: NEEDS_REVIEW. Conserva el body HTML ya construido y serializa un cuerpo HTTP; helpers no imponen codificación a callers, por lo que no existe garantía global demostrada para consumidores compartidos.

DOCUMENTADO / NEEDS_REVIEW conforme a [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md). No se confirmó vulnerabilidad, FAIL, PASS ni severidad. La codificación puede hacerse antes de concatenar markup fijo si permanece intacta hasta el intérprete: ensamblar envoltorios después de codificar no constituye por sí solo incumplimiento.

## Hallazgos y propuesta documental

1. **Contrato de pagos sin evidencia de receptor (E3–E4).** El formulario envía JSON, mientras el comentario describe extracción con Split. Si el receptor no interpreta escapes JSON según el contrato, ciertos caracteres podrían alterar o rechazar el blob. Hipótesis de incompatibilidad, sin explotación confirmada. Responsables candidatos: frontend/API y dueño de pagos. Primero obtener contrato y muestras sintéticas de extremo a extremo; definir remediación únicamente si se demuestra pérdida de estructura o significado.
2. **Contrato implícito de helpers HTML compartidos (E7–E9).** Core acepta fragmentos HTML y texto sin distinguirlos. Activación codifica sus variables y 2FA genera dígitos; eso no cubre otros callers. Impacto posible si otro caller pasa texto arbitrario: interpretarlo como markup. Responsable candidato: Core con consumidores. Documentar qué argumentos son HTML ya construido y cuáles requieren texto codificado; inventariar consumidores antes de decidir un cambio de API, evitando codificar globalmente cuerpos HTML y romper plantillas válidas.

Son propuestas de obtención de evidencia y aclaración de contratos, conservadas en esta ficha central. No se definió un fix concreto ni se distribuyeron copias en worktrees de otras refs; distribución pendiente de responsables/contrato y propuesta madura. No se aplicaron cambios a código, tests, configuración, dependencias ni submódulos.
