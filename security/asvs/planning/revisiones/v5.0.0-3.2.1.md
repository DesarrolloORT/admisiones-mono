# v5.0.0-3.2.1 — Interpretación no intencionada de contenido servido directamente

## Identificación

- **ID:** v5.0.0-3.2.1
- **Nivel mínimo:** L1 (capítulo V3 «Web Frontend Security», sección V3.2 «Unintended Content Interpretation»)
- **Texto oficial íntegro:**

  > Verify that security controls are in place to prevent browsers from rendering content or functionality in HTTP responses in an incorrect context (e.g., when an API, a user-uploaded file or other resource is requested directly). Possible controls could include: not serving the content unless HTTP request header fields (such as Sec-Fetch-\*) indicate it is the correct context, using the sandbox directive of the Content-Security-Policy header field or using the attachment disposition type in the Content-Disposition header field.

- **Interpretación local (separada del texto oficial):** para cada endpoint que devuelve directamente bytes de un recurso (no JSON), verificar si existe algún control — `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment`, CSP `sandbox`, o chequeo de `Sec-Fetch-*` — que impida que el navegador interprete esa respuesta como HTML/JS cuando se solicita en un contexto distinto del previsto por la SPA (por ejemplo, pegando la URL directamente en la barra de direcciones).
- **Pregunta concreta que debe quedar respondida:** ¿los endpoints que sirven bytes de un recurso (foto de perfil, adjuntos de la declaración jurada, material de estudio) llevan algún control de los descritos por el requisito, y el resto del pipeline HTTP aplica al menos uno de ellos globalmente?

## Aplicabilidad y alcance

Aplica. El requisito cubre cualquier respuesta HTTP que un navegador pudiera interpretar en un contexto distinto del previsto. Inventario de endpoints que devuelven bytes de un recurso directamente (no JSON) en `912fc665`, más el pipeline de headers global:

1. **`GET /person/photo`** (`PersonController.GetPersonPhoto`) — `File(bytes, "image/jpeg")`, sin nombre de archivo.
2. **`GET /scholarships/affidavit-document`** y **`GET /scholarships/income-receipt`** (`ScholarshipsController`, nuevos desde la revisión anterior) — adjuntos que sube la persona (declaración jurada y comprobante de ingreso), servidos con `File(content, contentType, fileName)`.
3. **`GET /scholarships/study-material`** (nuevo, commit `56329628`) — ZIP armado por la API a partir de URLs configuradas; no es contenido del usuario.
4. **`GET /person/identity-document`** — sigue devolviendo JSON (`PersonIdentityDocumentResponse` con `Front`/`Back`), no bytes top-level.
5. **Pipeline de seguridad global** (`MiddlewarePipelineExtensions.UseSecurityHeaders`) y el nuevo middleware `UseOriginCheck`, que lee `Sec-Fetch-Site`.
6. **Sitio de documentación estática** (`admisiones/docs-site`) con su propio `web.config` (frontend, no re-verificado).

Búsqueda de `File(`, `FileContentResult`, `PhysicalFile`, `FileStreamResult`, `Results.File|Bytes` en la API y Core: los únicos sinks de bytes son los de (1)-(3). `UseStaticFiles` solo sirve `Docs/contracts` (JSON de contratos) fuera de Production/Preproduction.

Alcance **no** inspeccionado que limita la conclusión:

- Servicios externos (Azure Document Intelligence, pasarela de pagos, worker de mensajería, origen del material de estudio): no se revisó qué headers agregan.
- Infraestructura de despliegue (App Service / contenedor / gateway) fuera del repo.
- Runtime: no se ejecutó ningún request; toda la evidencia es lectura de código.
- Datos legacy: no se inspeccionaron las extensiones realmente guardadas en `EXTENSION_ARCHIVO_INGRESO` / `EXTENSION_PDF_REVALIDAS_DJ` por el sistema legacy (relevante para el hallazgo 3).

## Resultado por componente y conclusión

- **API · `/person/photo`:** igual que antes. Control parcial: `Content-Type` fijo del servidor (E1) y `nosniff` global (E3). Faltan los controles que el requisito nombra: no hay `Content-Disposition`, no hay CSP `sandbox` y no hay chequeo de `Sec-Fetch-*` para GET (E8).
- **API · descargas de becas y material de estudio (nuevas):** llevan `Content-Disposition: attachment` (E4, E7), uno de los controles explícitos del requisito, más `nosniff` (E3). Queda una observación: el `Content-Type` sale de la extensión guardada e incluye `text/html` (E5). Hoy `attachment` y `nosniff` lo cubren, y el upload actual no deja guardar `.html` (E6).
- **API · `/person/identity-document`:** no aplica al riesgo descrito (E2).
- **Core:** ya no participa. `Core/Utilities/FileValidator.cs` no está en el grafo de compilación de la API; la validación equivalente está en `AppLogic.Contracts` (E6).
- **Frontend:** sin re-verificar (E9, E10). Su patrón de consumo no es un control del servidor.
- **Infraestructura:** sin evidencia versionada de headers de plataforma (E11).

**Conclusión: NEEDS_REVIEW.** La superficie que sirve bytes creció de 1 a 4 endpoints. Los 3 nuevos traen `Content-Disposition: attachment`, que es un control del requisito. `/person/photo` sigue dependiendo solo de `nosniff` y de su tipo constante. No hay evidencia ejecutada (ADR-002) de las respuestas reales.

## Hallazgos y propuesta documental

### Hallazgo 1 — `/person/photo` no lleva `Content-Disposition` ni chequeo de `Sec-Fetch-*`/CSP `sandbox` (vigente en 912fc665)

- **Condición concreta:** `GetPersonPhoto` (E1) no agrega `Content-Disposition`, la CSP global no tiene `sandbox` (E3) y `UseOriginCheck` deja pasar todos los GET sin mirar `Sec-Fetch-*` (E8). A diferencia de las descargas nuevas (E4), este endpoint no pasa nombre de archivo y por eso no recibe `attachment`.
- **Impacto:** falta defensa en profundidad, no es una vulnerabilidad confirmada. El `Content-Type` es constante (E1) y `nosniff` (E3) evita el sniffing.
- **Evidencia:** E1, E3, E8.
- **Responsable candidato:** api-admisiones (`PersonController`, `MiddlewarePipelineExtensions`).
- **Propuesta de cambio (fase posterior, no aplicada):** agregar `Content-Disposition` explícito en `GetPersonPhoto` (por ejemplo `inline; filename="photo.jpg"`, o `attachment` como en `AsFile`). Evaluar rechazar `Sec-Fetch-Dest: document` en los GET que sirven bytes.
- **Validación futura:** con sesión válida, navegar directo a `/person/photo` y comparar el tratamiento con `Sec-Fetch-Dest: document` y con `Sec-Fetch-Dest: image`.

### Hallazgo 2 — El `Content-Type` de `/person/photo` no se revalida contra el tipo real almacenado (deuda, no defecto confirmado; vigente)

- **Condición concreta:** el upload valida por magic bytes y acepta `.jpg/.jpeg/.png` (E6), pero `GetPersonPhoto` sirve siempre `image/jpeg` (E1). Una foto PNG válida se sirve con tipo JPEG.
- **Impacto:** no se ve explotabilidad. `nosniff` hace que el navegador confíe en el tipo declarado. Es deuda de diseño en el punto de salida.
- **Evidencia:** E1, E3, E6.
- **Responsable candidato:** api-admisiones (`AppLogic.People.UseCases.GetPersonPhoto`).
- **Propuesta de cambio (no aplicada):** detectar el tipo por magic bytes al servir y usarlo como `Content-Type`.
- **Validación futura:** nota de diseño; no hay escenario reproducible.

### Hallazgo 3 (nuevo) — Las descargas de becas derivan el `Content-Type` de la extensión guardada e incluyen `text/html` (observación, no defecto confirmado)

- **Condición concreta:** `AffidavitFileService.GetContentType` (E5) mapea `.html` a `text/html`, y un test lo fija. La extensión viene de una columna que también escribe el legacy. El upload de esta API solo admite `.pdf/.jpg/.jpeg/.png` (E6).
- **Impacto:** si existiera un registro legacy con extensión `.html` y contenido HTML, la API lo serviría como `text/html` desde su propio origen. Hoy `Content-Disposition: attachment` (E4) y `nosniff` (E3) hacen que se descargue en vez de renderizarse, y la CSP de la API bloquea scripts inline. No se verificó que haya datos así.
- **Evidencia:** E3, E4, E5, E6.
- **Responsable candidato:** api-admisiones (`AppLogic.Scholarships.Affidavit.Services.AffidavitFileService`).
- **Propuesta de cambio (no aplicada):** limitar el mapa a los tipos que el upload acepta y servir el resto como `application/octet-stream`, o detectar el tipo por magic bytes al servir.
- **Validación futura:** consultar las extensiones distintas guardadas en esas columnas; con un registro de prueba `.html`, observar los headers y el comportamiento del navegador.
