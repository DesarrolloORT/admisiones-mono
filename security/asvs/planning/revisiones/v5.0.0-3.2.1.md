# v5.0.0-3.2.1 — Interpretación no intencionada de contenido servido directamente

## Identificación

- **ID:** v5.0.0-3.2.1
- **Nivel mínimo:** L1 (capítulo V3 «Web Frontend Security», sección V3.2 «Unintended Content Interpretation»)
- **Texto oficial íntegro:**

  > Verify that security controls are in place to prevent browsers from rendering content or functionality in HTTP responses in an incorrect context (e.g., when an API, a user-uploaded file or other resource is requested directly). Possible controls could include: not serving the content unless HTTP request header fields (such as Sec-Fetch-\*) indicate it is the correct context, using the sandbox directive of the Content-Security-Policy header field or using the attachment disposition type in the Content-Disposition header field.

- **Interpretación local (separada del texto oficial):** para cada endpoint que devuelve directamente bytes de un recurso (no JSON), verificar si existe algún control — `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment`, CSP `sandbox`, o chequeo de `Sec-Fetch-*` — que impida que el navegador interprete esa respuesta como HTML/JS cuando se solicita en un contexto distinto del previsto por la SPA (por ejemplo, pegando la URL directamente en la barra de direcciones).
- **Pregunta concreta que debe quedar respondida:** ¿los endpoints que sirven bytes de un recurso (foto de perfil, documento de identidad) llevan algún control de los descritos por el requisito, y el resto del pipeline HTTP aplica al menos uno de ellos globalmente?

## Aplicabilidad y alcance

Aplica. El requisito cubre cualquier respuesta HTTP que un navegador pudiera interpretar en un contexto distinto del previsto. Se inventariaron los endpoints que devuelven bytes de un recurso directamente (no JSON) y el pipeline de headers global:

1. **`GET /person/photo`** (`PersonController.GetPersonPhoto`) — único endpoint localizado que retorna un `FileContentResult` con bytes crudos.
2. **`GET /person/identity-document`** (`PersonController.GetPersonIdentityDocument`) — retorna JSON (`OperationResult<PersonIdentityDocumentResponse>`) con el contenido del archivo como campo del payload, no como respuesta binaria top-level; el riesgo de "renderizado en contexto incorrecto" que describe el requisito no aplica del mismo modo porque el navegador nunca recibe `Content-Type: image/*` ni bytes para ese endpoint.
3. **Pipeline de seguridad global** (`MiddlewarePipelineExtensions.UseSecurityHeaders`), aplicado a todas las respuestas de la API, incluidas las de (1).
4. **Sitio de documentación estática** (`admisiones/docs-site`) con su propio `web.config`.

No se encontraron otros controllers en API o Core que devuelvan bytes de archivos (`return File(`, `FileContentResult`, `PhysicalFile`) fuera de `PersonController`.

Alcance **no** inspeccionado que limita la conclusión:

- Servicios externos: Azure (reconocimiento de documentos), pasarela de pagos, proveedor de mail — no se revisó qué headers agregan sus propias respuestas ni si la SPA navega directamente a URLs de esos proveedores.
- Infraestructura de despliegue (Azure App Service / IIS / nginx) fuera del repo: no versionada aquí: no se puede afirmar si agrega o sobrescribe headers a nivel de plataforma.
- Runtime: no se ejecutó ningún request contra la API; toda la evidencia es lectura de código de la respuesta configurada, no de la respuesta real observada por el navegador.
- Otros posibles sinks de bytes que no calcen con los patrones de búsqueda usados (`return File(`, `FileContentResult`, `PhysicalFile`, `Ok(bytes)` con `Content-Type` manual): no se garantiza cobertura exhaustiva por regex/rg, sólo por los patrones habituales de ASP.NET Core.
- Swagger/OpenAPI estático (`UseStaticFiles`) sólo se sirve en entornos no productivos; no es contenido de usuario y no se profundizó.

## Resultado por componente y conclusión

- **API · `/person/photo`:** control parcial presente por dos vías independientes — (a) el `Content-Type` es fijado por el servidor y no por el cliente (E1), y (b) `nosniff` está aplicado globalmente (E3), que es uno de los controles que el propio catálogo de ejemplos del requisito no menciona explícitamente pero cumple la misma función preventiva (evita que el navegador reinterprete bytes por sniffing cuando el `Content-Type` declarado no coincide con el contenido real). Falta el control explícito que el requisito sí nombra: no hay `Content-Disposition: attachment`, no hay CSP `sandbox`, y no hay chequeo de `Sec-Fetch-*` (E4) para rechazar una solicitud de navegación directa (top-level) a ese endpoint.
- **API · `/person/identity-document`:** NOT_APPLICABLE al riesgo descrito — el contenido nunca llega como bytes top-level con `Content-Type` de recurso (E2).
- **Core:** no se identificaron controllers propios que sirvan archivos directamente; la validación por magic bytes (E5) ocurre en el punto de entrada, no en el de salida, por lo que no es evidencia de un control de este requisito en particular, sólo contexto de v5.0.0-2.2.1.
- **Frontend:** el patrón de consumo actual (XHR con `responseType: 'blob'`, E6) mitiga el escenario típico dentro de la SPA, pero no es un control del servidor y no impide que cualquier cliente (no necesariamente la SPA) solicite la URL directamente, que es exactamente el escenario que el requisito contempla ("when … a resource is requested directly").
- **Infraestructura:** no hay evidencia en el repo de headers agregados a nivel de plataforma para la API o la SPA (E8); esa capa queda fuera del alcance verificable en este monorepo.

**Conclusión: NEEDS_REVIEW.** Existe un control real y aplicado globalmente (`nosniff`, E3) que reduce el riesgo central del requisito para el único endpoint que sirve bytes directamente, y el `Content-Type` de ese endpoint no depende de ningún dato controlado por el cliente (E1). No se satisface el requisito de forma completa porque ninguno de los controles que el texto oficial ejemplifica explícitamente —`Sec-Fetch-*`, CSP `sandbox`, `Content-Disposition: attachment`— está presente, y no hay evidencia reproducible (ADR-002) de que `nosniff` sea, en la práctica de este código, un control equivalente y suficiente: no se ejecutó ningún request real ni se observó la respuesta HTTP efectiva.

## Hallazgos y propuesta documental

### Hallazgo 1 — `/person/photo` no lleva `Content-Disposition` ni ningún control de `Sec-Fetch-*`/CSP `sandbox`

- **Condición concreta:** el único endpoint que sirve bytes de un recurso de usuario directamente (E1) no agrega `Content-Disposition` (ni `inline` ni `attachment`), no hay directive `sandbox` en la CSP global (E3), y no existe ningún chequeo de `Sec-Fetch-Dest`/`Sec-Fetch-Site` (E4) que distinga una solicitud programática (XHR de la SPA) de una navegación directa a la URL.
- **Impacto:** si un atacante logra que la respuesta de `/photo` no coincida con lo que el `Content-Type` declara (por ejemplo, si en el futuro el tipo dejara de fijarse como constante y pasara a derivarse de datos controlados por el usuario), el único freno actual sería `nosniff`. Hoy el `Content-Type` es una constante del servidor (E1), por lo que el escenario de explotación inmediato no está demostrado; el hallazgo es de falta de defensa en profundidad, no de una vulnerabilidad confirmada.
- **Evidencia:** E1, E3, E4.
- **Responsable candidato:** api-admisiones (`WebApiAdmisiones.Controllers.PersonController`, `Extensions.MiddlewarePipelineExtensions`).
- **Propuesta de cambio (para fase posterior, no aplicada):** agregar `Content-Disposition: inline; filename="photo.jpg"` (o `attachment` si se prefiere forzar descarga) explícitamente en `GetPersonPhoto`, y evaluar si conviene rechazar la solicitud cuando `Sec-Fetch-Dest` indique navegación de documento top-level (`document`) en vez de `image`/`empty`, dado que el consumo previsto es siempre XHR (E6).
- **Validación futura:** con la app corriendo, pegar la URL de `/person/photo` (con una sesión autenticada válida) directamente en la barra de direcciones del navegador y observar cómo la renderiza; repetir enviando manualmente `Sec-Fetch-Dest: document` vs. `Sec-Fetch-Dest: image` para confirmar si hay diferencia de tratamiento.

### Hallazgo 2 — El `Content-Type` de `/person/photo` no se revalida contra el tipo real almacenado (deuda, no defecto confirmado)

- **Condición concreta:** `FileValidator` detecta el tipo real por magic bytes al subir (E5), pero `GetPersonPhoto` fija `"image/jpeg"` como constante al servir (E1), sin volver a comprobar que el blob almacenado siga siendo efectivamente un JPEG.
- **Impacto:** si por cualquier vía (bug, migración de datos, cambio futuro del flujo de carga) el blob almacenado dejara de ser un JPEG real, la respuesta seguiría declarando `image/jpeg` con `nosniff` activo (E3); el navegador confiaría en la declaración del servidor y probablemente fallaría a renderizar en vez de interpretar el contenido como HTML — es decir, `nosniff` cubre este caso incluso sin revalidación en el punto de salida. No se encontró evidencia de que esto ocurra hoy; se documenta como deuda de diseño (falta de defensa en profundidad en el punto de salida), no como hallazgo explotable.
- **Evidencia:** E1, E3, E5.
- **Responsable candidato:** api-admisiones (`AppLogic.People.UseCases.GetPersonPhoto`).
- **Propuesta de cambio (para fase posterior, no aplicada):** ninguna con prioridad alta; si se decide reforzar, re-detectar el tipo por magic bytes en el momento de servir y usarlo en el `Content-Type` de la respuesta en vez de la constante.
- **Validación futura:** no aplica sin un escenario reproducible de blob corrupto; queda como nota de diseño.
