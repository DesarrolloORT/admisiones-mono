# v5.0.0-3.4.2

## Identificación

- **ID**: v5.0.0-3.4.2. **Nivel mínimo**: L1 (catalogo.md registra objetivo L2, pero la fase vigente solo exige L1).
- **Texto oficial**: "Verify that the Cross-Origin Resource Sharing (CORS) Access-Control-Allow-Origin header field is a fixed value by the application, or if the Origin HTTP request header field value is used, it is validated against an allowlist of trusted origins. When 'Access-Control-Allow-Origin: *' needs to be used, verify that the response does not include any sensitive information."
- **Interpretación local**: el `Access-Control-Allow-Origin` que emite la aplicación en producción debe ser un valor fijo o el resultado de validar el `Origin` de la request contra una allowlist explícita. Si en algún escenario se usa `*`, esa respuesta no debe contener datos sensibles.
- **Pregunta concreta**: ¿la política CORS que configura y aplica `api-admisiones` usa una allowlist fija de orígenes (o un valor fijo), en vez de reflejar cualquier `Origin` sin validar o de usar `*` con datos sensibles?
- **Avance documental**: DOCUMENTADO.
- **Resultado de seguridad**: NEEDS_REVIEW. La evidencia estática es favorable y hay tests reales que no se ejecutaron; falta verificación determinística en runtime (ver ADR-002).
- **Fecha de revisión**: 2026-09-17; actualización: 2026-10-23.

## Aplicabilidad y alcance

- CORS es responsabilidad exclusiva del servidor que emite el header. En este monorepo solo `api-admisiones` lo configura. El frontend es cliente y no aplica.
- `api-admisiones/Core` no registra ninguna política CORS.
- Cambio de diseño (`73794742`): la allowlist dejó de estar hardcodeada en código. Ahora se lee de `Cors:AllowedOrigins` del `appsettings.{env}.json` de cada ambiente. La misma lista alimenta el nuevo `UseOriginCheck` (ver 3.5.1).
- Alcance no inspeccionado:
  - Sobrescrituras de `Cors:AllowedOrigins` desde Key Vault o desde la configuración de la plataforma, que el proveedor de configuración podría aplicar sin pasar por el repo.
  - Hosting o reverse proxy que agregue o reescriba headers CORS.
  - El comportamiento en runtime.
  - Si el binario desplegado corresponde a este código.

## Resultado por componente y conclusión

- **API (`api-admisiones`)**: la política cumple la letra del requisito. Usa una allowlist explícita por ambiente, sin `*`, sin reflejar `Origin` sin validar y sin `AllowAnyOrigin`. Además mejoró respecto de la revisión anterior: producción ya no confía en orígenes no productivos (E2). Hay tests de pipeline que verifican el header (E5). Se mantiene NEEDS_REVIEW por dos motivos: (a) esos tests no se ejecutaron y no hay evidencia de runtime (ADR-002), y (b) la allowlist ahora depende de la configuración efectiva por ambiente, que puede sobrescribirse fuera del repo.
- **Core**: no aplica.
- **Frontend**: no aplica como emisor; no re-verificado.
- **Conclusión global**: no se observa el defecto que el requisito busca prevenir. Para avanzar falta ejecutar E5 y capturar el header real en al menos un ambiente desplegado.

## Hallazgos y propuesta documental

1. **Tests de CORS sin verificación real de contenido. Resuelto en parte en 912fc665 (`73794742`).**
   - Estado: se agregaron tests reales de preflight por ambiente (E5) y se borraron los 5 `Includes*Origins`. Quedan tests placebo con nombres engañosos (E6).
   - Impacto residual: confusión al leer la suite. La red de seguridad ya existe en E5.
   - Responsable candidato: equipo API.
   - Propuesta (no aplicada): borrar o renombrar los tests de E6, que dicen «DisallowsCredentials» cuando el código usa `AllowCredentials()`.
   - Validación futura: ejecutar `CorsPolicyByEnvironmentTests` y confirmar que falla con `AllowAnyOrigin()`.

2. **Gobernanza de `AllowCredentials()` (contexto, no hallazgo de código). Vigente.**
   - Condición concreta: ADR-009 sigue en `draft` y no refleja la decisión de `73794742`.
   - Propuesta: actualizar ADR-009 o enlazarlo con `docs/DECISIONES-IMPLEMENTACION.md` (V-02).

3. **Nuevo (observación): la allowlist depende de la configuración efectiva por ambiente.**
   - Condición concreta: `Cors:AllowedOrigins` se lee de `IConfiguration` (E1). Una clave con el mismo nombre en Key Vault o en las variables de la plataforma pisaría la lista versionada sin dejar rastro en el repo. Development (desplegado en `admisionesdesa*`) incluye `http://localhost:4200` con credenciales. Es deliberado: el flujo documentado del front es `npm start -- desa` desde localhost (comentario en `CorsPolicyByEnvironmentTests.cs:31`).
   - Impacto: no hay defecto observado. Es un límite de verificación, más un origen HTTP local aceptado con credenciales en un ambiente desplegado no productivo.
   - Responsable candidato: equipo API / infraestructura.
   - Propuesta (no aplicada): registrar al inicio, en el log, los orígenes efectivos por ambiente, y evaluar si el uso de `http://localhost:4200` contra Development justifica aceptar ese origen con credenciales.
   - Validación futura: preflight real contra cada ambiente desplegado.
