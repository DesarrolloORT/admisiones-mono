# v5.0.0-3.4.2

## Identificación

- **ID**: v5.0.0-3.4.2. **Nivel mínimo**: L1 (catalogo.md registra objetivo L2, pero la fase vigente solo exige L1).
- **Texto oficial**: "Verify that the Cross-Origin Resource Sharing (CORS) Access-Control-Allow-Origin header field is a fixed value by the application, or if the Origin HTTP request header field value is used, it is validated against an allowlist of trusted origins. When 'Access-Control-Allow-Origin: *' needs to be used, verify that the response does not include any sensitive information."
- **Interpretación local**: el header `Access-Control-Allow-Origin` que efectivamente emite la aplicación en producción debe ser un valor fijo o resultar de validar el `Origin` de la request contra una allowlist explícita; si en algún escenario se usa `*`, esa respuesta no debe contener datos sensibles.
- **Pregunta concreta**: ¿la política CORS que configura y aplica `api-admisiones` usa una allowlist fija de orígenes (o un valor fijo) en vez de reflejar cualquier `Origin` sin validar o usar `*` junto con datos sensibles?
- **Avance documental**: DOCUMENTADO.
- **Resultado de seguridad**: NEEDS_REVIEW (evidencia estática favorable; sin verificación runtime determinística, ver ADR-002).
- **Fecha de revisión**: 2026-09-17.

- CORS es responsabilidad exclusiva del servidor que emite el header; en este monorepo solo `api-admisiones` lo configura. El frontend Angular (`admisiones`) es cliente y no aplica al requisito; se confirmó que no define ninguna política CORS propia.
- `api-admisiones/Core` no registra ninguna política CORS (`grep` sin resultados para `Cors`/`CORS`), consistente con que Core es una librería de dominio, no el host HTTP.
- No existe otro proyecto/host en el monorepo que sirva HTTP público adicional (docs-site no fue inspeccionado para este punto porque no forma parte del alcance de componentes reales de la aplicación evaluados en fichas previas; se deja como límite de cobertura).
- Alcance no inspeccionado: configuración de hosting/reverse proxy (IIS, gateway) que pudiera agregar o sobrescribir headers CORS fuera del repo; comportamiento real del navegador y del middleware en runtime; verificación de que el binario desplegado corresponde exactamente a este código fuente.

## Resultado por componente y conclusión

- **API (`api-admisiones`)**: la política CORS efectiva en el código fuente cumple la letra del requisito — valor fijo/allowlist explícita, sin `AllowAnyOrigin()` productivo, sin reflejo sin validar del header `Origin`, y sin escenario de `*` combinado con datos sensibles. Esta conclusión es NEEDS_REVIEW y no PASS porque (a) es una revisión estática de IA sin evidencia runtime reproducible, según ADR-002, y (b) la suite de tests existente no verifica realmente el contenido de la política (hallazgo 1), por lo que no hay una red de seguridad automatizada que sostenga que este comportamiento se mantiene ante cambios futuros.
- **Core**: no aplica; no emite CORS. No contradice ni aporta al resultado del componente API.
- **Frontend**: no aplica como emisor; su consumo (`withCredentials`) es consistente con la necesidad de `AllowCredentials()` en la API, sin evidencia de conflicto.
- **Conclusión global**: el diseño actual, leído en código fuente, no presenta el defecto que el requisito busca prevenir. No se puede afirmar PASS del requisito compartido completo sin (i) confirmar el comportamentamiento runtime del header en al menos un entorno real, y (ii) cerrar el gap de cobertura de test descrito en el hallazgo 1, que es lo que permitiría detectar una regresión futura hacia `AllowAnyOrigin()` u orígenes no autorizados.

## Hallazgos y propuesta documental

1. **Tests de CORS sin verificación real de contenido (deuda de cobertura, no defecto de producción).**
   - Condición concreta: `ServiceCollectionExtensionsTests.cs:208-296` declara variables `expected*Origins` con dominios (`gestion.ort.edu.uy`, `funcionarios.ort.edu.uy`, etc.) que no coinciden con `allowedOrigins` real, y cada test solo hace `Assert.NotEmpty(services)`, que es verdadero para cualquier configuración de CORS, incluida una rota o abierta a `*`.
   - Impacto: si un cambio futuro (accidental o malicioso) reemplaza `WithOrigins(allowedOrigins)` por `AllowAnyOrigin()`, quita `AllowCredentials()` sin ajustar el frontend, o borra un origen de producción, esta suite seguiría en verde. No hay evidencia de que el defecto exista hoy; el hallazgo es sobre la ausencia de una salvaguarda automatizada.
   - Evidencia: E5.
   - Responsable candidato: equipo API (`api-admisiones`).
   - Propuesta de cambio: reescribir los tests para resolver la política real desde `IOptions<CorsOptions>` o `ICorsPolicyProvider` y comparar el conjunto exacto de orígenes, métodos y `AllowCredentials` esperado, en vez de `Assert.NotEmpty`.
   - Validación futura: ejecutar la suite corregida y confirmar que falla si se introduce `AllowAnyOrigin()` o se elimina un origen de la allowlist real, antes de considerar el gap cerrado.

2. **Gobernanza no confirmada de `AllowCredentials()` (contexto externo, no hallazgo nuevo de código).**
   - Condición concreta: ADR-009 (estado `draft`) documenta una reversión sin explicación de `DisallowCredentials()` a `AllowCredentials()` en mayo 2026 y pide confirmar el estado vigente en producción.
   - Impacto: no hay indicio de que la configuración actual (E1) sea insegura — `WithOrigins()+AllowCredentials()` es una combinación válida y no genera `*`—, pero el propio equipo no ha cerrado esa validación de proceso.
   - Evidencia: E6.
   - Responsable candidato: propietario del ADR (`rubino-f` según metadata) y equipo API.
   - Propuesta de cambio: ninguna sobre código; se sugiere que la confirmación pendiente en ADR-009 se resuelva antes de promoverlo a `accepted`, sin que esto bloquee el resultado de este punto.
   - Validación futura: seguimiento del propio ADR-009, no de esta ficha.

No se atribuyen vulnerabilidades confirmadas; ambos puntos son deuda/gaps de proceso, no defectos verificados del comportamiento CORS actual.
