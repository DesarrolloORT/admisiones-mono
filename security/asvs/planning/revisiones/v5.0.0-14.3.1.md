# v5.0.0-14.3.1 — Limpieza de datos autenticados del cliente

## Identificación

- **ID y nivel mínimo:** v5.0.0-14.3.1, L1.
- **Texto oficial:** "Verify that authenticated data is cleared from client storage, such as the browser DOM, after the client or session is terminated. The 'Clear-Site-Data' HTTP response header field may be able to help with this but the client-side should also be able to clear up if the server connection is not available when the session is terminated."
- **Interpretación local:** al terminar la sesión explícitamente, por expiración o por fallo de renovación, el cliente debe eliminar de DOM, memoria y almacenamiento del navegador los datos vinculados a la persona autenticada. La limpieza no puede depender exclusivamente de que el `POST /auth/logout` llegue al servidor.
- **Pregunta:** ¿el frontend elimina los datos autenticados de memoria y de todos los mecanismos de almacenamiento del navegador cuando finaliza la sesión?
- **Avance documental:** DOCUMENTADO.
- **Resultado de seguridad:** FAIL.
- **Fecha de revisión:** 2026-09-24; actualización: 2026-10-23.

## Aplicabilidad y alcance

Aplica al frontend Angular: la sesión usa cookies HTTP-only gestionadas por la API y conserva estado de usuario en memoria; además el flujo de inscripciones persiste en `sessionStorage` identificadores obtenidos durante navegación autenticada. La API participa porque borra las cookies y, desde esta actualización, revoca el refresh token al recibir logout.

No se evaluaron runtime, DOM efectivo tras navegación, IndexedDB/caches de navegador, service workers, extensiones, proxy/CDN ni headers HTTP de ambientes desplegados. El inventario estático del frontend (ref `86979de2`) no halló uso propio de IndexedDB. La telemetría también usa `sessionStorage` para identificador de sesión y traza de rutas; no se clasificó como dato autenticado con la evidencia disponible.

## Resultado por componente y conclusión

- **Frontend: FAIL.** Según la evidencia de `86979de2` (no re-verificada), hay limpieza resiliente del estado de autenticación en memoria, pero el flujo autenticado conserva en `sessionStorage` IDs de inscripciones y no hay llamada de logout, expiración o fallo de refresh que los elimine. Esto contradice el requisito de limpiar datos autenticados del almacenamiento del cliente al terminar la sesión.
- **API: evidencia parcial.** El logout borra cookies y ahora revoca el refresh token, lo que mejora la terminación de sesión, pero no puede limpiar `sessionStorage` y sigue sin emitir `Clear-Site-Data`.
- **Core: fuera del flujo inspeccionado.**

La conclusión es FAIL por la evidencia estática concreta de persistencia del contexto de reanudación. No se afirma que todos los demás datos del cliente estén correctamente inventariados o limpiados: faltan verificaciones de runtime y de infraestructura, y una re-verificación del frontend.

## Hallazgos y propuesta documental

1. **Contexto de reanudación persiste tras el cierre de sesión** (abierto según la última evidencia del frontend, `86979de2`).
   - Condición e impacto: `inscription-resume-context` contiene IDs ligados a una sesión autenticada y continúa disponible en la pestaña después de logout, expiración o caída de red; puede revelar contexto del flujo al siguiente usuario de ese perfil del navegador.
   - Evidencia: E1-E4.
   - Responsable candidato: frontend `admisiones`; coordinación con API para cobertura de cookies/headers.
   - Propuesta para una fase de fixes: centralizar una rutina de cierre de sesión que invoque la limpieza del contexto de reanudación y de cualquier store autenticado; cubrir logout exitoso, fallo de red y expiración. Evaluar `Clear-Site-Data: "storage"` (y eventualmente `"cache"`) en la respuesta de `POST /auth/logout` como defensa complementaria sin sustituir la limpieza local.
   - Validación futura: prueba de navegador que siembre el contexto, ejecute cada terminación de sesión y confirme la ausencia de las claves, del DOM protegido y de cookies; inspeccionar headers de ambiente real.

No se distribuyó propuesta a las ramas `fix/owasp`: esta sesión no modifica código, no se verificó un worktree aplicable y la propuesta queda centralizada aquí.

## Pendientes y dependencias

- El equipo frontend debe aportar o ejecutar pruebas de navegador para logout, refresh fallido y 401, comprobando `sessionStorage`, `localStorage`, IndexedDB, Cache Storage, DOM y navegación; y re-verificar E1-E5 contra una ref posterior a `86979de2`.
- El equipo de plataforma/API debe aportar una captura HTTP del logout en cada ambiente y confirmar si proxy/CDN agrega `Clear-Site-Data` u otro mecanismo de limpieza; no se infiere desde el código.
- El equipo funcional debe clasificar los datos de telemetría persistidos en `sessionStorage` y confirmar si el `sessionId` o la traza de rutas deben limpiarse junto con la sesión.
- La remediación debe inventariar todos los stores de features antes de declarar PASS; este punto se relaciona con v5.0.0-14.3.2 y v5.0.0-14.3.3 (L2), sin adelantarlos. La revocación del refresh en logout (E7) es insumo para [v5.0.0-7.4.1](./v5.0.0-7.4.1.md), que la auditoría del 2026-10-22 señala como desactualizada.
