## Aplicabilidad y alcance

- **API (`api-admisiones`)**: componente principal. Genera respuestas JSON de negocio (`OperationResult<T>` vía `ObjectResult`/`[ApiController]`), un único sink de bytes top-level (`PersonController.GetPersonPhoto` → `image/jpeg`), y dos middlewares que escriben el cuerpo de la respuesta directamente (`ExceptionHandlingMiddleware`, `ModelBindingErrorLoggingMiddleware`).
- **Core**: no expone HTTP propio (confirmado en fichas 3.5.2/3.5.3: sin controladores, sin acciones HTTP). Se excluye de la aplicabilidad directa; sólo aporta datos que la API serializa.
- **Frontend (`admisiones/`)**: SPA Angular sin servidor de aplicación propio; no genera respuestas HTTP dinámicas. El único punto donde el requisito aplicaría es el hosting estático (IIS/`web.config`), cuya configuración de `mimeMap` no está versionada en el repo — ya señalado como límite en la ficha 3.4.1. Se excluye de la evidencia reproducible por ese motivo, sin negar aplicabilidad.
- **API de pagos y Azure (servicios externos)**: fuera de alcance; no se controla su código.
- **`AppLogic.Scholarships.Services.ScholarshipFundService`** (con su propio `GetContentType(extension)`): tiene lógica de content-type pero **no está conectado a ningún controlador HTTP** en esta ref (ninguna coincidencia de `ScholarshipFundService`/`FileDownload` fuera de su propio módulo, tests y DI). No es un sink de respuesta real hoy; se documenta como hallazgo de deuda, no de aplicabilidad.

## Resultado por componente y conclusión

- **API — camino estándar (`ObjectResult`/`ActionResult<T>` vía `[ApiController]` + `ProducesAttribute`)**: el `Content-Type` con `charset` queda garantizado por el formateador por defecto de ASP.NET Core (E1). Sin evidencia de defecto.
- **API — `GetPersonPhoto`**: `Content-Type: image/jpeg` fijo por constante de servidor; consistente con el requisito salvo por la deuda ya documentada en 3.2.1 sobre no revalidar el tipo real del archivo (no se abre un hallazgo nuevo; se referencia como dependencia).
- **API — `ExceptionHandlingMiddleware`**: pese a fijar `ContentType` sin charset explícitamente, el comportamiint documentado por su propio test (no ejecutado) muestra que `WriteAsJsonAsync` corrige el valor final a `"application/json; charset=utf-8"`, coincidente con el cuerpo JSON real. Sin defecto confirmado, sujeto a validación runtime.
- **API — `ModelBindingErrorLoggingMiddleware` (400 transformados)**: **hallazgo concreto** (E6/E7/E8): quien sustituye el cuerpo por un `OperationResult` no toca el header, dejando potencialmente un `Content-Type: application/problem+json; charset=utf-8` (u otro valor heredado del pipeline anterior) sobre un cuerpo que ya no es un documento Problem Details ni corresponde a ese media type específico. Esto es exactamente la condición que 4.1.1 busca prevenir. No se puede afirmar FAIL determinístico sin observar el header real en runtime (ADR-002: sin evidencia reproducible no hay FAIL), por lo que el resultado queda en **NEEDS_REVIEW** con hallazgo documentado, no en PASS.
- **Frontend / hosting estático**: sin control propio versionado; no aporta evidencia a favor ni en contra.
- **Core**: no aplica (sin HTTP propio).

Conclusión global: el requisito **no está demostrado como cumplido** de forma completa y reproducible. El camino dominante (formateador JSON estándar) está bien resuelto por diseño de framework; el camino de reescritura de 400 (`ModelBindingErrorLoggingMiddleware`) tiene una inconsistencia de diseño real entre header y cuerpo que ningún test cubre, y que sólo runtime puede confirmar con certeza absoluta sobre el valor efectivo del header heredado.

## Hallazgos y propuesta documental

### Hallazgo 1 (API) — Content-Type no actualizado al reescribir el cuerpo de respuestas 400

- **Condición concreta**: `ModelBindingErrorLoggingMiddleware.HandleBadRequestProductionLikeAsync` y `HandleBadRequestDevelopmentAsync` (`Security/Middleware/ModelBindingErrorLoggingMiddleware.cs:157-204`) reemplazan los bytes del cuerpo de toda respuesta con `StatusCode == 400` que no tenga ya forma de `OperationResult`, pero nunca asignan `context.Response.ContentType` antes de escribir los nuevos bytes.
- **Impacto**: el cliente puede recibir un header `Content-Type` que no describe el cuerpo real (p. ej. `application/problem+json; charset=utf-8` sobre un `OperationResult` JSON simple), lo que viola literalmente el texto del requisito 4.1.1 y puede confundir a clientes que negocian/parsean por `Content-Type` (p. ej. librerías HTTP que eligen el deserializador según el media type).
- **Evidencia**: E6, E7, E8.
- **Responsable candidato**: equipo de `api-admisiones` (dueño de `Security/Middleware`).
- **Propuesta de cambio** (documental, no aplicada en esta fase): antes de escribir `bytes` en ambos métodos (`HandleBadRequestProductionLikeAsync` línea ~174 y `HandleBadRequestDevelopmentAsync` línea ~202), fijar explícitamente `context.Response.ContentType = "application/json; charset=utf-8"` (o reutilizar `MediaTypeNames.Application.Json` + `Encoding.UTF8.WebName`), ya que el cuerpo escrito siempre es un `OperationResult` serializado con `JsonSerializer.Serialize` en UTF-8.
- **Validación futura**: agregar assert de `context.Response.ContentType` en los tests existentes que ya cubren estos branches (`ModelBindingErrorLoggingMiddlewareTests.cs`, casos de las líneas 100-328), y confirmar en runtime (captura de tráfico o test de integración) el valor real heredado del pipeline en al menos un caso de `ValidationProblemDetails` automático de `[ApiController]`.

### Hallazgo 2 (deuda, no nuevo defecto) — `GetPersonPhoto` no revalida el tipo real del archivo

- Ya documentado como hallazgo de deuda en la ficha `v5.0.0-3.2.1.md` (mismo código, mismo símbolo `PersonController.GetPersonPhoto`). No se abre un hallazgo separado; se referencia como dependencia porque también es relevante para "Content-Type debe coincidir con el contenido real".
