## Aplicabilidad y alcance

Se incluyen login directo, login con 2FA, renovación por refresh y establecimiento de contraseña inicial, porque todos terminan emitiendo el par access/refresh. El navegador recibe cookies HttpOnly, pero la API también acepta el access JWT anterior por `Authorization: Bearer`. El límite de confianza decisivo es la validación de sesión en la API, no el estado local del frontend. Core fijado no participa en la emisión observada. No se inventariaron clientes alternativos, otros servicios consumidores de Core, proxies ni mecanismos de revocación fuera del repositorio.

## Resultado por componente y conclusión

- API: el refresh de referencia se reemplaza en la fila de persona/sistema; una vez persistido, la consulta del hash anterior no debería encontrarlo. El access JWT autocontenido anterior continúa verificándose por firma y expiración porque no hay comprobación de revocación en el validador leído. Esto incumple la terminación del token actual cuando se emite una nueva sesión. Además, el generador no garantiza un JWT de acceso distinto en emisiones próximas.
- Frontend: reemplaza cookies por respuesta y limpia su estado al salir; no puede invalidar copias de JWT ya emitidas. Core: no se identificó participación directa en el mecanismo examinado.

Resultado global: **DOCUMENTADO / FAIL** por la falta de terminación del access token anterior en el código de autenticación evaluado. No se afirma uso indebido observado ni se extiende la conclusión a infraestructura no inspeccionada.

## Hallazgos y propuesta documental

- **JWT previo permanece aceptable tras autenticación nueva.** Condición: una nueva emisión sustituye el refresh persistido y las cookies del cliente, pero el validador de access JWT no consulta un estado de revocación. Impacto: quien conserve un JWT anterior puede seguir presentándolo hasta su expiración configurada, incluso después de un nuevo login del titular. Evidencia: E1–E6. Responsable candidato: API. Propuesta futura: definir una versión de sesión o fecha mínima por persona, o registro de tokens terminados, y comprobarla en la validación de cada access JWT; rotar el identificador de sesión al autenticar y reautenticar. Decidir el alcance de sesiones paralelas y probar atomicidad con Oracle antes de implementar. Validar con dos clientes de prueba: tras login/2FA/refresh, el token anterior debe recibir 401 y el nuevo debe funcionar.
- **Distinción del nuevo JWT no garantizada.** Condición: el emisor carece de identificador o nonce explícito por sesión. Impacto: emisiones próximas para la misma persona podrían generar el mismo texto, frustrando una rotación observable. Evidencia: E5. Responsable candidato: API. Propuesta futura: incorporar identificador único y cubrir la emisión cercana con una prueba determinista. La coincidencia concreta no fue reproducida en esta revisión.

No se distribuyó propuesta a un repo responsable: no se comprobó disponibilidad de un worktree externo `fix/owasp`. Queda aquí para una fase posterior autorizada.
