## Aplicabilidad y alcance

El requisito es condicional: sólo aplica a un authorization server OAuth. La API expone autenticación propia por LDAP, 2FA, cookies HttpOnly, refresh token y JWT; el frontend consume esas rutas con credenciales de cookie. No se encontró endpoint de autorización, token endpoint OAuth, registro de clientes, `redirect_uri`, `response_type`, `client_id`, ni dependencias de servidor OAuth/OIDC en API, frontend o el Core fijado.

La única coincidencia OAuth fue una documentación de token JWT saliente para una API externa, que lo llama “OAuth 2.0 Client Credentials Flow (simplificado)”. El código correspondiente sólo genera un JWT de servicio para una audiencia dada; no procesa un navegador, una respuesta de autorización ni una URI de redirección. Por tanto no convierte a este monorepo en authorization server.

No se evaluó la API externa de Inscripciones y Pagos ni infraestructura o proveedores de identidad fuera de estos repositorios. Si alguno opera un authorization server para la aplicación, este resultado no lo cubre.

- **API:** NOT_APPLICABLE. Actúa como autenticador y emisor/validador de JWT propios, no como authorization server OAuth que redirige al navegador hacia clientes registrados.

- **Core:** NOT_APPLICABLE dentro del alcance de la búsqueda de inventario; no se localizó un componente OAuth/OIDC en la versión fijada.

La conclusión DOCUMENTADO / NOT_APPLICABLE se limita al monorepo: no existe un authorization server OAuth bajo inspección al que exigir la allowlist de redirect URI. No se ejecutaron tests, builds, runtime, escaneos ni cambios de código/configuración.
