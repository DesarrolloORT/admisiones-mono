## Aplicabilidad y alcance

El refresh token referencia una sesión autenticada: la API compara su hash con Oracle. El `sessionId` de 2FA referencia en Redis una sesión temporal de una persona después del primer factor. Permite recuperar ese estado y reenviar el código; para emitir la sesión autenticada se exige además el código correcto. Se incluye como sesión parcial, sin equipararlo a un token de acceso suficiente por sí mismo.

Los JWT de acceso y de activación/establecimiento de contraseña (incluido el del link del backoffice) son autocontenidos y no se evalúan contra el mínimo de entropía de referencias de este punto. El `flowId` del registro (`X-Flow-Id`) no representa una sesión de usuario autenticada y no se evaluó aquí. El frontend transporta `sessionId` y cookies; no genera esas referencias. No se inventariaron clientes alternativos, otros emisores de Core, integraciones externas ni sesiones del despliegue.

## Resultado por componente y conclusión

- API, refresh: el código usa 64 bytes de CSPRNG para la referencia. Su espacio de valores supera el mínimo; no se verificó persistencia ni unicidad observada en despliegue.
- API, 2FA: la referencia temporal sigue identificada con GUID v4, que aporta como máximo 122 bits. El incumplimiento del umbral de 128 es demostrable por diseño. No se observó una colisión Redis.
- Frontend: transporta la referencia emitida por la API (no re-verificado). Core fijado: no se localizó otro emisor de referencia en el alcance acotado.

Resultado global: **DOCUMENTADO / FAIL** por la referencia de sesión parcial 2FA. No se atribuye una toma de cuenta ni se afirma que el `sessionId` evite el segundo factor. La cobertura de emisores y el comportamiento en runtime quedan pendientes.

## Hallazgos y propuesta documental

- **Referencia 2FA por debajo del mínimo (vigente en `912fc665`).** Condición: `Guid.NewGuid()` produce un UUID v4 con como máximo 122 bits de entropía, usado como `sessionId` de una sesión temporal de persona en Redis. Impacto: incumple el margen exigido para referencias de sesión; una colisión teórica podría sobrescribir otra sesión porque el guardado usa `SET`. Evidencia: E3–E4. Responsable candidato: API. Propuesta futura: generar la referencia con al menos 16 bytes de `RandomNumberGenerator`, codificarla sin pérdida y evaluar escritura Redis sin sobrescritura con reintento ante colisión. Validar longitud, unicidad de una muestra controlada, TTL y flujo de verificación/reenvío. Esto no sustituye el código 2FA ni demuestra explotación actual.

No se distribuyó propuesta a un repo responsable: no se comprobó un worktree `fix/owasp` externo disponible. Queda en esta ficha para una fase autorizada posterior.
