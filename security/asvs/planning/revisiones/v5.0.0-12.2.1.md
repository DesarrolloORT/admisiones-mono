- **ID y nivel mínimo:** v5.0.0-12.2.1 (L1).

- **Interpretación local:** los navegadores que usan Admisiones deben conectarse por TLS a la API pública, al hosting y a cualquier pasarela HTTP externa a la que la aplicación los dirija; no debe existir una ruta aceptada que permita degradar a HTTP.

- **Fecha de revisión:** 2026-09-23.

## Aplicabilidad y alcance

Aplica a frontend y API. El frontend consume la API configurada y, en los pagos Banred, Geopay y Sistarbanc, recibe una URL de pago y publica un formulario del navegador hacia el servicio externo. Ese último tramo es conectividad cliente–servicio HTTP expuesto externamente y está dentro del requisito.

La API aporta el `paymentUrl` al contrato público y configura su propio pipeline HTTPS. Los HTTP configurados para LDAP, OTLP e Inscripciones/Pagos son conexiones servidor–servicio; se registran como límite y dependencia de V12.3, sin transferirlos como conclusión de este requisito. Core no participa directamente en el flujo de navegador revisado.

No se inspeccionó configuración efectiva de CDN, proxy, balanceador, hosting Angular, DNS ni las pasarelas de pago. Tampoco se ejecutaron navegador, API, pruebas, builds, scans ni handshakes.

## Resultado por componente y conclusión

- **Frontend — FAIL.** `ExternalPaymentSubmitter.toHttpUrl` permite `http:` y publica mediante `form.submit()` el campo `parametrosEncriptados` a ese destino. El flujo es alcanzable desde la respuesta pública `start-payment`; no hay una barrera de esquema HTTPS antes de la conexión del navegador.
- **API — FAIL como frontera que propaga el flujo.** La API separa y devuelve la URL recibida de Inscripciones/Pagos sin exigir HTTPS. Esto permite que un valor HTTP llegue al frontend; no se infiere que una pasarela concreta lo esté haciendo actualmente.
- **Hosting/TLS de API — NEEDS_REVIEW.** La configuración de código aporta redirección/HSTS y TLS de Kestrel, pero falta evidencia determinística del endpoint público y de su cadena proxy/hosting.
- **Core — sin evidencia directa aplicable al flujo de navegador.** Se fija la ref consumida sin atribuirle un resultado positivo.

**Conclusión: FAIL.** Aunque el origen de API observado en el frontend es HTTPS y la API incluye defensas TLS, el flujo de pasarela externa acepta y puede publicar a HTTP. El requisito exige que toda conectividad cliente–servicio HTTP expuesto externamente use TLS y no haga fallback inseguro; la aceptación explícita de HTTP contradice esa condición.

## Hallazgos y propuesta documental

1. **Condición:** el cliente acepta `paymentUrl` con esquema HTTP y remite el formulario con `encryptedParameters`; la API también propaga la URL sin validarla.
   - **Impacto:** si la integración o una respuesta aguas arriba entrega HTTP, el navegador puede transmitir el blob de pago sin TLS y quedar expuesto a observación o modificación en tránsito.
   - **Evidencia:** E4 y E5.
   - **Responsables candidatos:** frontend `admisiones` y API `api-admisiones`; confirmar con el dueño de Inscripciones/Pagos y cada pasarela.
   - **Propuesta para una fase de fixes:** exigir HTTPS tanto en la validación de URL del frontend como en la frontera API antes de devolver `PaymentUrl`; añadir pruebas de rechazo de HTTP y mantener un inventario allowlist de hosts de pasarela si el diseño lo requiere.
   - **Validación futura:** prueba unitaria y de contrato con `http://` rechazado; prueba de integración/navegador que confirme que cada método de pago usa HTTPS y que no se envía el formulario ante HTTP.

No se aplicó ningún fix ni se creó una copia distribuida de propuesta: los worktrees `fix/owasp` no fueron verificados ni modificados en esta iteración.
