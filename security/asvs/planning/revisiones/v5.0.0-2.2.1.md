# v5.0.0-2.2.1 — Validación positiva de entradas

## Identificación

- ID: v5.0.0-2.2.1. Nivel mínimo: L1.
- Sección oficial: V2.2, Input Validation (ordinal 1 de la sección; capítulo V2 Validation and Business Logic).
- Texto oficial íntegro: Verify that input is validated to enforce business or functional expectations for that input. This should either use positive validation against an allow list of values, patterns, and ranges, or be based on comparing the input to an expected structure and logical limits according to predefined rules. For L1, this can focus on input which is used to make specific business or security decisions. For L2 and up, this should apply to all input.
- Interpretación local / pregunta: para las entradas que deciden negocio o seguridad (tipo y número de documento, archivos adjuntos, identificadores y flags de flujo), ¿el servidor aplica validación positiva —allowlist, patrón, rango o estructura esperada— antes de usarlas?
- Alcance L1 acotado explícitamente por el texto oficial a las entradas que sustentan decisiones concretas; la cobertura de *toda* entrada corresponde al mismo requisito en L2 y no se evalúa aquí.
- Avance documental: DOCUMENTADO. Resultado de seguridad: NEEDS_REVIEW (sin cambio).
- Fecha de revisión: 2026-09-17; actualización: 2026-10-23. Contexto: [ITERACION.md](../ITERACION.md), plan [API](../api-admisiones.md); ficha previa [2.1.1](./v5.0.0-2.1.1.md) (documentación de las reglas) y [1.3.1](./v5.0.0-1.3.1.md) (sanitización); [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md).

## Aplicabilidad y alcance

Aplicable a la API: es la capa que recibe las entradas y toma las decisiones. Se delimitaron como «entradas que deciden negocio o seguridad» en el alcance L1:

1. **Tipo y número de documento**: decide la rama del registro (persona existente, persona nueva o solicitud de alta), la autenticación LDAP, la recuperación de password y las claves de rate limiting y de caché.
2. **Archivos adjuntos** (documento de identidad, foto, declaración jurada y comprobantes de becas): desde `90ccee3d` llegan como `multipart/form-data` con `IFormFile`; alimentan el reconocimiento con Azure Document Intelligence y la persistencia.
3. **Identificadores y campos de perfil** que llegan al alta de persona (fechas, sexo, IDs de catálogo).
4. **Cabecera `X-Flow-Id`** que sostiene la sesión del flujo de registro.

Excluido de esta iteración, no de la aplicabilidad: frontend (2.2.2 cubre la no-dependencia del cliente), inventario campo a campo de todos los endpoints (mismo ID en L2), catálogos/becas/encuestas campo a campo, y las respuestas de integraciones externas (pagos, Tivenos, Azure Document Intelligence). No se evaluó la validación efectiva en runtime ni la respuesta real ante entradas hostiles.

## Resultado por componente y conclusión

- **API — NEEDS_REVIEW.** Validación positiva real y consistente sobre la entrada más crítica: allowlist cerrada de tipo de documento en todos los casos de uso que deciden autenticación, recuperación, encuesta y rama del registro, con el tipo exigido por rama (E5, E6); patrón/rango en el alta de persona (E8); estado del flujo en los endpoints públicos (E11); y, con la migración a multipart, validación por magic bytes y tamaño en **todas** las rutas de subida más un tope global de body (E9, E14, E15). En contra, sin cambios: la capa central de validación estructural sigue registrada sin cubrir ningún endpoint existente (E2–E4), y el número de documento para DE/PS/CC no tiene estructura, largo ni conjunto de caracteres definidos (E5, E7).
- **Core — fuera de la cadena.** La validación de archivos y de cédula que antes se evaluaba en Core se trasladó a la API (E5, E9). Core deja de aportar evidencia para este requisito.
- **Frontend — no evaluado** en esta ficha; su papel corresponde a 2.2.2.
- **Global: DOCUMENTADO / NEEDS_REVIEW**, conforme [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md): toda la evidencia es lectura estática. No alcanza para PASS. Tampoco se declara FAIL global: el hallazgo 1 describe un control inoperante, no una ausencia total de validación, porque las reglas de dominio cubren la entrada que el nivel L1 señala.

## Hallazgos y propuesta documental

1. **La validación por JSON Schema está registrada pero no se aplica a ningún endpoint.** Sigue abierto en `912fc665`. Condición: `InMemoryJsonSchemaRegistry` carga una única clave, `POST /api/datospersonales`, ruta inexistente (E3, E4). `JsonSchemaValidationFilter` aporta en la práctica sólo `Accept` y `Content-Type`; desde `90ccee3d` además acepta `multipart/form-data` y nunca valida esos bodies por esquema (E2). Impacto candidato: un control de seguridad declarado no produce efecto y quien lea el arranque puede asumir cobertura estructural inexistente. Severidad no definitiva: sólo inoperancia del control. El único esquema sigue derivado con `JsonSchema.FromSampleJson`. Responsable candidato: API (plataforma/seguridad). Propuesta futura: (a) poblar el registry con esquemas escritos a mano para los endpoints JSON públicos, partiendo de `Docs/contracts/`, o (b) retirar el filtro de esquema (conservando la parte de media types) y documentar que la validación estructural vive en DTO/casos de uso. Validación futura: test de integración con body que viole el esquema contra un endpoint real, y chequeo de arranque que falle si una clave del registry no corresponde a una ruta.
2. **El número de documento no tiene validación positiva para DE/PS/CC.** Sigue abierto. Condición: `ValidateBaseDocument` valida el tipo y el número sólo si es CI; para DE, PS y CC cualquier cadena no vacía es aceptada (E5) y los DTO aportan sólo `[Required]` (E7). Ese valor se usa para autenticar contra LDAP, consultar el padrón, crear solicitudes de alta y componer claves de rate limiting (`TextNormalization.NormalizeDocumentForKey`) y de `RedisPendingPersonStore`. Atenuante nuevo: la clave de la caché de imágenes ahora es `SHA256(tipo:documento)` (`62effb5d`), así que ahí el largo ya no llega a la clave; el resto de los consumidores no cambió. **No se confirma vulnerabilidad**: no se evaluó el comportamiento de los consumidores ante valores desmesurados ni se ejecutó ninguna prueba. Responsable candidato: API Identity/Registration, con dominio para definir los formatos. Propuesta futura: acordar y documentar largo máximo, conjunto de caracteres y estructura por tipo —sin inventar reglas de pasaporte— y aplicarla en `IdentityDocumentRules.ValidateBaseDocument`, el punto único por el que ya pasan todos los casos de uso. Validación futura: casos positivos y negativos por tipo, ejecutados sobre la misma ref.
3. **La comprobación del hash de la fuente ASVS falla en checkouts Windows.** Sigue abierto: [ITERACION.md](../ITERACION.md) no se modificó. Condición: `core.autocrlf=true` convierte el JSON al extraerlo, de modo que el hash sobre el archivo en disco no reproduce el oficial aunque el contenido versionado sea idéntico. Propuesta documental: fijar en ITERACION.md que la verificación se hace sobre el blob o sobre el archivo normalizado a LF; alternativa en fase autorizada: `.gitattributes` que marque el JSON como binario.

Propuestas distribuidas a los repos responsables: **ninguna**. Distribución pendiente, registrada aquí.
