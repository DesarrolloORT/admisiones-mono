## Aplicabilidad y alcance

Incluidos: texto y atributos HTML del frontend (sin re-verificar), formulario DOM de pagos, salidas HTTP de la API (cuerpos JSON, headers de seguridad, rate limit, cookies, Content-Disposition y Content-Type de descargas) y el correo HTML, que ahora renderiza un worker externo.

Cambios de alcance en 912fc665:
- La API no construye HTML ni XML de correo. Publica contratos ORT.Messaging a Service Bus y el worker los renderiza con Razor (TemplatesORT). El contexto HTML del correo sale del repo evaluado; el envelope SOAP de Core/MailORT ya no se usa.
- Aparecen endpoints de descarga de archivos con nombre en Content-Disposition (material de estudio ZIP, documento de DJ, comprobante de ingresos) y un mapeo `.html → text/html` en AffidavitFileService.
- Kestrel sin header Server (KestrelExtensions) y headers de seguridad globales con CSP.

Búsqueda en la API vigente: File(, Content-Disposition, Response.Headers, Cookies.Append, Redirect(, ContentResult/Content(, WriteAsJsonAsync, JsonSerializer.Serialize y text/html. No se localizó construcción manual de HTML/XML en WebApiAdmisiones/AppLogic. Límites: renderizador Angular y componentes ORT, worker de correo, paquetes ORT.*, hosting/proxy efectivo y PDF generado con PDFsharp-MigraDoc (no inspeccionado). URLs y JSON/JS quedan para 1.2.2/1.2.3.

## Resultado por componente y conclusión

- Frontend: NEEDS_REVIEW (sin re-verificar). Faltan el renderizador real y getBankSvg/OrtIcon.
- API: NEEDS_REVIEW. No construye HTML/XML; los headers dinámicos son numéricos o los arma el framework. El correo delega la codificación contextual al worker (no verificado), y las descargas nuevas agregan Content-Disposition/Content-Type a verificar en runtime.
- Core: NEEDS_REVIEW acotado. Ningún contexto HTML/XML/HTTP de Core está en el flujo vigente de la API.

DOCUMENTADO / NEEDS_REVIEW conforme a [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md). No hay evidencia determinística suficiente para PASS/FAIL ni vulnerabilidad confirmada.

## Hallazgos y propuesta documental

1. **Contrato HTML compartido de Core (E4–E6 anteriores).** Resuelto en 912fc665 para la API: ya no usa los helpers de Core/MailORT ni arma HTML (7e749347, 5a405230). Queda vigente para otros consumidores de Core, a cargo de su responsable. Se reemplaza por el hallazgo 3.
2. **Delegación SVG sin cobertura (E2).** Vigente (frontend sin re-verificar). Responsable candidato: frontend y librería ORT.
3. **Nuevo — codificación contextual del correo en un worker externo (E4–E5).** El HTML (texto y href con FirstName/URL) se genera fuera del repo evaluado. Responsable candidato: dueño del worker/TemplatesORT. Aportar la ref de las plantillas, confirmar que no usan salida cruda para esos campos y obtener un correo renderizado con datos sintéticos (<, >, &, comillas).
4. **Nuevo — Content-Type derivado de una extensión persistida (E10).** El mapeo `.html → text/html` permitiría servir un adjunto legacy como HTML. Con attachment + nosniff el riesgo es bajo, pero depende del cliente. Responsable candidato: API. Propuesta futura: limitar el mapeo de descarga a los tipos que hoy acepta la subida y usar application/octet-stream para el resto, o justificar el caso legacy. Validar con un registro sintético con extensión .html.

Propuestas conservadas en esta ficha central; no se distribuyeron a otros repos. No se aplicaron fixes.
