## Aplicabilidad y alcance

Aplica a la API ASP.NET Core, que configura Kestrel y recibe tráfico HTTPS, y al frontend, cuyo origen de API configurado usa HTTPS y cuyo hosting es una terminación TLS independiente. También aplica a los reverse proxies, balanceadores, CDN, IIS o plataforma que pudieran terminar TLS antes de Kestrel; ninguno está versionado en este árbol.

El alcance cubre el arranque, pipeline y configuración versionada de la API, la configuración fuente del frontend y el inventario de manifiestos de despliegue. No cubre certificados, listeners y políticas efectivas de cada ambiente, negociación con clientes, orden de preferencia observado, configuraciones del sistema operativo/contenedor ni servicios externos. Las URL HTTP de LDAP, OTLP y algunos servicios internos observadas en `appsettings*` son relevantes para V12.2/V12.3, pero no determinan qué versiones TLS se habilitan en el servidor bajo este requisito.

## Resultado por componente y conclusión

- **API — NEEDS_REVIEW:** la configuración fuente de Kestrel está alineada con TLS 1.2 y TLS 1.3, y el pipeline fuerza HTTPS a nivel de aplicación. Falta evidencia determinística de los listeners activos, las terminaciones TLS previas y la preferencia real de TLS 1.3 por ambiente.
- **Frontend — NEEDS_REVIEW:** el consumidor configura un origen API HTTPS, pero el repositorio no contiene la configuración de la terminación TLS que sirve su aplicación ni una prueba de protocolo contra el sitio publicado. Evidencia no re-verificada en esta actualización.
- **Core — NEEDS_REVIEW:** no se identificó una terminación TLS propia; sus consumidores y conexiones salientes se revisarán en los requisitos de comunicación correspondientes. Esto no acredita el control compartido de los bordes públicos.

La conclusión global es **NEEDS_REVIEW**, de acuerdo con ADR-002: la evidencia estática sustenta una restricción de Kestrel, pero no verifica de forma reproducible todas las superficies TLS ni la preferencia efectiva de TLS 1.3.

## Hallazgos y propuesta documental

No se confirma un protocolo TLS obsoleto habilitado en el código propio inspeccionado. Se registra una brecha de evidencia: no hay configuración de reverse proxy/hosting ni resultados de handshake por ambiente en el monorepo, por lo cual un cambio externo podría habilitar TLS 1.0/1.1 o impedir la preferencia de TLS 1.3 sin que E1 lo detecte. Responsable candidato: plataforma/infraestructura, en coordinación con API y frontend. En una fase posterior, inventariar todas las terminaciones TLS, fijar explícitamente la política donde corresponda y validar con clientes que ofrezcan TLS 1.2 y TLS 1.3. No se aplicó ningún cambio.

## Pendientes y dependencias

1. Plataforma debe aportar la configuración efectiva y el inventario de terminaciones TLS (proxy, balanceador, CDN, IIS/hosting y Kestrel) para Production, Preproduction, Testing y Development relevantes.
2. Ejecutar posteriormente, sin secretos ni PII, una prueba de handshake por hostname/puerto con clientes que ofrezcan TLS 1.0, 1.1, 1.2 y 1.3; registrar que 1.0/1.1 fallan y que TLS 1.3 se negocia/puede preferirse cuando está soportado.
3. API debe confirmar si Kestrel termina TLS en algún ambiente o si recibe siempre tráfico ya terminado por un proxy; si hay puertos HTTP internos intencionales, documentar su boundary y red aislada.
4. Frontend/plataforma debe aportar la configuración TLS de su hosting. El `web.dev.config` de la documentación no acredita ni reemplaza la configuración de entrega de la aplicación Angular.
5. Las conexiones HTTP a LDAP, OTLP y servicios internos observadas en la API se evalúan, sin reabrir este ID, bajo `v5.0.0-12.2.1`, `v5.0.0-12.2.2` y los requisitos V12.3 aplicables.
