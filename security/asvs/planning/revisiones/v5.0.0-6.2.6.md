## Aplicabilidad y alcance

El control aplica al navegador en login (contraseña actual), establecimiento/activación de contraseña (nueva y confirmación) y cambio voluntario (actual, nueva y confirmación): seis campos en tres vistas. El límite relevante es la plantilla Angular y el `input` HTML entregado al navegador. API y Core reciben las contraseñas pero no determinan el atributo visual `type`. La búsqueda de plantillas `*.html` y usos de `createPasswordVisibility` en `admisiones/src/app` no mostró otro campo de contraseña propio. No se verificaron bibliotecas externas, pantallas fuera del árbol ni la aplicación desplegada.

## Resultado por componente y conclusión

**Frontend: NEEDS_REVIEW.** El código propio respalda que los seis campos inician enmascarados y permiten verlos sólo mediante su botón. Según ADR-002, la lectura de código y de pruebas no ejecutadas no basta para PASS; falta comprobar el DOM de cada flujo en un navegador real.

**API y Core:** el atributo de un campo HTML no les aplica directamente. Su exclusión no cambia la necesidad de validar el frontend servido. **Conclusión global: NEEDS_REVIEW.**

## Hallazgos y propuesta documental

No hay un defecto concreto demostrado en el código propio para este requisito. No se propone fix ni copia distribuida. Si la verificación de navegador descubre un campo sin `type=password` inicial, el responsable candidato es frontend; la corrección y sus pruebas se definirán en una fase de fixes posterior.
