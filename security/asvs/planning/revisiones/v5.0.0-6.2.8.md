## Aplicabilidad y alcance

Aplica al login de personas existentes, al cambio voluntario (verificación de la contraseña actual) y al establecimiento tras activación o recuperación (conservación de la nueva contraseña que luego se verificará). El límite principal es formulario Angular → JSON HTTP → filtros MVC → casos de uso → proxy SOAP de Core → servicio LDAP externo. El proveedor SOAP/LDAP y su política efectiva están fuera del repositorio; también falta comprobar el DOM y la dependencia privada de controles del frontend. La recuperación por identidad no verifica una contraseña previa; comparte la ruta de establecimiento de una nueva.

## Resultado por componente y conclusión

**Frontend:** no se encontró transformación propia en las rutas leídas; quedan la biblioteca de controles y el comportamiento efectivo. **API: FAIL documental.** El filtro global reescribe cualquier propiedad de contraseña para la que `HtmlSanitizer` produzca una salida diferente. El test existente evidencia que ese cambio ocurre para ciertas cadenas; la exclusión necesaria para contraseñas no está presente. **Core:** el proxy transmite lo recibido, pero no contiene el verificador. **Conclusión global: FAIL** para el requisito de exactitud en la frontera de API. No se atribuye todavía una vulnerabilidad explotable ni se afirma que el LDAP desplegado acepte una contraseña de prueba concreta.

## Hallazgos y propuesta documental

- **H1 — modificación previa a la verificación.** Condición: `SanitizeAttribute` global aplica `HtmlSanitizer` a `Password` y `CurrentPassword` antes de login/cambio, y a `NewPassword` antes de establecimiento. Impacto: una entrada cuyo texto se altere deja de verificarse o establecerse exactamente como fue recibida; podría causar rechazo o equivalencias inesperadas, según la política LDAP. Evidencia: E3–E8. Responsable candidato: API, coordinado con Core/LDAP. Propuesta para fase posterior: excluir explícitamente las propiedades de contraseña de la sanitización de contenido y mantener validación de política separada; añadir pruebas que comparen la cadena recibida con la enviada al proxy para casos con capitalización, espacios, marcas Unicode y caracteres HTML. Validar después contra el proveedor real con credenciales de prueba y sin registrar el secreto. No se aplicó fix ni se distribuyó propuesta a otro repositorio; distribución documental pendiente si se habilita una rama responsable.

## Pendientes y dependencias

- API/QA: ejecutar una prueba controlada del filtro MVC con DTOs reales que capture la contraseña antes y después del filtro, y una integración que registre sólo igualdad/longitud o hashes efímeros en un entorno de prueba, sin exponer contraseñas.
- Equipo LDAP: aportar contrato y prueba de comparación exacta del servicio SOAP para mayúsculas/minúsculas, espacios, Unicode y longitudes límite; distinguir rechazo de política de transformación. La implementación del proveedor no está en este árbol.
- Frontend/QA: comprobar valor del control y payload de red de las tres rutas en build servido, incluyendo la dependencia `@desarrolloort/components`.
