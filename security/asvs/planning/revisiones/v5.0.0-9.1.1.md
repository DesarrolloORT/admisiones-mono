# v5.0.0-9.1.1 — integridad de tokens autocontenidos

## Identificación

- ID: v5.0.0-9.1.1; nivel mínimo L1.
- Texto oficial íntegro: “Verify that self-contained tokens are validated using their digital signature or MAC to protect against tampering before accepting the token's contents.”
- Interpretación local: la API no debe aceptar claims de un JWT de acceso o de sesión/activación hasta validar criptográficamente su firma MAC.
- Pregunta: ¿los JWT autocontenidos que la API acepta validan su firma/MAC antes de usar sus claims?
- Avance: DOCUMENTADO. Resultado: NEEDS_REVIEW. Fecha: 2026-09-22.

## Aplicabilidad y alcance

Se incluyeron los JWT de acceso aceptados por el middleware bearer (cookie HttpOnly o encabezado `Authorization`) y los JWT de activación/sesión temporal que se aceptan durante el flujo de contraseña. Son tokens autocontenidos con claims que condicionan identidad o continuación de flujo.

El JWT de servicio generado para Inscripciones y Pagos se registró como boundary saliente: su consumidor es la API destino y no está en este monorepo, por lo que no demuestra ni contradice la validación de tokens aceptados aquí. Los refresh tokens son referencias opacas persistidas, no JWT autocontenidos, y no forman parte del punto. No se revisaron proxy/gateway, configuraciones efectivas, todos los consumidores externos ni el runtime.

## Resultado por componente y conclusión

- API: la lectura estática muestra validación de firma MAC antes de aceptar claims tanto en el bearer de acceso como en la sesión temporal. La fuente también configura emisor, audiencia, vigencia y HS256. Esto es evidencia favorable, pero no determinística.
- Core: no se identificó participación directa en esos validadores.
- API de Inscripciones y Pagos: no evaluada; debe aportar su propia evidencia si acepta el JWT de servicio saliente.

Resultado global: DOCUMENTADO / NEEDS_REVIEW. Según [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md), una revisión estática sin evidencia determinística no permite registrar PASS, aun cuando la configuración leída exige validación de firma.

## Hallazgos y propuesta documental

No se confirma incumplimiento ni se propone fix de código. Existe un gap de evidencia: los tests actuales no cubren aceptación/rechazo criptográfico real ni el camino HTTP completo. Responsable candidato: API/QA. Propuesta documental para fase posterior: agregar pruebas de integración que emitan un JWT HS256 válido y que alteren header, payload y firma, verificando que ninguna ruta protegida recibe claims ni devuelve éxito; cubrir análogamente la sesión de activación. No se distribuyó propuesta a ramas `fix/owasp`.
