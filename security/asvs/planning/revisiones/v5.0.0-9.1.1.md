# v5.0.0-9.1.1 — integridad de tokens autocontenidos

## Identificación

- ID: v5.0.0-9.1.1; nivel mínimo L1.
- Texto oficial íntegro: “Verify that self-contained tokens are validated using their digital signature or MAC to protect against tampering before accepting the token's contents.”
- Interpretación local: la API no debe aceptar claims de un JWT de acceso o de sesión/activación hasta validar criptográficamente su firma MAC.
- Pregunta: ¿los JWT autocontenidos que la API acepta validan su firma/MAC antes de usar sus claims?
- Avance: DOCUMENTADO. Resultado: NEEDS_REVIEW. Fecha de revisión: 2026-09-22; actualización: 2026-10-23.

## Aplicabilidad y alcance

Se incluyeron los JWT de acceso aceptados por el middleware bearer (cookie HttpOnly o encabezado `Authorization`) y los JWT de enlace de activación/recupero/alta y de sesión temporal que acepta `PasswordActivationService`. Desde la revisión anterior, ese mismo validador acepta también el enlace de una solicitud de alta aprobada por un backoffice externo (claim `idSolicitudAlta`, ADR-030), que según `DECISIONES-IMPLEMENTACION.md` y los tests se firma con la misma clave. Son tokens autocontenidos con claims que condicionan identidad o continuación de flujo.

El JWT de servicio generado para Inscripciones y Pagos es un boundary saliente: su consumidor no está en este monorepo. Los refresh tokens son referencias opacas persistidas, no JWT. No se revisaron proxy/gateway, valores efectivos en Key Vault, el emisor backoffice ni el runtime.

## Resultado por componente y conclusión

- API: la lectura estática de HEAD muestra validación de firma MAC antes de aceptar claims en el bearer de acceso y en enlaces/sesiones temporales, incluido el enlace de backoffice. Hay un test existente (no ejecutado) que cubre firma alterada en el enlace. Es evidencia favorable, no determinística.
- Core: sin participación; la API ya no referencia `Core/Utilities` ni `Core/LdapService`.
- API de Inscripciones y Pagos y emisor backoffice: no evaluados.

Resultado global: DOCUMENTADO / NEEDS_REVIEW. Según [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md), una revisión estática con tests no ejecutados no permite PASS.

## Hallazgos y propuesta documental

No se confirma incumplimiento ni se propone fix de código. Gap de evidencia: no hay prueba ejecutada del rechazo criptográfico; el test de enlace alterado (E7) existe pero no se corrió, y no hay casos equivalentes para bearer HTTP ni sesión temporal. Responsable candidato: API/QA. Propuesta para fase posterior: ejecutar E7 y agregar, sobre `ApiPipelineHarness`, casos con header, payload y firma alterados que verifiquen 401 y ausencia de principal; cubrir análogamente `ValidateSessionToken`. No se distribuyó propuesta a ramas `fix/owasp`.
