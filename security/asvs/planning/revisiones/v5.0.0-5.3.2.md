- ID: v5.0.0-5.3.2. Nivel mínimo: L1. Sección V5.3, File Storage.
- Texto oficial: "Verify that when the application creates file paths for file operations, instead of user-submitted filenames, it uses internally generated or trusted data, or if user-submitted filenames or file metadata must be used, strict validation and sanitization must be applied. ## Aplicabilidad y alcance

La SPA envía nombres (en `IFormFile.FileName`, por `multipart/form-data`) y bytes para reconocimiento de documento, foto, identidad y, ahora expuestos por HTTP, documento de la declaración jurada y comprobantes de ingreso. El reconocimiento genera un recorte de cara con nombre derivado del original. Se revisaron los usos de esos nombres y todas las construcciones de paths locales y URLs remotas productivas. Los bytes se almacenan en Oracle BLOB o Redis; no se halló escritura al filesystem desde estos flujos. La API lee/expone contratos, comentarios XML y fuentes del PDF con rutas originadas en `ContentRootPath`, `AppContext.BaseDirectory` o literales. Las llamadas remotas (Azure Document Intelligence/Face vía paquetes `ORT.*`, material de estudio, reCAPTCHA, API de pagos) usan endpoints de configuración.

No se inspeccionaron despliegue, integraciones fuera del repo (incluido el sistema legacy que lee las mismas tablas), el código interno de los paquetes NuGet `ORT.DocumentIntelligence.*`/`ORT.Vision.*`, código Devart generado ni almacenamiento de la API de pagos. No se infiere ausencia de paths dinámicos en esos límites.

## Resultado por componente y conclusión

Frontend: transmite nombres, sin poder imponer este control en el servidor (no re-verificado). API: los nombres de carga se guardan como metadatos o se devuelven en `Content-Disposition`; las rutas de filesystem se construyen con raíces del proceso y constantes; los fetch remotos usan URLs de configuración. Los adjuntos de la declaración jurada, nuevos en el alcance, aplican una sanitización estricta. Core: no participa. No se encontró un sink local o remoto cuyo path o URL provenga del nombre de archivo del usuario. Esto acota el riesgo en la ref evaluada, pero no cubre despliegue, paquetes externos ni consumidores legacy; el resultado queda NEEDS_REVIEW según ADR-002, sin afirmar PASS/FAIL ni vulnerabilidad de traversal/SSRF.

## Hallazgos y propuesta documental

No hay defecto de path traversal, LFI, RFI o SSRF confirmado. Observación preventiva (actualizada): `ResolveFileName`, `ResolvePersistedExtension` y el nombre de la cara de `FaceRecognizer` conservan partes de nombres aportados por usuarios sin la sanitización de `SanitizeFileName`; los adjuntos de la declaración jurada sí la aplican, pero las filas legacy se devuelven con el nombre guardado tal cual. Hoy los usos inspeccionados son metadatos/DTO/encabezados, no rutas. Si algún consumidor (incluido el legacy) usa esos valores para crear un path, deberá generar un identificador interno o validar estrictamente y verificar que el path resuelto queda dentro de una raíz fija. Responsables candidatos: API. No se distribuye propuesta a otro repo: no hay fix concreto en el flujo actual.
