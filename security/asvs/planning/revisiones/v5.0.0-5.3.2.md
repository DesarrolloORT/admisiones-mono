## Aplicabilidad y alcance

La SPA envía al servidor nombres y bytes para reconocimiento de documento, foto e identidad; los métodos de becas también aceptan `fileName`, aunque la ficha 5.2.2 no localizó caller HTTP activo. La API/Core puede generar una imagen de cara con un nombre derivado del original. Se revisaron los usos de esos nombres y las construcciones de paths locales de producción. Los bytes revisados se almacenan en Oracle BLOB o Redis; no se halló una escritura al filesystem desde estos flujos. La API lee/expone contratos y comentarios XML usando rutas originadas en `ContentRootPath` o `AppContext.BaseDirectory` más literales internos. Las llamadas de Azure construyen URL con endpoint de configuración y parámetros del servicio, no con el nombre completo del archivo.

El frontend tiene `.codegraph/` sin índice, sólo `.gitignore`; se usó `rg`. API y Core no tienen `.codegraph/`. No se inspeccionaron despliegue, integraciones fuera del repo, otros consumidores de Core, código Devart generado ni almacenamiento de la API de pagos. No se infiere ausencia de paths dinámicos en esos límites.

## Resultado por componente y conclusión

Frontend: transmite nombres, sin poder imponer este control en el servidor. API: los nombres de carga revisados se guardan como metadatos o se devuelven; las rutas de filesystem leídas se construyen con raíces del proceso y constantes. Core: la imagen derivada se produce en memoria; la URL Azure usa configuración y valores codificados. No se encontró un sink local o remoto de file I/O cuyo path provenga del nombre de archivo del usuario. Esto acota la aplicabilidad del riesgo en la ref evaluada, pero no demuestra cobertura del despliegue e integraciones; el resultado queda NEEDS_REVIEW según ADR-002, sin afirmar PASS/FAIL ni vulnerabilidad de traversal/SSRF.

## Hallazgos y propuesta documental

No hay defecto de path traversal, LFI, RFI o SSRF confirmado. Observación preventiva: `ResolveFileName`, `ResolvePersistedExtension` y `ConstruirNombreArchivoCara` conservan partes de nombres aportados por usuarios sin la sanitización completa; hoy los usos inspeccionados son metadatos/DTO, no rutas. Si algún consumidor posterior usa esos valores para crear un path, deberá generar un identificador interno o validar estrictamente y verificar que el path resuelto queda dentro de una raíz fija. Responsables candidatos: API/Core. No se distribuye propuesta a otro repo: no hay fix concreto en el flujo actual y `git worktree list` sólo muestra el monorepo.

## Pendientes y dependencias

- Equipo API/operaciones: aportar mapa de almacenamiento y rutas efectivas en despliegue, incluidos jobs/integraciones que consuman `NombreImagen`, `NombreArchivo*` o `FileName` de DTO; seguir sus `File.Open/Write` o URI remotas. Método: revisión de código/configuración de esos consumidores y prueba aislada con nombres que contengan separadores y secuencias de traversal, sin scan activo en esta fase.
- Equipo Core/API: confirmar en ambiente reproducible si algún nombre recibido llega a una operación de filesystem o a un fetch remoto. Si aparece ese sink, comprobar contención del path normalizado en raíz fija y destino del URI; registrar resultado antes de PASS/FAIL.
- Equipo API: revisar configuración efectiva del endpoint Azure y el manejo de URLs de operación devueltas por el proveedor dentro del análisis SSRF de integraciones. No se atribuye control del endpoint al `FileName` cliente en este flujo.
- Dependencia: la ficha 5.3.1 documenta ausencia de escritura a carpeta pública en los flujos revisados, pero no sustituye la búsqueda de sinks de paths de este requisito. La discrepancia extensión/contenido de 5.2.2 es otro control.
