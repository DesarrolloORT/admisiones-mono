## Aplicabilidad y alcance

Aplica a la API por dos flujos: (1) la recuperación de `PASSWORD_LDAP`, que se «descifra» antes de llamar al servicio LDAP, y (2) la caché Redis de imágenes de documento, cifrada con AES-256-GCM. También abarca el blob `parametrosEncriptados` de Pagos si el algoritmo lo decide el sistema integrado; API y frontend sólo lo transportan.

Core ya no participa del camino activo: la API dejó de referenciar `Core/Utilities` y `Core/LdapService`. No se evaluaron el productor/receptor de Pagos, el productor histórico de `PASSWORD_LDAP`, los paquetes `ORT.*` como binarios, Key Vault/Redis efectivos ni tráfico real.

## Resultado por componente y conclusión

- **API: FAIL.** El secreto LDAP sigue recuperándose mediante una transformación reversible propia (E1, E2), que no es un cifrado ni modo aprobado. La caché de imágenes sí usa AES-256-GCM (E3), lo que es favorable pero no compensa el otro flujo.
- **Core: FAIL sin impacto directo en la API.** `Encriptador` sigue sin ser cifrado aprobado; ya no está en el camino de la API, pero permanece en el submódulo para otros posibles consumidores.
- **Frontend: NEEDS_REVIEW** según la evidencia de `86979de2`, no re-verificada.
- **Integraciones externas: NEEDS_REVIEW.** Sin contrato del algoritmo de `parametrosEncriptados`.

Resultado global: **FAIL** por H1. No se ejecutaron tests, builds, runtime ni scans.

## Hallazgos y propuesta documental

**Hallazgo H1 — protección reversible no aprobada para `PASSWORD_LDAP` (vigente; reubicado).** Condición: hasta la revisión anterior en `Core/Utilities/Encriptador` + `Core/LdapService/Ldap`; desde `cebff419`/`12248719` en `LdapServiceKeyProvider.Deobfuscate` de la API (E1), con el mismo formato persistido (E2). Impacto: el valor almacenado se revierte con el código disponible, sin propiedades de un cifrado autenticado. Responsable candidato: API (y dueño de la tabla de parámetros). Propuesta: mover el secreto LDAP a Key Vault, como el resto de los secretos desde `60c05999`, o cifrarlo con AES-GCM y clave administrada; validar migración, rotación y rechazo del formato legacy. No se aplicó ningún cambio.

**Observación O1 — blob de Pagos sin algoritmo verificable (vigente).** Responsable candidato: integración Inscripciones/Pagos. Propuesta: contrato técnico con algoritmo, modo, versionado e integridad, más prueba representativa.

**Observación O2 (nueva, positiva con salvedad) — caché de imágenes con AES-256-GCM.** Cumple el algoritmo/modo aprobado; la derivación de clave por SHA-256 simple y la ausencia de rotación/versionado de clave quedan para v5.0.0-11.4.1 y gestión de claves.
