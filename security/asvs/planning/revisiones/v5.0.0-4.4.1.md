# v5.0.0-4.4.1

## Identificación

- ID: v5.0.0-4.4.1. Nivel mínimo: L1.
- Texto oficial: "Verify that WebSocket over TLS (WSS) is used for all WebSocket connections."
- Interpretación local: el requisito exige que, si el sistema abre canales WebSocket, éstos usen el esquema cifrado `wss://` y no `ws://` sin TLS. No exige que el sistema use WebSocket; su aplicabilidad depende de que exista al menos una conexión WebSocket real (propia o de una dependencia productiva) en algún componente, como servidor o como cliente.
- Pregunta concreta: ¿existe, en `admisiones` (frontend), `api-admisiones` o `Core`, algún endpoint, cliente o dependencia productiva que abra una conexión WebSocket (servidor `UseWebSockets`/SignalR/`MapHub`, o cliente `new WebSocket(...)`/`ClientWebSocket`/`socket.io`/transporte WebSocket de un SDK)? Si existe, ¿usa exclusivamente `wss://`?
- Avance documental: DOCUMENTADO.
- Resultado de seguridad: NEEDS_REVIEW.
- Fecha de revisión: 2026-09-17; actualización: 2026-10-23.

## Aplicabilidad y alcance

- `security/asvs/planning/api-admisiones.md` (sección V4) marca V4.4 — WebSocket como sección que "requiere confirmar uso" antes de excluir. En la revisión anterior el inventario fue negativo y el punto quedó NOT_APPLICABLE.
- **Cambio de aplicabilidad**: desde la migración del email a ORT.Messaging/Service Bus (`6f5f685b`), la API crea un `ServiceBusClient` con `ServiceBusTransportType.AmqpWebSockets`. Es decir, la API **abre conexiones WebSocket salientes como cliente** (AMQP sobre WebSocket hacia Azure Service Bus). El requisito pasa a aplicar a ese canal.
- Componentes inspeccionados en esta actualización: `api-admisiones` (código `.cs`, `.csproj`, `appsettings*.json`, `Dockerfile`) y el Core consumido. Frontend: se conserva el inventario negativo de `86979de2` sin re-verificar.
- No inspeccionado / fuera de alcance: el código interno de `Azure.Messaging.ServiceBus` y `ORT.Messaging.ServiceBus` (paquetes NuGet, no versionados en el repo); el valor efectivo de `ServiceBus:Fqdn` en producción (vacío en `appsettings.Production.json`, llega por Key Vault); proxy/firewall de salida; configuración de hosting no versionada; dependencias de build tooling del frontend.

## Resultado por componente y conclusión

- **API (`api-admisiones`)**: aplica. Abre un canal AMQP sobre WebSocket hacia Azure Service Bus (E1). La configuración (namespace + `TokenCredential`, sin connection string ni modo emulador) apunta a que el SDK usa `wss://` sobre 443, pero eso es una propiedad del SDK externo, no verificada con código leído ni con tráfico.
- **Core**: sin WebSocket (E5); la API sólo consume `DbConnectionContext`.
- **Frontend**: sin WebSocket según la evidencia de `86979de2` (E6), no re-verificada.
- **Conclusión**: el punto deja de ser NOT_APPLICABLE. No hay indicio de `ws://` en texto claro, pero la propiedad exigida depende del comportamiento interno del SDK y no hay evidencia determinística (captura de tráfico, test, lectura del SDK fijado). Según ADR-002, el resultado es **NEEDS_REVIEW**.

## Hallazgos y propuesta documental

- Sin hallazgo de defecto: el único canal WebSocket es gestionado por el SDK oficial con autenticación Entra ID, y no se encontró forma de configurar un esquema sin TLS desde el repo.
- Observación (aplicabilidad): la exclusión anterior quedó invalidada por un cambio de infraestructura de mensajería que no tocó código HTTP. Se recomienda, para la fase posterior, que el inventario de 4.4.x incluya transportes de SDKs (`TransportType`, `AmqpWebSockets`) y no sólo servidores/clientes WebSocket explícitos.
- Observación de deuda: no hay control automatizado que alerte si se introduce `ws://`, `UseWebSockets()` o un `ServiceBusClient` por connection string con `UseDevelopmentEmulator`. Sin propuesta de fix en esta fase.
