## Aplicabilidad y alcance

- Frontend: código propio de navegador y herramientas JS; entradas de formularios, datos HTTP, selección de campos, navegación y carga de bibliotecas. Se inspeccionaron candidatos a temporizadores, imports y evaluadores; los ejemplos seguidos pasan datos a callbacks o rutas literales.
- API: fuentes C# y manifiestos de proyectos, incluidos infraestructura Redis y filtro por reflexión. El nombre ExecuteAsync de un caso de uso o transacción no constituye por sí mismo evaluación de código.
- Core: fuentes C# de la ref consumida, utilidades, Azure, módulos y proxies SOAP generados; se clasificaron coincidencias de CodeDom, expresiones y delegates. No se excluye globalmente el requisito por tratarse de .NET/Angular.
- No se auditaron implementaciones transitivas, paquetes privados, artefactos compilados, scripts reCAPTCHA recibidos, configuración efectiva del hosting ni los servidores de servicios externos. La ausencia de coincidencias en código propio no cubre esos boundaries.
- SpEL se buscó como candidato, sin localizarlo en las fuentes y manifiestos inspeccionados. No se hace una exclusión general de tecnologías ni se abren revisiones OAuth/GraphQL u otros requisitos.

## Resultado por componente y conclusión

- **Frontend — NEEDS_REVIEW:** fuentes propias y candidatos observados sin evaluación de strings; falta evidencia del bundle real, dependencias privadas y script externo.
- **API — NEEDS_REVIEW:** sin motor directo localizado; Redis y reflexión inspeccionados manipulan datos o miembros de tipos enlazados. Faltan dependencias transitivas y artefacto/configuración efectivos.
- **Core — NEEDS_REVIEW:** coincidencias clasificadas sin evaluar código de usuario; cobertura limitada a la ref consumida y las búsquedas/fuentes descritas.

**Conclusión compartida: DOCUMENTADO / NEEDS_REVIEW**, según [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md). No hay un flujo confirmado de entrada no confiable hacia ejecución dinámica que justifique FAIL, ni evidencia suficiente para PASS o NOT_APPLICABLE. AOT configurado y sanitización HTML global no cierran el requisito. No se estableció contradicción documental confirmada; los planes son contexto, no demostraciones de cumplimiento.

## Hallazgos y propuesta documental

No se confirma una vulnerabilidad ni se propone un fix concreto sobre los candidatos leídos. El gap de cobertura es la falta de inventario y evidencia del código efectivamente ejecutado en dependencias/hosting. Responsable candidato: frontend y plataforma para bundle/scripts; API/Core y plataforma para assemblies y configuración efectiva.

Propuesta para fase posterior: inspeccionar un artefacto existente identificado por commit/hash y sus dependencias, clasificar cada evaluador localizado y seguir sus entradas. Si se encuentra evaluación de texto no confiable, documentar necesidad/alternativa y restricciones del lenguaje en ese boundary antes de diseñar remediación. No aceptar HtmlSanitizer como evidencia suficiente para código. Validación futura: demostrar con datos sintéticos que el valor llega como dato y no se ejecuta, o que el lenguaje permitido y sus límites están efectivamente impuestos.

No se distribuyeron copias en worktrees fix/owasp: no hay remediación de código concreta para distribuir; la propuesta de obtención de evidencia queda central. Si aparece un hallazgo en validación posterior, comprobar branch/worktree y ref del repositorio responsable antes de distribuir Markdown, sin recrear checkouts por suposición.
