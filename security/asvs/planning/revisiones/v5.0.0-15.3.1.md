# v5.0.0-15.3.1 — subconjunto de campos en respuestas

## Identificación

- ID y nivel mínimo: v5.0.0-15.3.1 (L1).
- Texto oficial: “Verify that the application only returns the required subset of fields from a data object. For example, it should not return an entire data object, as some individual fields should not be accessible to users.”
- Interpretación local: cada respuesta HTTP debe ser un contrato deliberado que exponga únicamente los campos necesarios para su consumidor y su sujeto autorizado; no debe serializar entidades, filas de vista ni respuestas de integraciones completas por conveniencia.
- Pregunta: ¿los endpoints devuelven sólo los campos necesarios para cada flujo y no objetos de persistencia o integración completos?
- Avance documental: DOCUMENTADO. Resultado de seguridad: NEEDS_REVIEW.

## Aplicabilidad y alcance

El requisito aplica a las respuestas de la API y a los datos que el frontend recibe antes de adaptarlos a su estado de vista. Se inspeccionaron como muestra los flujos autenticados de datos personales y de inscripciones: `GET /person/details`, `GET /person/enrollments` y `GET /enrollments/details`, incluidos sus DTOs, mapeadores y consumidores Angular. En esta actualización se sumaron los flujos nuevos o modificados con datos sensibles: reconocimiento de documento de identidad (`POST /registration/analyze-attachment`, Azure Document Intelligence), declaración jurada de becas (`GET /scholarships/affidavit`) y el cuerpo de error unificado (`Result<T>`/`Error`). También se inventariaron las declaraciones de respuesta de los controladores versionados.

No se inspeccionaron uno por uno todos los contratos de Auth, Registration, Catalogs, Scholarships, fotos/documentos, los clientes de integraciones, código generado ni Core. Tampoco se ejecutaron pruebas de contrato, llamadas autenticadas con más de un usuario, ni se contrastaron los campos con una matriz de necesidad por pantalla, rol, estado y destinatario. Por ello la muestra no acredita el requisito para toda la aplicación.

## Resultado por componente y conclusión

- API: NEEDS_REVIEW. La muestra de persona, inscripciones, reconocimiento de documento y declaración jurada usa contratos de respuesta y mapeos de lista permitida, y evita devolver directamente entidades, filas de vista o la respuesta cruda de Azure; los errores sólo exponen el mensaje. Sin embargo, no hay inventario de clasificación/necesidad de campos por endpoint ni evidencia de los payloads efectivos de todos los controladores, integraciones y estados.
- Frontend: NEEDS_REVIEW. Los adaptadores inspeccionados reducen respuestas a modelos de pantalla, lo que limita la propagación local, pero el control requerido debe ocurrir antes de transmitir datos y la cobertura de consumidores no es exhaustiva (evidencia no re-verificada).
- Core: NEEDS_REVIEW. Está fijado como dependencia de la API (sólo `DbConnectionContext`), pero no se inspeccionaron sus entidades ni eventuales superficies de respuesta para este requisito.
- Conclusión: NEEDS_REVIEW. Hay evidencia favorable de diseño de DTO/mapeo explícito en los flujos muestreados, insuficiente para afirmar que toda respuesta contiene exclusivamente el subconjunto necesario. Según ADR-002, la revisión estática sin evidencia determinística no permite PASS.

## Hallazgos y propuesta documental

1. Condición (vigente en 912fc665): no se encontró una matriz versionada que relacione endpoint/estado/consumidor con sus campos permitidos y su justificación; tampoco una validación de contrato que detecte campos adicionales. Impacto: un DTO puede acumular campos de conveniencia o un nuevo mapeo puede exponer campos internos sin que la necesidad mínima sea revisable. Responsable candidato: arquitectura/seguridad junto con mantenedores de API y frontend. Propuesta para fase posterior: definir contratos de respuesta por caso de uso con allowlist y clasificación de datos, y añadir pruebas de contrato negativas para campos no permitidos, empezando por persona, inscripción, pago, reconocimiento de documento (incluido `PersonFace`) y declaración jurada. Validación futura: con ambiente autorizado, capturar respuestas de cada endpoint/rol/estado y compararlas con la matriz y las pruebas de contrato.
2. Observación menor: el comentario XML de `GET /person/enrollments` (E3) describe el payload como «todos los campos expuestos por la vista»; corregirlo evitaría que el contrato publicado en Swagger sugiera lo contrario de lo que hace el mapeo.

No se distribuyó propuesta a worktrees: no hubo fase de remediación autorizada.
