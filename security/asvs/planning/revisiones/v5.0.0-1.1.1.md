- Frontend: NEEDS_REVIEW. Los caminos explícitos leídos tienen expectativas locales de representación y no muestran doble decodificación del mismo valor. Falta ejecución del router, parsers y boundary de pagos.

## Hallazgos y propuesta documental

No se confirma vulnerabilidad ni severidad. Dos condiciones requieren investigación:

1. **Representación validada frente a representación procesada (E4–E5).** El esquema analiza el documento antes del binding y luego el action filter aplica interpretación HTML a strings. Si esta transformación cambia la semántica de un campo validado o trata entidades donde el contrato exige texto literal, podría invalidar la decisión previa. Responsable candidato: API, con frontend para contrato. Primero capturar valores sintéticos en cada etapa y comportamiento de la versión instalada del sanitizador; cualquier propuesta de cambio debe decidirse con esa evidencia, preservando el contrato público.
2. **Contrato del sufijo de pagos (E7–E8).** Split asume que todo lo posterior al marcador es el parámetro codificado. Sin contrato no se conoce tratamiento de escapes dobles, separadores adicionales o decodificación del receptor. Impacto posible: alterar o rechazar el blob enviado a pagos; no se demuestra explotación. Responsables candidatos: API y dueño de integración de pagos. Primero confirmar gramática y transformaciones esperadas en cada extremo antes de proponer remediación.

Las propuestas actuales son de obtención de evidencia, conservadas en esta ficha central. No se definió ni aplicó un cambio de implementación. Distribución documental a worktrees originales pendiente de confirmar responsables y contratos; no se escribieron copias en otras refs ni se mezcló su evidencia.
