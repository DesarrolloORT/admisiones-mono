## Aplicabilidad y alcance

Aplica a frontend y API; Core solo en la medida en que la API lo consume. Boundaries: navegador/API (query, JSON y, desde 90ccee3d, multipart/form-data con IFormFile), almacenamiento de sesión del frontend, respuesta de la API interna de pagos → API → frontend → receptor externo, Redis (caché cifrada de imágenes) y respuestas de Azure Document Intelligence, que ahora se consumen mediante paquetes ORT.DocumentIntelligence/ORT.Vision y lógica propia en AppLogic.Identity.Recognition.

Cambio de alcance en Core: en 912fc665 los proyectos de la API solo referencian `Core/DbConnectionContext/ConnectionContext.csproj` (AppLogic.*, DataAccess, WebApiAdmisiones, UnitTesting). Core/Utilities (Encriptador), Core/AzureService, Core/MailORT y Core/LdapService siguen en el checkout del submódulo, pero no los compila ni los invoca la API; no se evalúan como parte del flujo vigente. El código de los paquetes ORT.* (DocumentIntelligence, Vision, Ldap, Messaging) no se inspeccionó.

Inventario acotado en la API vigente: búsqueda de FromBase64String, UrlDecode, HtmlDecode, UnescapeDataString, Regex.Unescape, WebUtility./HttpUtility. y Normalize en AppLogic, WebApiAdmisiones, BusinessLogic y DataAccess. Coincidencias productivas: InvoicePaymentUrl (UnescapeDataString), RedisIdentityDocumentImageCache (FromBase64String de un blob propio) y normalización Unicode de OCR en TextNormalizer. No se excluyen tecnologías por ausencia de coincidencias. Fuera de cobertura efectiva: parsers de terceros (System.Text.Json, NJsonSchema, binder multipart, HtmlSanitizer), proxy/IIS/Kestrel efectivos, receptor externo de pagos, paquetes ORT.* y ejecución HTTP real.

CodeGraph: no hay .codegraph/ en la API ni en Core; se usaron rg/Grep y lectura. No se ejecutaron builds, tests, runtime ni scans.

## Resultado por componente y conclusión

- Frontend: NEEDS_REVIEW (sin re-verificar). Se conserva la conclusión original; el cambio a multipart en la API hace probable que E1 ya no describa el frontend vigente.
- API: NEEDS_REVIEW. Mejora: desaparece la decodificación Base64 de archivos de entrada (E6). Se mantienen la secuencia schema → binding → HtmlSanitizer (E4–E5) y el desescapado del sufijo de pagos (E8), y aparece la hipótesis de sanitización HTML sobre metadatos multipart (E7).
- Core: NEEDS_REVIEW acotado. Solo DbConnectionContext está en el grafo de la API, y no realiza decodificaciones relevantes para este ID. Las utilidades citadas antes quedaron fuera del flujo (E12).

Conclusión compartida: DOCUMENTADO / NEEDS_REVIEW según ADR-002. No hay evidencia determinística para PASS/FAIL ni exclusión que justifique NOT_APPLICABLE. No se ejecutaron builds, tests, runtime ni scans.

## Hallazgos y propuesta documental

No se confirma vulnerabilidad ni severidad. Condiciones a investigar:

1. **Representación validada frente a representación procesada (E4–E5).** Vigente en 912fc665. El esquema analiza el documento antes del binding y luego el action filter aplica interpretación HTML a strings. Si cambia la semántica de un campo validado o escapa entidades donde el contrato exige texto literal, invalida la decisión previa. Responsable candidato: API, con el frontend para el contrato. Primero capturar valores sintéticos en cada etapa con la versión instalada (HtmlSanitizer 9.1.982).
2. **Contrato del sufijo de pagos (E8–E9).** Vigente, sin cambios de lógica. Split asume que todo lo posterior al marcador es el parámetro codificado y lo desescapa una vez. Responsables candidatos: API y dueño de la integración de pagos.
3. **Nuevo — sanitización HTML de metadatos multipart (E7).** Si SanitizeAttribute desciende en IFormFile y reescribe ContentDisposition/ContentType, el FileName y el MIME que usan las acciones serían una representación HTML-escapada de un valor no HTML, aplicada antes de FileValidator. Impacto posible: nombres alterados o rechazos inesperados; no se demuestra bypass. Responsable candidato: API. Propuesta futura: test unitario con un FormFile sintético (`a&b.pdf`, `x<y>.png`) que compare FileName antes y después del filtro y, si se confirma, excluir IFormFile del recorrido o restringirlo a DTO propios.
4. **Base64 de imágenes de entrada (revisión anterior).** Resuelto en 912fc665 para la API: ya no aplica porque las subidas son multipart binarias desde 90ccee3d (E6). Se conserva el registro.

Las propuestas siguen siendo de obtención de evidencia y quedan en esta ficha central. No se distribuyeron copias a otros repos.
