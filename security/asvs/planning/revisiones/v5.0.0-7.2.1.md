## Aplicabilidad y alcance

Se revisaron el JWT de acceso en cookie o Bearer, el refresh token, la sesión temporal de contraseña (incluida la sesión del link del backoffice, ADR-030) y el identificador previo al 2FA. La frontera es navegador → API; Oracle y Redis son almacenes backend. El estado Angular controla navegación, mientras la API verifica credenciales en rutas protegidas.

No se inspeccionaron runtime, proxy, configuración efectiva, servicios externos (incluida la API de inscripciones/pagos que recibe el JWT del usuario reenviado), todos los consumidores de Core ni todas las rutas. Esto limita la conclusión sobre “all”.

## Resultado por componente y conclusión

- API: los tokens examinados, incluida la nueva sesión del link de backoffice, se verifican en backend; faltan pruebas integradas e inventario exhaustivo de receptores (la API interna de inscripciones/pagos recibe el JWT del usuario y no fue inspeccionada). NEEDS_REVIEW.
- Frontend: consulta API para rehidratar y renovar; el estado local no autoriza la API. No re-verificado en esta actualización. NEEDS_REVIEW.
- Core fijado: sin rol directo identificado en los flujos acotados; otros consumidores no inventariados.

Resultado global: DOCUMENTADO / NEEDS_REVIEW. La revisión estática no permite afirmar PASS para “all session token verification”.
