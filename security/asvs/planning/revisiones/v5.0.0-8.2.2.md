## Aplicabilidad y alcance

Aplica a las instancias de datos que el consumidor puede inferir o modificar: persona, foto y documento de identidad, encuesta inicial, intereses, ofertas, inscripciones y pago. Los catálogos públicos o compartidos no son recursos personales, aunque sus identificadores alimenten operaciones posteriores.

Se siguió el flujo desde los controllers protegidos hasta casos de uso y repositorios: la identidad se obtiene desde el claim del JWT y no desde `personId` aportado por el cliente; las operaciones de inscripción y pago que sí reciben IDs los consultan junto al `personId`. También se leyeron tests unitarios de controllers, sin ejecutarlos. No se ejecutaron requests con dos cuentas, pruebas de integración, consultas Oracle, ni se inspeccionaron la API interna de inscripciones/pagos, gateway, LDAP o infraestructura.

## Resultado por componente y conclusión

- **API: NEEDS_REVIEW.** El patrón visible es correcto para los recursos personales: la identidad viene del JWT, no existe un `personId` controlado por el cliente, y las rutas que aceptan IDs de inscripción los cotejan con ese `personId`. Hay controles estáticos concretos para reactivación, detalle y pago.
- **Frontend:** no es un boundary de autorización; sus cambios locales no se usaron para acreditar este requisito.
- **Core:** no expone recursos HTTP propios. Los repositorios y servicios remotos que materializan las consultas siguen siendo una dependencia de la conclusión.

El resultado global es **DOCUMENTADO / NEEDS_REVIEW**. No apareció un BOLA/IDOR confirmado en el flujo estático revisado, pero ADR-002 impide elevarlo a PASS sin evidencia determinística. Faltan pruebas multi-identidad contra el host y Oracle, inventario completo de recursos y confirmación de que la API interna no permite reintroducir un ID ajeno después de las validaciones locales.

## Hallazgos y propuesta documental

1. **Cobertura BOLA no demostrada de extremo a extremo.** Condición: los controles locales enlazan IDs de inscripción con `personId`, pero sólo hay tests unitarios de delegación y no se ejecutó una prueba con dos identidades. Impacto: un cambio de repositorio, mapping o integración podría romper la relación sin detectarse. Evidencia E4–E9. Responsable candidato: API/QA. Propuesta futura: crear y ejecutar pruebas de integración de A/B que intenten leer, actualizar, subir documento, reactivar y pagar recursos de B usando el token de A, esperando 404/403 y sin efecto persistente.
2. **Contrato de la integración de inscripciones/pagos sin evidencia de autorización.** Condición: el host filtra antes de invocar al cliente, pero el contrato y autorización efectiva del servicio remoto no se revisaron. Impacto: una ruta futura o un cambio de orden puede confiar indebidamente en el límite local. Evidencia E5, E6 y E8. Responsable candidato: owners de API e integración. Propuesta futura: documentar el boundary, identidad de servicio y garantías del proveedor; incluir pruebas contractuales sin secretos.

No se aplicó ninguna propuesta ni se modificaron código, configuración, contratos o tests.
