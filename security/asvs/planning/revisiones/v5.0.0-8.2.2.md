# v5.0.0-8.2.2 — acceso específico a datos

## Identificación

- ID: v5.0.0-8.2.2; nivel mínimo L1; sección V8.2, General Authorization Design.

## Aplicabilidad y alcance

Aplica a las instancias de datos que el consumidor puede inferir o modificar: persona, foto y documento de identidad, encuesta inicial, intereses, ofertas, inscripciones, pago y, desde la revisión anterior, postulaciones a becas (`applicationId` = `ID_INSCRIPTO_PRUEBA`), su aceptación, la declaración jurada (`applicationId`, `affidavitId`) y sus comprobantes de ingreso (`incomeId`). También el link del backoffice (ADR-030), que decide sobre qué persona escribe el alta. Los catálogos públicos o compartidos y el material de estudio (`study-material`, igual para todos) no son recursos personales.

Se siguió el flujo desde los controllers protegidos hasta casos de uso y repositorios: la identidad se obtiene del claim del JWT y no de un `personId` aportado por el cliente; las operaciones que reciben IDs los consultan junto al `personId`. Se leyeron tests unitarios, sin ejecutarlos. No se ejecutaron requests con dos cuentas, pruebas de integración ni consultas Oracle, ni se inspeccionaron la API interna de inscripciones/pagos, el backoffice, gateway, LDAP o infraestructura.

## Resultado por componente y conclusión

- **API: NEEDS_REVIEW.** El patrón visible es correcto y se extendió a los recursos nuevos: la identidad viene del JWT, no existe un `personId` controlado por el cliente, y las rutas que aceptan IDs de inscripción, postulación, declaración jurada o comprobante los cotejan con ese `personId`, con 404 uniforme. Hay tests unitarios de dueño ajeno para becas, adjuntos y link de backoffice.
- **Frontend:** no es un boundary de autorización; no re-verificado.
- **Core:** no expone recursos HTTP propios. Repositorios y servicios remotos que materializan las consultas siguen siendo una dependencia de la conclusión.

El resultado global es **DOCUMENTADO / NEEDS_REVIEW**. No apareció un BOLA/IDOR confirmado en el flujo estático revisado, pero ADR-002 impide elevarlo a PASS sin evidencia determinística. Faltan pruebas multi-identidad contra el host y Oracle, revisión del SQL de vistas y repositorios, y confirmación de que la API interna (que recibe sólo IDs de prueba/producto para postular) no permite reintroducir un ID ajeno.

## Hallazgos y propuesta documental

1. **Cobertura BOLA no demostrada de extremo a extremo (vigente en `912fc665`).** Condición: los controles locales enlazan IDs con `personId` y ahora hay tests unitarios de dueño ajeno para becas y declaración jurada, pero no se ejecutó una prueba con dos identidades. Impacto: un cambio de repositorio, vista, mapping o integración podría romper la relación sin detectarse. Evidencia E4–E12. Responsable candidato: API/QA. Propuesta futura: pruebas de integración A/B que intenten leer, actualizar, subir documento, reactivar, pagar, postular, aceptar beca y leer/escribir/borrar adjuntos de la declaración jurada de B con el token de A, esperando 404 y sin efecto persistente.
2. **Contrato de la integración de inscripciones/pagos sin evidencia de autorización (vigente).** Condición: el host filtra antes de invocar al cliente, pero el contrato y la autorización efectiva del servicio remoto no se revisaron; el alta de postulación ni siquiera envía la persona y depende de que el proveedor la derive del JWT reenviado. Impacto: una ruta futura o un cambio de orden puede confiar indebidamente en el límite local. Evidencia E6–E8 y E10. Responsable candidato: owners de API e integración. Propuesta futura: documentar el boundary, identidad de servicio y garantías del proveedor; incluir pruebas contractuales sin secretos.
3. **Link de backoffice sin cotejo cuando la solicitud no tiene persona (observación nueva).** Condición: ADR-030 sólo compara `codigoPersona` cuando la solicitud ya tiene `CODIGO_PERSONA`; si no lo tiene, cualquier persona existente indicada en el token se acepta y el alta la actualiza. Impacto: un error del backoffice podría pisar datos y fijar la contraseña de otra persona; ADR-030 lo asume explícitamente como confianza en el emisor. Evidencia E11. Responsable candidato: API/backoffice. Propuesta futura: confirmar con el backoffice que ese caso no ocurre o agregar un cotejo adicional (p. ej. documento de la solicitud contra el de la persona) y probarlo. No es un IDOR explotable por un consumidor sin el secreto de firma.

No se aplicó ninguna propuesta ni se modificaron código, configuración, contratos o tests.
