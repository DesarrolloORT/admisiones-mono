## Aplicabilidad y alcance

El requisito sigue aplicando al menos al cliente SOAP de LDAP, que ahora vive en el paquete `ORT.Ldap.Soap` (cebff419) en lugar de Core/LdapService. El límite de confianza es la respuesta del servicio LDAP, aunque sea interno. El SOAP de correo Office365 dejó de ser alcanzable desde la API: los correos se publican como mensajes JSON en Azure Service Bus (`ORT.Messaging.ServiceBus`, a092f905) y los envía un worker externo, fuera de este repositorio.

Entrada HTTP: no hay formatters XML registrados. Desde la revisión anterior, `JsonSchemaValidationFilter` rechaza con 415 los requests con body cuyo Content-Type no sea `application/json` o `multipart/form-data`. Las subidas multipart (ADR-019, 90ccee3d) solo admiten .jpg/.jpeg/.png/.pdf validados por magic bytes; no se aceptan SVG ni formatos OOXML en las listas activas.

Reconocimiento de documentos y caras usa los SDK de Azure mediante paquetes ORT (JSON sobre HTTP). Core consumido se reduce a DbConnectionContext, sin XML. Core/LdapService y Core/MailORT siguen en el checkout Core, pero admisiones ya no los compila.

Frontend (evidencia original): sin DOMParser/XMLSerializer/parseFromString propios; SVG de un paquete privado y herramientas transitivas pendientes.

Fuera de cobertura: implementación del paquete ORT.Ldap.Soap y de System.ServiceModel efectivamente resueltos, artefacto desplegado, worker de correo, servicios SOAP remotos, parsers de proveedores externos y otros consumidores de Core. No se declara NOT_APPLICABLE global.

- API: NEEDS_REVIEW. Sin parser XML propio y, ahora, con rechazo explícito de Content-Type no JSON/multipart en el filtro de recursos. El único XML entrante identificado es la respuesta SOAP de LDAP procesada dentro de `ORT.Ldap.Soap`/WCF, sin evidencia determinística de su configuración.

- Frontend: NEEDS_REVIEW, con la evidencia original sin re-verificar.

Conclusión compartida: DOCUMENTADO / NEEDS_REVIEW según [ADR-002](../../../adr/ADR-002-asvs-evidence-model.md). No hay PASS/FAIL reproducible suficiente.

## Hallazgos y propuesta documental

H1 — Falta de evidencia de la política efectiva de XML en el cliente SOAP (vigente, responsable desplazado). Condición: la API delega el parsing de respuestas LDAP en `ORT.Ldap.Soap` (WCF/BasicHttpBinding) sin evidencia sobre DTD, entidades, resolver y cuotas aplicados. El cliente SOAP Office365 ya no aplica a admisiones (resuelto por eliminación en a092f905, no por configuración). Impacto condicional: si el parser resolviera recursos externos, una respuesta maliciosa podría originar acceso a archivos o red; no demostrado. Responsables candidatos: mantenedores de ORT.Ldap.Soap (repositorio de paquetes ORT) e integración API.

Propuesta para fase posterior: leer la fuente de ORT.Ldap.Soap en la versión consumida (2.0.5) y documentar binding, encoder y cuotas; si se encuentra configuración permisiva, definir el cambio mínimo en el paquete. La observación de cuotas `int.MaxValue` de los proxies generados en Core (E5 original) ya no aplica a admisiones; queda para otros consumidores de Core.

Observación menor: el comentario de [Directory.Build.props](../../../../api-admisiones/WebApiAdmisiones/Directory.Build.props#L1) atribuye la dependencia de System.Security.Cryptography.Xml a Core/LdapService, que la API ya no referencia; hoy llega por ORT.Ldap.Soap (que declara 10.0.11, superior al pin 10.0.10). No afecta este requisito; corresponde a V15 (dependencias).

No existe un fix concreto sustentado para distribuir. Propuesta conservada centralmente.
