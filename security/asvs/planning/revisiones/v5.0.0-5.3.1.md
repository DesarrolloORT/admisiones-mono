## Aplicabilidad y alcance

Registro, foto, identidad y adjuntos de becas aceptan o derivan bytes no confiables. Los destinos observados en API/Core son BLOB de Oracle o Redis. El frontend Angular empaqueta assets públicos desde `src/assets` y `public`; la API sirve `Docs/contracts` en `/contracts` fuera de Production/Preproduction. No se identificó un flujo desde uploads hacia esas carpetas. La foto se devuelve por una acción de API autenticada que lee BLOB. No se inspeccionaron configuración efectiva de IIS/proxy, permisos de escritura del despliegue, artefacto publicado, integraciones externas de almacenamiento ni otros consumidores de Core. Por ello no se declara aún una exclusión global NOT_APPLICABLE.

El frontend tiene `.codegraph/` sin índice, sólo `.gitignore`; se usó `rg`. API y Core no tienen `.codegraph/`.

## Resultado por componente y conclusión

Frontend: los assets públicos del build provienen de rutas versionadas, sin upload hacia ellas localizado. API: los archivos revisados se guardan en BLOB/Redis; su único directorio servido directamente contiene contratos. Core: la imagen generada inspeccionada permanece en memoria. No se halló un camino desde archivo no confiable hacia carpeta pública ni una ruta que lo ejecute. El hosting real podría añadir mapeos o escrituras no versionados. Resultado NEEDS_REVIEW conforme a ADR-002, sin afirmar PASS, FAIL o NOT_APPLICABLE global.

## Hallazgos y propuesta documental

No hay defecto de ejecución confirmado. Riesgo condicionado: si el despliegue permite que una aplicación o integración escriba archivos no confiables en `/contracts` o en assets del frontend, deberá comprobarse el handler de acceso HTTP directo. Responsable candidato: operaciones/API. Propuesta para futura fase de fixes, sólo si ese montaje existe: separar uploads de directorios públicos y deshabilitar ejecución de código del servidor para esos archivos. No se distribuyó propuesta a otro repo: no hay fix concreto confirmado y `git worktree list` mostró sólo el monorepo.
