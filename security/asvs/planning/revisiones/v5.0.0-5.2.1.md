## Resultado por componente y conclusión

Frontend: limita y comprime para experiencia de usuario; el límite de seguridad depende de servidor. API: configura un techo global de 16 MiB para cuerpo de request en Kestrel y los flujos de persona delegan en Core. Core: limita los bytes aceptados por tipo; reconocimiento impone además un máximo configurable antes de Azure. Los valores son acotados y hay pruebas unitarias existentes de rechazo, pero no se ejecutaron y no hay evidencia de capacidad operativa ni comportamiento bajo concurrencia. Resultado `NEEDS_REVIEW` según ADR-002; no se atribuye un DoS confirmado ni PASS.

## Hallazgos y propuesta documental

- Observación de capacidad, pendiente de validar: el JSON base64 se materializa como `byte[]` antes del control por archivo y una carga de dos imágenes puede acercarse al límite de 16 MiB por request. Bajo concurrencia podría ejercer presión de memoria. Evidencia E1-E4; responsable candidato: API/infraestructura. Propuesta para fase posterior: medir rechazo de 16 MiB y consumo pico con cargas simultáneas representativas, revisar límites del hosting, y ajustar techo/concurrencia sólo según resultados. No hay fix de código sustentado aún.
- Observación de configuración: `ReconocimientoDocumento:MaxFileBytes` permite un máximo configurable; falta verificar valor efectivo por ambiente. E5. Responsable candidato: API/operaciones. Propuesta: registrar configuración efectiva sin secretos y probar sus bordes; el `FileValidator` conserva 5 MiB para imágenes.
- No se distribuyó propuesta a otro worktree: las acciones propuestas son verificaciones de capacidad y configuración, sin remediación concreta confirmada.
