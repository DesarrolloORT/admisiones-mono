# v5.0.0-3.5.1

## Identificación

- ID: v5.0.0-3.5.1. Nivel mínimo: L1.
- Texto oficial: "Verify that, if the application does not rely on the CORS preflight mechanism to prevent disallowed cross-origin requests to use sensitive functionality, these requests are validated to ensure they originate from the application itself. This may be done by using and validating anti-forgery tokens or requiring extra HTTP header fields that are not CORS-safelisted request-header fields. This is to defend against browser-based request forgery attacks, commonly known as cross-site request forgery (CSRF)."
- Interpretación local: el requisito es condicional. Primero hay que determinar si la aplicación *depende* del preflight CORS como defensa CSRF; solo si NO depende de él, corresponde exigir tokens anti-CSRF o un header adicional no CORS-safelisted. Si depende del preflight, el control exigible por el texto oficial para esa vía es el de v5.0.0-3.5.2 (siguiente en cola), no este.
- Pregunta concreta: ¿existe algún camino de estado mutante (sensible) alcanzable desde un origen cruzado no listado, sin que el navegador dispare un preflight CORS, y sin ningún otro control (token anti-CSRF, header no safelisted) que lo bloquee?
- Avance documental: DOCUMENTADO.
- Resultado de seguridad: NEEDS_REVIEW.
- Fecha de revisión: 2026-09-17.

## Resultado por componente y conclusión

- **API (`api-admisiones`)**: el diseño observado no implementa la vía que 3.5.1 exige de forma explícita (tokens anti-forgery o header adicional consistente no-safelisted) porque, según el comentario propio del código (E2) y el patrón de lectura de cookie (E1), el sistema fue diseñado para depender del preflight CORS con credenciales como defensa CSRF. Esa es una estrategia válida bajo ASVS, pero corresponde evaluarla con el criterio de **v5.0.0-3.5.2** ("si la app depende del preflight, verificar que no se puede invocar la funcionalidad sensible sin disparar preflight"), no con el de 3.5.1 en sentido estricto.
- No se encontró, dentro del código fuente propio inspeccionado, ninguna vía de "simple request" (GET mutante, `multipart/form-data`, `x-www-form-urlencoded` o `text/plain` en una mutación) que evadiera el preflight (E6, E7, E8). Si esa observación se sostiene, la condición "if the application does not rely on..." de 3.5.1 no se cumple (la app sí depende exclusivamente y efectivamente del preflight), por lo que 3.5.1 podría cerrarse como NOT_APPLICABLE — pero esa conclusión requiere la verificación positiva de 3.5.2 (que aún no se hizo) antes de darla por válida, y ninguna revisión estática de fuente sustituye una prueba de tráfico real.
- **Frontend (`admisiones`)**: consistente con el diseño anterior; no se detectaron llamadas que rompan el patrón "JSON + método no-simple" para operaciones mutantes.
- **Conclusión de esta ficha**: NEEDS_REVIEW. No se confirma un defecto de 3.5.1 en sí (no falta un control que el requisito exija para este diseño), pero tampoco se puede cerrar el requisito sin ejecutar la verificación runtime/negativa que corresponde a 3.5.2, de la cual 3.5.1 depende para saber cuál es el estándar de comparación correcto. Se documenta como NEEDS_REVIEW en lugar de PASS/NOT_APPLICABLE porque ADR-002 exige evidencia determinística reproducible, que aquí no existe (sólo lectura de código).

## Hallazgos y propuesta documental

- **Hallazgo 1 (deuda de diseño, no defecto confirmado)**: la defensa CSRF del sistema depende en su totalidad de la combinación "CORS con allowlist + credentials + Content-Type JSON/método no-simple", sin ninguna capa independiente (anti-forgery token o header fijo exigido server-side en cada endpoint mutante). Esto es arquitectónicamente frágil: un único cambio futuro (agregar un endpoint que acepte `multipart/form-data`, relajar `AddAnyHeader`/`WithOrigins`, o migrar un flujo a `sendBeacon`/`fetch` con `mode: 'no-cors'`) rompería la única barrera existente sin que ningún test lo detecte, dado que — según la ficha 3.4.2 — los tests de CORS existentes ya no reflejan la allowlist real y no fallarían ante una regresión a `AllowAnyOrigin()`.
  - Impacto: si se pierde la dependencia del preflight (por cualquiera de las vías anteriores), no queda ningún control CSRF de reemplazo; ASVS 3.5.1 exige explícitamente esa capa independiente para ese escenario.
  - Evidencia: E1-E7.
  - Responsable candidato: equipo API (propietario de `ServiceCollectionExtensions.AddCorsPolicy` y de los controladores).
  - Propuesta de cambio (para fase de remediación, no aplicada aquí): documentar explícitamente en ADR la decisión de depender del preflight CORS como control CSRF primario (o, alternativamente, agregar un header custom obligatorio validado server-side, p. ej. `X-Requested-With: XMLHttpRequest` verificado en un filtro/middleware global, como capa de defensa en profundidad independiente de la configuración CORS).
  - Validación futura: prueba de integración que envíe una request `multipart/form-data` o `GET` con side-effect simulado desde un origen no listado y confirme rechazo; prueba negativa de preflight (ver 3.5.2).
- No se registran hallazgos de defecto confirmado específicos de 3.5.1 en esta iteración; el hallazgo de tests de CORS desalineados ya está registrado en la ficha v5.0.0-3.4.2 (no se duplica aquí, se referencia).
