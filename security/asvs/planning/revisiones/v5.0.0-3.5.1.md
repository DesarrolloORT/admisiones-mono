# v5.0.0-3.5.1

## Identificación

- ID: v5.0.0-3.5.1. Nivel mínimo: L1.
- Texto oficial: "Verify that, if the application does not rely on the CORS preflight mechanism to prevent disallowed cross-origin requests to use sensitive functionality, these requests are validated to ensure they originate from the application itself. This may be done by using and validating anti-forgery tokens or requiring extra HTTP header fields that are not CORS-safelisted request-header fields. This is to defend against browser-based request forgery attacks, commonly known as cross-site request forgery (CSRF)."
- Interpretación local: el requisito es condicional. Primero hay que determinar si la aplicación *depende* del preflight CORS como defensa CSRF. Si NO depende, corresponde exigir una validación de que la request sale de la propia aplicación: token anti-CSRF, header no safelisted u otro control equivalente que valide el origen. La validación del `Origin` exacto es el control que la OWASP CSRF Cheat Sheet recomienda como complemento. Si depende del preflight, el control exigible para esa vía es el de v5.0.0-3.5.2.
- Pregunta concreta: ¿existe algún camino de estado mutante (sensible) alcanzable desde un origen cruzado no listado, sin preflight CORS y sin ningún control (token anti-CSRF, header no safelisted, validación de origen) que lo bloquee?
- Avance documental: DOCUMENTADO.
- Resultado de seguridad: NEEDS_REVIEW.
- Fecha de revisión: 2026-09-17; actualización: 2026-10-23.

## Resultado por componente y conclusión

- **API (`api-admisiones`)**:
  - Cambio de premisa: la aplicación ya **no depende solo del preflight** como defensa CSRF. Hay simple requests reales (5 multipart y 3 POST sin body, E5 y E6) y un control independiente que valida el origen de toda request no segura (E3), que es lo que 3.5.1 pide para ese caso. El control es global, se ejecuta antes de la autenticación y de los controllers, y usa la misma allowlist por ambiente que CORS.
  - Límites del control:
    - Acepta requests sin `Origin` ni `Sec-Fetch-Site`. Los navegadores modernos mandan al menos uno en un POST cross-site, pero un navegador muy antiguo podría no mandar ninguno.
    - Acepta `Sec-Fetch-Site: same-origin`, que se refiere al origen de la API y sirve para Swagger, que no está en Production/Preproduction.
    - No usa token anti-forgery (decisión documentada en E7).
- **Frontend**: no re-verificado. La evidencia de `86979de2` no describe el cliente que hoy usa multipart.
- **Conclusión**: NEEDS_REVIEW. El control que el requisito exige está implementado y hay tests de integración que lo cubren (E4), pero no se ejecutaron. Según ADR-002, la revisión estática con tests no ejecutados no da PASS. Para PASS falta ejecutar E4 (o una prueba equivalente en runtime) y verificar que ninguna acción mutante quede fuera del middleware.

## Hallazgos y propuesta documental

- **Hallazgo 1 (deuda de diseño): resuelto en 912fc665 (`73794742`).**
  - Condición original: la defensa CSRF dependía en su totalidad de «CORS + credentials + JSON/método no simple», sin capa independiente. Un endpoint multipart nuevo rompía esa única barrera.
  - Qué pasó: la regresión ocurrió (ADR-019, E5) y se corrigió con `UseOriginCheck` (E3), que es una capa independiente de la configuración CORS, con tests de pipeline (E4). La propuesta original (un header custom validado server-side) se reemplazó por la validación de `Origin` exacto, que la propia auditoría recomienda porque front y API son *same-site* (`security/reports/AUDITORIA-INTEGRACION-ANGULAR-ASPNET.md`, P0-1).
- **Observación nueva (residual, no defecto confirmado)**: `IsAllowedOrigin` deja pasar requests sin `Origin` ni `Sec-Fetch-Site` ([MiddlewarePipelineExtensions.cs:223-225](../../../../api-admisiones/WebApiAdmisiones/WebApiAdmisiones/Extensions/MiddlewarePipelineExtensions.cs#L223-L225)). Es intencional, para clientes no navegador.
  - Impacto: un navegador que no mande ninguno de los dos headers no estaría protegido. No se identificó un navegador soportado con ese comportamiento.
  - Responsable candidato: equipo API.
  - Propuesta (no aplicada): documentar la matriz de navegadores soportados, o exigir `Authorization: Bearer` a los clientes no navegador y rechazar la request sin headers cuando trae cookie de sesión.
  - Validación futura: ejecutar E4 y agregar un caso «cookie de sesión sin `Origin` ni `Sec-Fetch-Site`» para dejar explícito el comportamiento.
- **Observación nueva (cobertura de test)**: E4 cubre 7 acciones. No hay un test de arquitectura que recorra todas las acciones mutantes y falle si alguna queda fuera del control. La propuesta T-1 de la auditoría no se implementó, pero hoy el middleware es global y no depende de cada acción.
