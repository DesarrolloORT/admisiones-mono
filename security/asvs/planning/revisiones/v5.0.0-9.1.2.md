# v5.0.0-9.1.2 — allowlist de algoritmos de tokens autocontenidos

## Identificación

- ID: v5.0.0-9.1.2; nivel mínimo L1.
- Texto oficial íntegro: “Verify that only algorithms on an allowlist can be used to create and verify self-contained tokens, for a given context. The allowlist must include the permitted algorithms, ideally only either symmetric or asymmetric algorithms, and must not include the 'None' algorithm. If both symmetric and asymmetric must be supported, additional controls will be needed to prevent key confusion.”
- Interpretación local: cada contexto que emite o acepta JWT debe restringir explícitamente los algoritmos de firma aceptables; no basta que el emisor actual genere HS256.
- Pregunta: ¿cada validador de JWT autocontenidos de la API tiene una allowlist explícita, coherente con su emisor y sin `None` ni mezcla simétrica/asimétrica?
- Avance: DOCUMENTADO. Resultado: FAIL. Fecha: 2026-09-22.

## Aplicabilidad y alcance

Se incluyeron dos contextos que aceptan JWT en la API: el bearer de acceso, recibido por cookie HttpOnly o encabezado `Authorization`, y los enlaces/sesiones temporales de activación de contraseña. Se revisaron también sus emisores para contrastar el algoritmo emitido.

El JWT HS256 que `TokenServiceInternalApi` emite para Inscripciones y Pagos es un boundary saliente: el receptor no está disponible en este monorepo y no se puede evaluar su allowlist. Los refresh tokens son opacos y no se incluyeron. No se inspeccionaron proxy/gateway, configuraciones efectivas ni runtime.

## Resultado por componente y conclusión

- API, bearer de acceso: evidencia estática favorable; hay allowlist explícita de HS256 y emisor consistente.
- API, activación y sesiones temporales: incumplimiento documental. El validador compartido no define allowlist de algoritmos, aunque el emisor actual use HS256.
- API externa de Inscripciones y Pagos: pendiente de evaluación del receptor del token saliente.

Resultado global: DOCUMENTADO / FAIL. Un contexto entrante relevante carece de la allowlist explícita requerida. La prueba de comportamiento y la configuración efectiva siguen pendientes; no cambian la observación de que la fuente no declara dicha allowlist.

## Hallazgos y propuesta documental

1. Condición: `PasswordActivationService.ValidateJwt` acepta tokens de activación/sesión con validación de firma, pero no declara `ValidAlgorithms` ni un validador equivalente. Impacto: la política de algoritmo queda implícita en la biblioteca y la clave, sin el control explícito y revisable que exige ASVS para evitar algoritmos no previstos o confusión futura. Evidencia: E3 y E4. Responsable candidato: API/Authentication. Propuesta para fase posterior: definir una allowlist única `[SecurityAlgorithms.HmacSha256]` para ese contexto y probar rechazo de `None`, HS384 y un algoritmo asimétrico. Validar con pruebas directas del flujo y de `ValidateSessionToken`. No se aplicó fix ni se distribuyó propuesta a ramas `fix/owasp`.
2. Condición: no se dispone del receptor del JWT de servicio de Inscripciones/Pagos. Impacto: no puede verificarse su política de algoritmos. Evidencia: E6. Responsable candidato: equipo propietario de la API destino. Propuesta: inventariar el receptor, su configuración de validación y pruebas de algoritmo no permitido.
