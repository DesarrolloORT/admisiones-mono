# v5.0.0-9.1.2 — allowlist de algoritmos de tokens autocontenidos

## Identificación

- ID: v5.0.0-9.1.2; nivel mínimo L1.
- Texto oficial íntegro: “Verify that only algorithms on an allowlist can be used to create and verify self-contained tokens, for a given context. The allowlist must include the permitted algorithms, ideally only either symmetric or asymmetric algorithms, and must not include the 'None' algorithm. If both symmetric and asymmetric must be supported, additional controls will be needed to prevent key confusion.”
- Interpretación local: cada contexto que emite o acepta JWT debe restringir explícitamente los algoritmos de firma aceptables; no basta que el emisor actual genere HS256.
- Pregunta: ¿cada validador de JWT autocontenidos de la API tiene una allowlist explícita, coherente con su emisor y sin `None` ni mezcla simétrica/asimétrica?
- Avance: DOCUMENTADO. Resultado: FAIL. Fecha de revisión: 2026-09-22; actualización: 2026-10-23.

## Aplicabilidad y alcance

Se incluyeron dos contextos que aceptan JWT en la API: el bearer de acceso (cookie HttpOnly o `Authorization`) y los enlaces/sesiones temporales de contraseña, que desde la revisión anterior también reciben enlaces firmados por el backoffice (claim `idSolicitudAlta`, ADR-030). Se revisaron sus emisores para contrastar el algoritmo emitido.

El JWT HS256 que `TokenServiceInternalApi` emite para Inscripciones y Pagos es un boundary saliente cuyo receptor no está disponible. Los refresh tokens son opacos. No se inspeccionaron proxy/gateway, el emisor backoffice, configuraciones efectivas ni runtime.

## Resultado por componente y conclusión

- API, bearer de acceso: evidencia estática favorable; allowlist explícita HS256 y emisor consistente.
- API, activación/sesión temporal (incluido el enlace de backoffice): incumplimiento documental vigente en 912fc665. `ValidateJwt` no define allowlist de algoritmos.
- API externa de Inscripciones y Pagos y emisor backoffice: pendientes de evaluación.

Resultado global: DOCUMENTADO / FAIL. Un contexto entrante relevante, que ahora además recibe tokens de un emisor externo, carece de la allowlist explícita requerida.

## Hallazgos y propuesta documental

1. Condición (vigente en 912fc665): `PasswordActivationService.ValidateJwt` acepta tokens de activación/sesión validando firma, pero no declara `ValidAlgorithms` ni un validador equivalente. Impacto: la política de algoritmo queda implícita en la biblioteca y la clave, ahora también para tokens emitidos por un sistema externo (backoffice). Evidencia: E3, E4, E6. Responsable candidato: API/Authentication (y equipo backoffice para el algoritmo emitido). Propuesta para fase posterior: definir `ValidAlgorithms = [SecurityAlgorithms.HmacSha256]` en `ValidateJwt`, acordar con el backoffice el algoritmo, y probar rechazo de `None`, HS384 y un algoritmo asimétrico en enlace propio, enlace de backoffice y sesión. No se aplicó fix ni se distribuyó propuesta a ramas `fix/owasp`.
2. Condición: no se dispone del receptor del JWT de servicio de Inscripciones/Pagos. Impacto: no puede verificarse su política de algoritmos. Evidencia: E7. Responsable candidato: equipo propietario de la API destino. Propuesta: inventariar el receptor, su configuración y pruebas de algoritmo no permitido.

## Cambios respecto de la revisión anterior

- Las líneas de `ValidateJwt` y del emisor de activación cambiaron (L439–454, L403–429), pero el validador sigue sin `ValidAlgorithms`: el hallazgo 1 no se corrigió.
- El validador ahora también acepta enlaces de backoffice (ADR-030, `980b688a`/`aadcda6f`), lo que amplía el impacto del hallazgo a tokens de un emisor externo.
- La emisión del access token pasa por `SessionTokenIssuer` (912fc665) sin cambiar el algoritmo; los secretos se leen de `IConfiguration`/Key Vault (`60c05999`), sin efecto sobre la allowlist.
- Resultado anterior → actual: FAIL → FAIL.
