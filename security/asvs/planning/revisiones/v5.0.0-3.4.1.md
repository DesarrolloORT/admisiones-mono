# v5.0.0-3.4.1

## Identificación

- ID: v5.0.0-3.4.1. Nivel mínimo: L1.
- Texto oficial (JSON fuente, `V3.4.1`): "Verify that a Strict-Transport-Security header field is included on all responses to enforce an HTTP Strict Transport Security (HSTS) policy. A maximum age of at least 1 year must be defined, and for L2 and up, the policy must apply to all subdomains as well."
- Interpretación local: para L1 alcanza con `Strict-Transport-Security` presente en todas las respuestas HTTPS con `max-age >= 31536000`; `includeSubDomains` es exigencia adicional de L2, no de L1, pero si ya está presente no perjudica la evaluación L1.
- Pregunta concreta: ¿toda respuesta HTTPS servida por los componentes propios (API, frontend) incluye `Strict-Transport-Security` con `max-age` de al menos un año, de forma determinística y sin que otro middleware/config lo sobrescriba con un valor menor?
- Avance documental: DOCUMENTADO.
- Resultado de seguridad: NEEDS_REVIEW.
- Fecha de revisión: 2026-09-17.

## Resultado por componente y conclusión

- **API**: no se puede concluir PASS por lectura estática. Existe un valor conforme (`UseSecurityHeaders`, 1 año + subdominios + preload) pero coexiste con el middleware estándar `UseHsts()`, cuyo callback de escritura tardía puede sobrescribirlo con el default de 30 días sin subdominios según la topología real de despliegue (TLS terminado en la propia app vs. detrás de proxy). Sin una prueba de integración que capture la respuesta HTTPS final, o sin confirmar la topología de red de cada ambiente, el resultado es NEEDS_REVIEW y no PASS, conforme ADR-002 (revisión de IA sin evidencia determinística no produce PASS).
- **Frontend / docs-site**: la configuración IIS versionada en el repo cumple el mínimo L1 (y la cláusula L2 de subdominios) si se despliega sin modificaciones; falta confirmar el `web.config` generado realmente en cada ambiente.
- **Conclusión general del requisito**: NEEDS_REVIEW. El riesgo concreto (posible degradación del header HSTS en la API a 30 días sin subdominios) es plausible bajo una topología de despliegue específica y no fue descartado ni confirmado por este análisis estático.

## Hallazgos y propuesta documental

1. **Redundancia de middlewares HSTS con posible sobrescritura silenciosa (API).**
   - Condición concreta: `ConfigureMiddlewarePipeline` registra tanto `app.UseHsts()` (línea 26, ambientes no-Development) como `UseSecurityHeaders()` (línea 47, incondicional), y `UseHsts()` se agrega antes de `UseForwardedHeaders()`. El header final `Strict-Transport-Security` que llega al cliente depende de si el callback `OnStarting` de `HstsMiddleware` llega a ejecutarse (esquema HTTPS visto por la app en el momento de invocar `UseHsts()`).
   - Impacto: si la API recibe TLS directamente (o el proxy no está configurado para reenviar el esquema antes de este punto), el header de 1 año/subdominios/preload podría degradarse silenciosamente al default de ASP.NET Core (30 días, sin subdominios), incumpliendo V3.4.1 en producción sin que ningún test lo detecte.
   - Evidencia: E1, E2, E4.
   - Responsable candidato: equipo API (api-admisiones), propietario de `MiddlewarePipelineExtensions.cs`.
   - Propuesta de cambio (documental, no aplicada): eliminar la dependencia del comportamiento por defecto de `UseHsts()` — o bien remover `app.UseHsts()` y depender únicamente de `UseSecurityHeaders()` (que ya fija el valor correcto de forma explícita e incondicional), o bien configurar explícitamente `services.AddHsts(o => { o.MaxAge = TimeSpan.FromDays(365); o.IncludeSubDomains = true; o.Preload = true; })` para que ambos middlewares coincidan y el resultado sea determinístico sin importar el orden de ejecución. Agregar un test de integración (`TestServer`/`WebApplicationFactory`) que ejecute el pipeline completo sobre una request HTTPS y aserte el valor final de `Strict-Transport-Security`, cerrando el gap que dejan los tests unitarios actuales (E3).
   - Validación futura: confirmar en runtime/staging con una request HTTPS real (o revisando logs de headers del proxy) cuál es el valor efectivo enviado al cliente en Production/Preproduction.

2. **Deuda, no defecto: dependencia no verificada de la topología de reenvío de esquema.** `UseForwardedHeaders` se registra sin `KnownProxies`/`KnownNetworks` explícitos y después de `UseHsts()`; el comportamiento de ambos middlewares frente al esquema real (HTTP interno vs HTTPS directo) no está documentado en el repo. Esto afecta tanto al hallazgo 1 como potencialmente a otros requisitos que dependen de `context.Request.IsHttps`/`X-Forwarded-Proto` (fuera del alcance de este punto; anotado como dependencia).
