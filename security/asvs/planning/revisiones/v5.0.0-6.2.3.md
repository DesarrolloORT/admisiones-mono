## Aplicabilidad y alcance

Aplica al cambio voluntario de contraseña de una persona autenticada: formulario Angular → POST /person/change-password → caso de uso People → Core → servicio SOAP LDAP. El sujeto se toma del token, no del body. La recuperación de contraseña y el alta usan operaciones de restablecimiento sin contraseña actual; son flujos distintos y no se usan como evidencia de este control. No se inspeccionó el código del proveedor SOAP/LDAP, otros consumidores de Core, ni el despliegue o las peticiones HTTP reales.

## Resultado por componente y conclusión

Frontend presenta y envía ambos valores. API exige ambos campos en el contrato y su lógica rechaza una contraseña actual vacía antes de llamar a Core. Core incluye ambos en la petición SOAP y propaga un resultado negativo. La parte decisiva —que el proveedor rechace una contraseña actual incorrecta y no cambie la contraseña en ese caso— no se puede comprobar leyendo el cliente SOAP. Resultado compartido: NEEDS_REVIEW; no se atribuye una vulnerabilidad confirmada ni PASS global.

## Hallazgos y propuesta documental

No se confirmó un defecto de implementación propio de este punto. La dependencia de seguridad es el comportamiento del proveedor SOAP/LDAP: si éste aceptara un valor anterior incorrecto, una sesión autenticada podría cambiar la contraseña sin demostrar conocimiento de la actual. Responsable candidato: equipo de identidad/API. Propuesta para fase posterior: verificar el contrato y la implementación del proveedor y ejecutar pruebas negativas controladas; corregir el límite responsable sólo si se confirma que acepta una contraseña anterior incorrecta. No hay fix concreto ni propuesta distribuida a worktrees fix/owasp.

## Pendientes y dependencias

- Identidad/API: aportar contrato o implementación del servicio SOAP CambiarPassword y comprobar que valida viejoPassword para el usuario indicado; no registrar credenciales en la evidencia.
- Identidad/API: en ambiente de ensayo, invocar el endpoint autenticado con contraseña actual incorrecta y nueva válida; comprobar rechazo y que la contraseña anterior sigue funcionando. Repetir con la actual correcta y comprobar autenticación posterior con la nueva. Esta evidencia decide PASS/FAIL.
- API: verificar por HTTP que omitir, enviar null o dejar vacía cada contraseña produce rechazo sin llamar al proveedor. Los atributos y tests aislados leídos no sustituyen esa prueba de integración.
- Ejecutar los tests existentes en una fase autorizada; su ejecución aislada no demostraría la verificación del proveedor.
- Relación: [6.2.2](./v5.0.0-6.2.2.md) cubre disponibilidad del cambio. Recuperación y contraseña inicial usan ForzarCambiarPasswordAsync y requieren análisis en sus propios requisitos, sin extender este resultado.
