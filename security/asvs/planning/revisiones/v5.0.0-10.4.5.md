# v5.0.0-10.4.5 — Replay de refresh token para clientes públicos OAuth

## Identificación

- **ID y nivel mínimo:** v5.0.0-10.4.5 (L1).
- **Texto oficial:** "Verify that the authorization server mitigates refresh token replay attacks for public clients, preferably using sender-constrained refresh tokens, i.e., Demonstrating Proof of Possession (DPoP) or Certificate-Bound Access Tokens using mutual TLS (mTLS). For L1 and L2 applications, refresh token rotation may be used. If refresh token rotation is used, the authorization server must invalidate the refresh token after usage, and revoke all refresh tokens for that authorization if an already used and invalidated refresh token is provided."
- **Interpretación local:** cuando un componente opere un authorization server OAuth para clientes públicos, debe impedir el replay de sus refresh tokens mediante constricción al emisor o rotación con invalidación tras el uso y revocación de la autorización ante reutilización.
- **Pregunta:** ¿algún componente del monorepo opera un authorization server OAuth para clientes públicos y mitiga el replay de sus refresh tokens conforme al requisito?
- **Avance documental:** DOCUMENTADO.
- **Resultado de seguridad:** NOT_APPLICABLE para los componentes del monorepo inspeccionados.
- **Fecha de revisión:** 2026-09-23; actualización: 2026-10-23.

## Aplicabilidad y alcance

El requisito es condicional al rol de authorization server OAuth con refresh tokens para clientes públicos. Las fichas [`v5.0.0-10.4.1`](./v5.0.0-10.4.1.md) a [`v5.0.0-10.4.4`](./v5.0.0-10.4.4.md), actualizadas contra 912fc665, no localizan ese rol en el monorepo.

La API implementa una sesión propietaria: recibe un refresh token desde la cookie `X-Refresh-Token`, busca su hash activo y emite un par nuevo mediante `SessionTokenIssuer` (912fc665). Desde `73794742`, el refresh no extiende la sesión más allá del vencimiento original, rechaza personas que ya no pueden tener sesión y el cambio de contraseña revoca el refresh vigente. Nada de esto convierte a la API en authorization server OAuth ni al navegador en cliente público OAuth; la rotación se conserva como observación de sesión.

No se evaluaron gateway, LDAP, Inscripciones/Pagos, backoffice, un IdP ni configuración de plataforma.

## Resultado por componente y conclusión

- **API:** NOT_APPLICABLE para este requisito OAuth. Renovación de sesión propia, no authorization server para clientes públicos.
- **Frontend:** NOT_APPLICABLE según la evidencia de `86979de2`, no re-verificada.

La rotación propietaria mejoró desde la revisión anterior (sin extensión de sesión, revocación por cambio de contraseña y por persona inhabilitada), pero sigue sin detección de reuse ni consumo atómico ante dos renovaciones concurrentes. Son límites para la revisión de gestión de sesión (V7), no un FAIL de `v5.0.0-10.4.5`. No se ejecutaron tests, builds, runtime ni scans.

## Hallazgos y propuesta documental

Sin hallazgo aplicable al authorization server OAuth. Observación no concluyente del flujo propietario (vigente): el modelo reemplaza un único registro por persona/sistema y no conserva historial ni marca el token presentado como reutilizado; un replay concurrente del mismo refresh podría obtener dos pares válidos hasta el siguiente reemplazo. Responsable candidato: `api-admisiones`.

Propuesta documental futura: en la revisión de sesión, definir el modelo deseado de reuse y concurrencia (consumo condicional `UPDATE ... WHERE TokenHash = :hash AND IsActive = 'SI'` o equivalente, y revocación de la sesión ante reuse) y validarlo con Oracle real. No se aplicó ningún cambio.
