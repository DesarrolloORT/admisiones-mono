# v5.0.0-10.4.5 — Replay de refresh token para clientes públicos OAuth

## Identificación

- **ID y nivel mínimo:** v5.0.0-10.4.5 (L1).
- **Texto oficial:** "Verify that the authorization server mitigates refresh token replay attacks for public clients, preferably using sender-constrained refresh tokens, i.e., Demonstrating Proof of Possession (DPoP) or Certificate-Bound Access Tokens using mutual TLS (mTLS). For L1 and L2 applications, refresh token rotation may be used. If refresh token rotation is used, the authorization server must invalidate the refresh token after usage, and revoke all refresh tokens for that authorization if an already used and invalidated refresh token is provided."
- **Interpretación local:** cuando un componente opere un authorization server OAuth para clientes públicos, debe impedir el replay de sus refresh tokens mediante constricción al emisor o rotación con invalidación tras el uso y revocación de la autorización ante reutilización.
- **Pregunta:** ¿algún componente del monorepo opera un authorization server OAuth para clientes públicos y mitiga el replay de sus refresh tokens conforme al requisito?
- **Avance documental:** DOCUMENTADO.
- **Resultado de seguridad:** NOT_APPLICABLE para los componentes del monorepo inspeccionados.
- **Fecha de revisión:** 2026-09-23.

## Aplicabilidad y alcance

El requisito es condicional al rol de authorization server OAuth y, específicamente, a refresh tokens emitidos para clientes públicos OAuth. La revisión precedente [`v5.0.0-10.4.4`](./v5.0.0-10.4.4.md) no localizó en el monorepo endpoint OAuth de autorización o token, registro de clientes, metadata de grants, `client_id`, `response_type`, `redirect_uri` ni `grant_type=authorization_code`.

La API sí implementa una sesión propietaria: recibe un refresh token desde la cookie `X-Refresh-Token`, lo compara con el hash persistido y emite un par nuevo. El frontend sólo invoca esa ruta con credenciales de cookie. Esto no la convierte en authorization server OAuth ni al navegador en un cliente público OAuth: no hay cliente OAuth registrado ni token endpoint de dicho protocolo. La rotación local se conserva como observación de sesión, no como evidencia de cumplimiento OAuth.

No se evaluaron gateway, LDAP, Inscripciones/Pagos, un IdP separado ni configuración de plataforma. Si alguno emite refresh tokens OAuth para clientes públicos en representación de Admisiones, queda fuera de este resultado.

## Resultado por componente y conclusión

- **API:** NOT_APPLICABLE para este requisito OAuth. Expone una renovación de sesión propia, no un authorization server OAuth que emita refresh tokens para clientes públicos.
- **Frontend:** NOT_APPLICABLE. Consume la renovación propietaria por cookie y no se comporta como cliente público OAuth.
- **Core:** NOT_APPLICABLE dentro del alcance del inventario estático; no se localizó componente OAuth/OIDC en la versión fijada.
- **Integraciones externas:** fuera del alcance disponible. No se transfiere este resultado al IdP, gateway ni a Inscripciones/Pagos.

La rotación propietaria reemplaza el hash almacenado y por ello puede rechazar el token anterior después de una rotación serial, pero no demuestra las condiciones de este control OAuth. En particular, no hay evidencia de detección de reuse ni de una operación atómica ante dos renovaciones concurrentes; son límites a validar en la revisión de gestión de sesión correspondiente, no un FAIL de `v5.0.0-10.4.5`.

No se ejecutaron tests, builds, runtime, escaneos ni cambios de código o configuración.

## Hallazgos y propuesta documental

No se identificó un hallazgo aplicable al authorization server OAuth, porque no se evidenció tal rol en el monorepo. Como observación no concluyente del flujo propietario, la interfaz describe “revocar tokens activos anteriores” pero la implementación reemplaza un único registro y no conserva historial ni marca explícitamente el token presentado como reutilizado. Responsable candidato: `api-admisiones`.

Propuesta documental futura: al revisar gestión de sesión, especificar el modelo deseado para reuso y concurrencia de refresh tokens, y validar con Oracle real una carrera de dos usos del mismo token. Si la arquitectura confirma un authorization server externo, copiar esta propuesta al repositorio responsable y evaluar DPoP/mTLS o la rotación/revocación exigida allí. No se aplicó ningún cambio.

## Pendientes y dependencias

1. **Inventario de servicios externos:** arquitectura/integraciones debe confirmar si gateway, LDAP, un IdP, Inscripciones/Pagos u otro servicio opera OAuth/OIDC para usuarios de Admisiones. Método: arquitectura aprobada y contrato/deployment sin secretos. Si existe authorization server, revisar allí `v5.0.0-10.4.5` con clientes públicos reales y evidencia de replay.
2. **Validación de sesión propietaria:** `api-admisiones` debe aportar una prueba reproducible contra Oracle y el host representativo: uso inicial, reuso secuencial y dos renovaciones simultáneas del mismo refresh token. Determinar si el modelo debe revocar toda la sesión ante reuse. Esta evidencia no cambia la no aplicabilidad OAuth sin confirmar antes ese rol.
3. **Confirmación operativa opcional:** plataforma puede aportar una exportación sin credenciales de las rutas del gateway para confirmar que no publica `authorize`/`token` OAuth en representación de esta aplicación.
4. **Dependencias relacionadas:** [`v5.0.0-10.4.4`](./v5.0.0-10.4.4.md) documenta la ausencia de authorization server y configuración de grants en el monorepo. La observación de sesión no reabre ni modifica resultados anteriores; los controles V7 conservan su propia revisión.

No hay propuesta distribuida: no se confirmó un repositorio responsable de un authorization server externo.
