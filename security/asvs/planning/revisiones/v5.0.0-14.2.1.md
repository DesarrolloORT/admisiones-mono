# ASVS v5.0.0-14.2.1 — Sensitive Data in URLs

## Identificación

- **ID y nivel mínimo:** v5.0.0-14.2.1 (L1).
- **Texto oficial:** “Verify that sensitive data is only sent to the server in the HTTP message body or header fields, and that the URL and query string do not contain sensitive information, such as an API key or session token.”
- **Interpretación local:** tokens de activación, recuperación o sesión, credenciales, PII y parámetros de pago sensibles no deben viajar en path o query hacia el frontend, la API ni terceros; deben usarse cuerpo o headers cuando se envían al servidor.
- **Pregunta verificable:** ¿los flujos reales evitan enviar datos sensibles, en particular tokens de activación/recuperación y parámetros de pago, en URL o query string?
- **Avance documental y resultado de seguridad:** DOCUMENTADO / FAIL.
- **Fecha de revisión:** 2026-09-23.

## Aplicabilidad y alcance

Aplica a las URLs de navegación Angular, las solicitudes HTTP de la API y los redireccionamientos o formularios hacia pasarelas de pago. Se trataron como sensibles el JWT recibido por correo para activación/recuperación —el propio contrato lo marca `[Redact]`— y `parametrosEncriptados`, cuyo contenido y sensibilidad frente a la pasarela externa no son verificables desde este monorepo.

Se revisaron los flujos de activación/recuperación y pago externo, junto con las queries de catálogo y navegación local localizadas. Los IDs de producto, proceso, oferta, estado, `flow` y `isPrimaryPhone` observados no se clasifican aquí como secretos por sí solos. No se inventarió cada URL construida por dependencias, emails efectivamente emitidos, proxies, CDN, historial del navegador ni la pasarela de pagos.

## Resultado por componente y conclusión

- **API — FAIL:** el generador de enlaces de activación/recuperación incorpora un JWT sensible en `?token=…`. La codificación URL, la vigencia, el hash en Redis y el canje posterior no satisfacen el requisito de que ese dato no esté en URL/query.
- **Frontend — FAIL compartido:** consume el token desde la query que recibió el navegador. Luego lo canjea en cuerpo y limpia la barra de direcciones, una mitigación posterior insuficiente respecto del enlace inicial.
- **Pago externo — NEEDS_REVIEW:** el recorrido propio usa `POST` para `parametrosEncriptados`, señal favorable; sigue sin evidencia del contrato de la pasarela, contenido del blob, URL de retorno y comportamiento efectivo.
- **Core — sin evidencia directa aplicable.**

**Conclusión: FAIL.** La presencia comprobada de un JWT de activación/recuperación en la query del enlace de correo contradice directamente V14.2.1. La evidencia positiva de redacción de telemetría y envío por cuerpo posterior no compensa esa exposición inicial.

## Hallazgos y propuesta documental

### H-14.2.1-01 — Token de activación/recuperación en query string

- **Condición e impacto:** `BuildLink` emite el JWT en `?token=…`; al abrir el mail, el secreto puede quedar expuesto a historial, logs de acceso, proxy/CDN, analítica o referer según el ambiente. El token autoriza iniciar la activación o recuperación de contraseña.
- **Evidencia:** E2–E4.
- **Responsables candidatos:** API de autenticación y frontend de activación; plataforma debe aportar alcance de logs/proxy/CDN.
- **Propuesta futura:** rediseñar la entrega/canje del token para que el secreto no viaje en URL/query; definir el mecanismo con producto, UX y seguridad y actualizar contratos/pruebas. No se aplicó ningún cambio.
- **Validación futura:** prueba controlada que inspeccione URL, historial, `Referer`, logs de frontend/API/proxy/CDN y correo de prueba, verificando que ningún token ni PII sea persistido o retransmitido.

## Pendientes y dependencias

1. Autenticación/producto: definir y aprobar un mecanismo de activación y recuperación sin token en URL; conservar compatibilidad y expiración/uso único como requisitos del rediseño.
2. Plataforma/observabilidad: aportar configuraciones y muestras redaccionadas de IIS/proxy/CDN, analítica y logs de acceso para medir exposición histórica y efectiva del parámetro `token`.
3. Pagos: aportar contrato de la pasarela, clasificación de `parametrosEncriptados`, URL de retorno y captura controlada que confirme que el `POST` no deriva el blob a URL/query.
4. V7 y V9: coordinar cualquier cambio con las revisiones de sesión y tokens; no reutilizar este FAIL como conclusión de todos los mecanismos de sesión.
