# Auditoría de errores — Sistema de Admisiones

> Estado: relevamiento **COMPLETO** (Fases 1-7 + entregables) + **rondas 1, 2 y 3 de correcciones de frontend aplicadas** (ver Bitácora). El relevamiento original fue de solo lectura, salvo la inicialización del submódulo git `Core` en `api-admisiones` (clonado desde el remoto configurado, sin cambios de contenido).
>
> **Objetivo de las rondas de corrección**: bajar la cantidad de mensajes remapeados o inventados en el frontend, para que cuando se reporten errores a Análisis Funcional el texto que ve el usuario provenga ~99% del backend. Cada remapeo que sobreviva en el frontend debe ser, o una decisión deliberada documentada, o un hueco del contrato del backend — y por eso se listan aparte en "Remapeos de frontend restantes".

## Bitácora de cambios

### Ronda 3 — 2026-09-15 · hallazgos HIGH/MEDIUM de frontend fuera de los "10 puntos"

Repo `admisiones`, rama `v1.0.0/fix/apiMessages`, cambios todavía sin commit. A diferencia de las rondas 1 y 2 (que cerraban puntos que descartaban un mensaje ya disponible del backend), esta ronda ataca hallazgos de calidad de error-handling que quedaban fuera de esa cuenta: mensajes calculados pero nunca renderizados, catálogos que degradan en silencio total, y control de flujo frágil.

**HIGH**

1. **FE-ENR-018**: `catalogError` de `EnrollmentSurveyOptionsFacade` se calculaba pero no se renderizaba en ningún `.html`. Ahora se muestra en `enrollment-personal-step` con `app-error-alert`.
2. **FE-HOME-006**: reactivar una inscripción "Dada de baja" tragaba el error HTTP en silencio (`error: () => this.isReactivating.set(false)`). Ahora `dashboard-quick-actions.ts` muestra el mensaje del backend vía `getApiErrorMessage`.
3. **FE-CAT-002**: los 5 puntos de carga en cascada de `AcademicProposalSelection` (seminarios, comienzos, turnos) degradaban a `[]` sin avisar. Ahora todos reportan al `catalogError` ya renderizado por FE-CAT-001, y se limpia el mensaje al cambiar de selección para no dejar un error viejo pegado.

**MEDIUM**

4. **FE-AUTH-027**: `phoneValidator` del registro trataba cualquier error de red/servidor como "teléfono válido" (fail-open). Ahora bloquea el control con `phoneValidation` y muestra el mensaje del backend, mismo patrón que FE-HOME-007 (ronda 2).
5. **FE-AUTH-029**: el límite de archivo "5 MB" estaba hardcodeado en el mensaje de error, desincronizable de `MAX_IMAGE_SIZE_BYTES`. Ahora el mensaje deriva el valor de esa constante.
6. **FE-ENR-012**: `enrollment-survey.ts` usaba `throw new Error('identity-save')` y comparaba `error.message` como control de flujo. Reemplazado por una clase `IdentitySaveError` y `error instanceof IdentitySaveError`.
7. **FE-ENR-010**: la carga inicial de encuesta clasificaba cualquier error (401/403/500/red) en el mismo mensaje genérico, descartando el mensaje real del backend. Se hizo viajar el mensaje desde `resolveInitialSurvey` (nuevo campo `loadFailedMessage`) hasta `EnrollmentSurveyFacade.surveyLoadError()`.
8. **FE-ENR-014**: la confirmación de preinscripción mostraba un mensaje fijo para cualquier fallo no ambiguo. Ahora usa `getApiErrorMessage` (la rama de fallo ambiguo y la de identidad no tocada por backend siguen con sus textos propios, son decisiones de negocio).
9. Catálogos silenciosos de `EnrollmentSurveyOptionsFacade` (departamentos e instituciones, parte del patrón FE-ENR-020): ambos reportan ahora al `catalogError` compartido de la encuesta en vez de degradar sin avisar.

**Cleanup Candidate #7**: código muerto en `enrollment-proposal.ts` (`registerProductInterest` nunca emitía `false`, confirmado en `enrollments.api.ts`). `registerProductInterest` pasó a `Observable<void>` y se eliminó la rama `if (!registered)`.

**Verificación (2026-09-15)**: 951 → **962 tests**, todos verdes (incluye 17 tests nuevos/actualizados de esta ronda). `tsc --noEmit` limpio, `prettier --check` limpio, `eslint` limpio en los archivos tocados, `check-comment-noise` sin hallazgos.

### Ronda 1 — 2026-09-10 · unificación del criterio de mensajes (frontend)

Repo `admisiones`, rama `v1.0.0/fix/apiMessages`, commit `9e7cb92` ("feat: implement unified backend error messaging policy and update error handling across components"). El backend (`api-admisiones`, rama `testing`) no cambió respecto del relevamiento: su último commit es del 2026-08-27, anterior a esta auditoría.

**Qué se implementó**

1. **`APP_API_ERROR_POLICY`** (`src/app/core/services/api-error-policy.ts`), inyectada vía `provideOrtApiErrorHandling({ config: { errorPolicy: ... } })` en `app.config.ts:76-78`. Reabilita `useBackendMessage: true` para `400/401/403/404/409/422/429`, que la política default de `@desarrolloort/ngx-utils` descartaba en `401/403/404`. El `defaultMessage` de la librería queda solo como fallback para respuestas sin `message`.
2. **`getApiErrorMessage(error, fallback)`** promovido de `features/auth/models/` a `src/app/shared/errors/api-error-message.ts` y adoptado como único lector de errores de API en pantallas y facades (15 puntos de uso). El `fallback` es para errores que no son de API, no para pisar al backend.
3. **`CUSTOM_ERROR_MESSAGES` eliminado del código de producción** (0 usos fuera de specs). Era el mecanismo de mayor precedencia sobre la política y el menos visible desde la pantalla.
4. **`EnrollmentPaymentResponse` perdió `success`/`message`/`errorCode`**: el rechazo de pago viaja por el canal de error, porque `operationResultInterceptor` convierte `success:false` en `NormalizedApiError` incluso con HTTP `2xx`.

**Decisión explícita: los `5xx` quedan fuera de la política.** El normalizador de la librería fuerza texto genérico para cualquier status `>= 500` y el backend oculta el detalle real en producción. Esa es la barrera que hoy contiene los hallazgos CRITICAL de fuga de mensajes crudos (LDAP, Azure Document Intelligence, API de Inscripciones y Pagos) — no debe abrirse antes de sanear el backend.

## FASE 1 — Arquitectura

### Repositorios y stack

|              | Frontend — `admisiones`                                    | Backend — `api-admisiones`                                             |
| ------------ | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| Stack        | Angular ^22, RxJS 7.8, Angular Material ^22                | .NET 10 (ASP.NET Core), EF Core 10, Serilog, OpenTelemetry             |
| HTTP         | `HttpClient` + wrapper propio `ApiHttpClient`              | Controllers `[ApiController]` sobre `ApiBaseController<T>`             |
| Arquitectura | Features con `api/*.api.ts` adapters → contratos generados | `AppLogic.*` (12 módulos) → `BusinessLogic` → `DataAccess` (Devart/EF) |

### Mecanismos globales de error

**Frontend:**

- Interceptors (`app.config.ts:57-61`): `httpInterceptor` (propio, solo telemetría) → `ortApiErrorInterceptor` (librería interna `@desarrolloort/ngx-utils`, normaliza y aplica política por status) → `authRefreshInterceptor` (propio, maneja 401) → `operationResultInterceptor` (ngx-utils, desenvuelve el `OperationResult` del backend y convierte `success:false` en `NormalizedApiError` **aunque el HTTP sea 2xx**).
- No hay `ErrorHandler` global de Angular; notificación centralizada vía `AppApiErrorNotifier` (`src/app/core/services/api-error-notifier.ts:14-17`) → `SnackbarHandler` (`src/app/shared/ui/snackbar/snackbar-handler.ts`), con **401/404 ignorados** globalmente (`IGNORED_GLOBAL_ERROR_STATUSES`) y delegados a cada feature.
- Política default de mensajes por status (400/401/403/404/409/422/429/500) vive **fuera del repo**, en `@desarrolloort/ngx-utils` (compilada, sin fuente disponible). Descarta el `message` del backend en `401/403/404`.
- **Desde 9e7cb92** la app la sobreescribe con `APP_API_ERROR_POLICY` (`src/app/core/services/api-error-policy.ts`): `useBackendMessage: true` para `400/401/403/404/409/422/429`. Los `5xx` quedan deliberadamente con el texto genérico del normalizador.
- **Desde 9e7cb92** el único lector de errores de API en pantallas y facades es `getApiErrorMessage(error, fallback)` (`src/app/shared/errors/api-error-message.ts`): devuelve `error.message` si es `NormalizedApiError`, sino el `fallback` del punto de uso. `CUSTOM_ERROR_MESSAGES`/`CUSTOM_ERROR_MESSAGE` ya no se usan en producción.
- Validación de formularios centralizada en `src/app/shared/forms/form-error-summary.ts`. Los mensajes de validación de formulario siguen siendo (y deben seguir siendo) 100% de frontend: no son errores de API.
- No hay i18n; todos los mensajes están hardcodeados en español, dispersos en componentes/facades.

**Backend:**

- Patrón _Result_ (no excepciones de dominio): `OperationResult<T>` (`Core/Utilities/OperationResult.cs`) con `Success`, `HttpCode`, `ErrorCode`, `Method`, `Message`, `Data`. Estáticos: `Ok`, `IsSuccess`, `IsFailed(errorCode, originMethod, message, httpCode=400, data)`.
- `ApiBaseController<T>.ValidateResponse` es el único punto de traducción `OperationResult` → `IActionResult` (`StatusCode(retorno.HttpCode, retorno)`).
- Dos middlewares globales:
  - `ExceptionHandlingMiddleware` — excepciones no capturadas → 401 (`UnauthorizedAccessException`/`AUTH_UNAUTHORIZED`), 409 (`InputSanitizationException`/`SANITIZATION_ERROR`), 500 genérico (`INTERNAL_ERROR`). Oculta el mensaje real en producción.
  - `ModelBindingErrorLoggingMiddleware` — uniforma los 400 de validación automática de `[ApiController]` (`ProblemDetails` → `OperationResult`, códigos `MBM_DA_01`/`MBM_DA_02`).
- Única excepción custom del repo: `InputSanitizationException`.
- Errores de DB (EF Core/Devart) **no se traducen explícitamente**: suben crudos hasta el middleware genérico (500/`INTERNAL_ERROR`). El código Devart generado no envuelve nada en `OperationResult`.
- Errores de la API externa `EnrollmentsAndPayments` sí se traducen explícitamente (`API_TIMEOUT`, `API_NETWORK`, `API_UNEXPECTED`).
- Códigos de error descentralizados por módulo en carpetas `Constants/` de cada `AppLogic.*` (ej. `RegistrationErrorCodes`), sin `.resx` ni catálogo central.
- Submódulo `Core` (Utilities, AzureService, LdapService, MailORT, Modules) fue inicializado durante esta auditoría (antes no estaba clonado).

### Integración

Front → Back: HTTP/JSON envolviendo `OperationResult`. Back → DB: EF Core/Devart (sin capa de traducción). Back → APIs externas: `EnrollmentsAndPayments` (bien mapeado), `Tivenos` (parcialmente auditado), `Core/AzureService`/`LdapService`/`MailORT` (pendiente auditoría detallada).

## FASE 6 — Problemas transversales detectados (cruce Front↔Back)

### Passthrough roto / responsabilidad incorrecta

- ~~**El hallazgo más grave de toda la auditoría**: en el frontend, `enrollments.api.ts:271-285` (`pay()`) fuerza `success:true` en **toda** respuesta 2xx del backend, anulando cualquier rechazo de pago que el backend intente comunicar con `success:false`/`message`/`errorCode` (ver FE-ENR-001/023).~~ **RESUELTO en ronda 1 (9e7cb92)**: el mapper ya no fuerza `success:true` y `EnrollmentPaymentResponse` ya no declara campos de error. El diagnóstico original quedó a medias en un punto: el frontend **nunca iba a recibir** un `success:false` por el canal de éxito, porque `operationResultInterceptor` lo convierte en `NormalizedApiError` antes de llegar al facade. Los campos de error del DTO eran, desde el principio, código inalcanzable — y por eso el fallback genérico se veía siempre.
- **Sigue en pie del lado backend**: `EnrollmentsAndPaymentsApiClient` puede fallar con passthrough de errores crudos de la API de Inscripciones y Pagos (BE-ENR-090/091). Ahora que el frontend propaga el mensaje del backend en 4xx, ese passthrough crudo **es visible al usuario** si el proveedor responde con un 4xx. La única barrera que queda es la política de `5xx`. Sanear BE-ENR-090/091 pasa de "higiene" a **prerrequisito**.
- Varios endpoints de backend documentan (Swagger) respuestas de error que la implementación real no genera (`CatalogsController.GetBanks`, BE-CAT-004) — riesgo de que el frontend nunca maneje esos casos "porque nunca los vio".
- Varios endpoints frontend (`getMyScholarships`, `getAvailableScholarships`, `getAcademicStepData`, `createApplication`) están **stubbeados** porque el backend removió o nunca expuso esas funcionalidades del lado que el frontend espera — de este lado backend, `ScholarshipFundService` (14 métodos) existe pero no tiene controller, lo que sugiere que la funcionalidad de becas está incompleta/discontinuada en ambos lados de forma coordinada pero no documentada como tal.

### Passthrough riesgoso de mensajes externos (no normalizados)

- Backend → cliente: LDAP (`AUTH_LDAP_94/95/96/97/98/99`, `EnviarContrasenia`), Azure Document Intelligence (`REC_DOC_05/07/99`), Google reCAPTCHA (`AUTH_CAPTCHA_03/04`), API de Inscripciones y Pagos (BE-ENR-090/091), servicio interno de mail (BE-LDAP-007).
- Frontend → usuario: ninguno de estos mensajes crudos se filtra especialmente en frontend — el `SnackbarHandler`/`AppApiErrorNotifier` los muestra tal cual si superan la política (no ignorados en 401/404), amplificando el riesgo de exposición.
- **Efecto de la ronda 1 sobre este riesgo — leer con atención**: reabilitar `useBackendMessage` en `401/403/404` **amplía** la superficie de exposición para esos tres status, que antes quedaban tapados por el `defaultMessage` de la librería. Los casos CRITICAL relevantes (BE-LDAP-016/017 en `POST /auth/complete-initial-password`, BE-AZR-013/023 en reconocimiento de documento) devuelven HTTP 400 y **ya estaban expuestos** antes del cambio, así que la ronda 1 no los empeora. Pero la conclusión práctica es la misma: **la política de mensajes del frontend no puede sustituir el saneamiento del backend**, y los ítems 1 y 5 de Cleanup Candidates son ahora la prioridad real. La única cobertura efectiva hoy es que los `5xx` colapsan a texto genérico — y eso solo protege lo que el backend clasifica como `5xx`.

### Duplicación de errores (mismo concepto, distinto código/mensaje)

- Backend: "Persona/Usuario no encontrado" aparece con ≥5 códigos distintos entre módulos (`INI_PAS_03`, `GEN_TOK_01`, `REFRESH_TOKEN_04`, `GEN_OEI_01`/`INS_EI_01` via `PersonaNoEncontradaMessage`, `PER_ADP_01`).
- Frontend: mensajes de fallback genéricos ("No se pudo completar el registro.", "Intentá nuevamente en unos minutos.") reutilizados para operaciones de negocio semánticamente distintas dentro de la misma feature.
- **Cambio de impacto tras la ronda 1**: esos fallbacks del frontend ya **no** son lo que ve el usuario cuando el backend manda un `message` — pasaron a ser texto de último recurso (red caída, `5xx`, respuesta sin `message`). Que sigan siendo genéricos importa menos; lo que ahora importa es que la duplicación del **backend** llega intacta al usuario. La deuda de mensajes se corrió de capa: es un problema de catálogo de backend, que es exactamente donde tiene que estar para reportarlo a Análisis Funcional.

**Antes de la ronda 1** — la cadena rota que motivó el hallazgo más grave:

```text
Pantalla: Paso 3 - Confirmación de pago (enrollments)
  ↓
Frontend handler: enrollment-payment.ts (confirmar medio de pago)
  ↓
API call: EnrollmentsApi.pay() [enrollments.api.ts:271-285]
  ↓
Backend endpoint: POST /enrollments/start-payment → PayWithPersonalAccount / RegisterExternalPaymentMethod / GenerateInvoicePaymentUrl
  ↓
Service: EnrollmentsAndPaymentsApiClient (llamada a API externa de Pagos)
  ↓
External API: API de Inscripciones y Pagos — puede rechazar con HTTP 200 + body de negocio, o HTTP error con body crudo
  ↓
Backend mapping: EnrollmentMapper.ToPaymentMessages — copia mensajes crudos sin sanear (BE-ENR-093); o SendAsync concatena errorContent crudo (BE-ENR-090/091)
  ↓
HTTP response: OperationResult con success/message/errorCode del backend (potencialmente correcto)
  ↓
Frontend mapping: EnrollmentsApi.pay() FUERZA success:true en cualquier 2xx, descartando el body real (FE-ENR-001)
  ↓

```

**Después de la ronda 1 (9e7cb92)** — mismo flujo, cadena cerrada:

```text
HTTP response: OperationResult { success:false, httpCode:409, errorCode:'PAY_INS_04', message:'Saldo insuficiente' }
  ↓
operationResultInterceptor: convierte success:false en NormalizedApiError (incluso si el HTTP fuera 2xx)
  ↓
ortApiErrorInterceptor + APP_API_ERROR_POLICY: 409 con useBackendMessage:true → conserva 'Saldo insuficiente'
  ↓
EnrollmentsApi.pay(): ya no interviene — el error no pasa por el mapper de éxito (FE-ENR-001 cerrado)
  ↓
enrollment-payment.ts:259-263 → getApiErrorMessage(error, 'Intentá nuevamente en unos minutos.')
  ↓
Mensaje mostrado al usuario: 'Saldo insuficiente' (el fallback solo aplica si no hay message: red, 5xx)
```

Lo que este flujo ilustra ahora es el **límite** del cambio: si la API de Inscripciones y Pagos rechaza con un HTTP de error y el backend concatena su `errorContent` crudo (BE-ENR-090/091), ese texto crudo es lo que el usuario ve — a menos que el status resultante sea `5xx`.
